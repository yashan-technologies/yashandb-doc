在集群数据库的环境下可能会出现一些异常问题，可以通过查看run log，比对集群的实际表现来确定问题原因并解决。

### 1. 集群启动过程中，数据库实例启动失败

**可能原因**：

多台服务器近似同时发起实例启动命令时，多个数据库实例出现并发启动的情况，此时可能由于内部冲突导致实例启动失败。

**可能的定位观测点**：

db run log中存在日志：`[AXC] trigger shutdown instance due to database is not open`。

**规避解决方案**：

避免多台服务器同时发起实例启动命令；手动启动实例时，按顺序登录各服务器依次操作，且必须将实例启动到open状态。

### 2. 集群运行过程中，出现数据库实例反复掉线后又被自动拉起的情况

**可能原因**：

多台服务器近似同时发起实例启动命令时，多个数据库实例出现并发启动的情况，此时可能由于内部冲突导致实例启动失败。

**可能的定位观测点**：

- yasdb进程被反复启停。
- db run log中存在日志：`[AXC] trigger shutdown instance due to database is not open`。

**规避解决方案**：

手动停止其中一台服务器上的实例，并重启另一台服务器上的实例至open状态，成功后再启动第一台服务器上的实例至open状态。

### 3. 集群运行过程中，出现数据库实例掉线后无法恢复拉起的情况

**可能原因**：

实例恢复阶段需要使用DATA BUFFER，此时可能无法淘汰出需要的页面内存导致恢复进程卡住。

**可能的定位观测点**：

- 查询v$instance_recovery，IN_RECOVERY字段为true，PHASE字段一直为LOCK RECOVERY SET，说明恢复进程卡住。
- 查询v$buffer_pool_statistics，NUM_RESIDENT和NUM_WRITE占NUM_TOTAL的占比较大，说明可用于淘汰的页面较少。
- 多次查询v$dbwr_statistics，频繁出现CURRENT_STATUS字段为BUFFER CLEAN的数据，说明BUFFER可用页面太少，经常性需要清理；或视图数据完全不改变，说明清理的过程可能被在线恢复阻塞。
- 查询v$sysstat，NAME字段为BUFFER FREE REQUEST的数据持续增加，说明淘汰页面次数增多。

**规避解决方案**：

连接现存open状态的主实例，执行ALTER SYSTEM SET DATA_BUFFER_SIZE语句临时扩展DATA BUFFER。若v$instance_recovery的PHASE字段一直为LOCK RECOVERY SET，继续扩展DATA BUFFER直到字段改变，掉线的实例成功恢复到open状态。
