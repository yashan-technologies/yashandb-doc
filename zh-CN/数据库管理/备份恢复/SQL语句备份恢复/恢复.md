通过SQL语句执行恢复操作适用于单机部署、共享集群部署的数据库，且要求执行恢复操作的数据库版本需与生成备份集的数据库版本完全一致。

当需恢复的数据量大或希望提升恢复效率时，可适当增大并发度，并发度默认为2。

恢复过程中，可以通过$YASDB_DATA/log/run/run.log运行日志查看恢复过程的详细日志。

> **Caution**:
> 
> 在双复制组主备部署环境中，执行数据库恢复操作后的实例均会成为主库，若目标实例为备库且原主库存活则不可对该实例执行恢复操作，否则会出现双主导致部署状态或数据异常。如需重建备库请执行备库BUILD操作。

## 完整恢复

完整恢复是指将全库备份集中的备份文件，解压、解密恢复到数据库目录，然后回放备份集中的归档日志将数据库恢复到一致性状态，可将数据库完整恢复到备份时刻。

- 基于全量备份集恢复：直接从该备份集中恢复所有文件，包括控制文件、数据文件、归档日志。

- 基于增量备份集恢复：首先恢复LEVEL 0备份集中的数据文件，然后用后续的LEVEL 1备份集中的页面覆盖数据库的页面，最后用当前增量备份集的归档日志，回放数据库到一致性状态。

### 操作说明

- RESTORE DATABASE语句仅SYS用户才可执行，详细语法介绍请查阅[RESTORE DATABASE](../../../开发手册/SQL参考手册/SQL语句（yashan模式）/RESTORE DATABASE)。

- 共享集群部署中，只能在主实例（V$INSTANCE视图中INSTANCE_ROLE字段为MASTER_ROLE的实例）上执行数据库恢复操作。

- 如果数据库备份集采用加密备份，恢复时需指定解密关键字及其解密密码。

- 恢复前数据库环境准备：

  - 数据库实例处于NOMOUNT阶段。

  - 在单机一主一备部署中，若已开启[yasom仲裁选主](../../../工具手册/yasboot/yasboot命令介绍/yasboot election)，需先关闭仲裁选主再进行恢复操作，待恢复完成后再按需还原对应配置。

  - 在单机一主多备部署中，在对主库（尤其是故障场景中仅剩孤立主库时）执行恢复操作前，需要先关闭自动降备功能（将HA_ELECTION_LEADER_LEASE_ENABLED设置为FALSE），避免因未及时检测到备库心跳而触发自动降备，待恢复完成后再按需还原对应配置。
  
  - 恢复到与备份集不同的数据库文件或日志文件路径（例如高可用部署中的主备复制）时，需要先配置DB_FILE_NAME_CONVERT和REDO_FILE_NAME_CONVERT参数指定文件路径转换。
  
  - 需手动清理已有数据文件：单机部署中要求$YASDB_DATA/dbfiles中不存在数据文件，共享集群部署中则要求+DG0目录（安装时默认的第一个磁盘组名称，调整为其他值时此处相应修改）下不存在数据文件，否则将触发YAS-00311错误。

  - 执行全量恢复且仅需恢复备份集中的内容时，需要清空当前数据库中的归档日志文件（默认路径为$YASDB_DATA/archive），避免执行RECOVER操作时回放残留归档日志文件中的数据从而导致实际恢复出的数据与备份集不一致的问题。

  - 如果备份集中存在加密对象，需先打开对应的密钥钱包文件，再进行恢复操作。

### 基于全量备份集恢复

全量恢复是指基于全量备份生成的备份集将数据库恢复至备份时间点，属于完全恢复，恢复成功后可以直接打开当前数据库。对于共享集群，在主实例恢复成功后，需要依次启动其他实例（可查阅[共享集群启停](../../../共享集群/集群服务管理/共享集群启停)）。

示例（单机部署）

```sql
-- 1. 在NOMOUNT阶段执行RESTORE DATABASE，执行完成后数据库会启动至MOUNT阶段
-- 场景1：指定并发度为6进行恢复
RESTORE DATABASE FROM '/data/backup/full_20211209191000' PARALLELISM 6;

-- 场景2：基于加密的备份集恢复需指定DECRYPTION关键字，并确保密码与加密时的一致
RESTORE DATABASE DECRYPTION yas2022 FROM '/data/backup/bak_20211209191100';
 
-- 2. 执行RECOVER DATABASE
-- 成功恢复备份集后，若归档日志和在线日志连续且完整，YashanDB将自动应用所有日志
RECOVER DATABASE;

-- 3. 打开数据库
ALTER DATABASE OPEN;
```

### 基于增量备份集的连续恢复

基于增量备份集的连续恢复是指使用增量备份生成的备份集对数据库进行恢复，可以恢复至备份集链路中任意一次执行备份操作的时间点。

在执行增量备份集恢复时，需先恢复LEVEL 0备份集然后依次按顺序指定增量备份集进行恢复，且需确保目标备份集所依赖的备份集的备份文件保存目录存在且完整：

- 假如零级增量备份指定tag为incr_0，普通一级增量备份指定tag为incr_1_1、incr_1_2、……（按顺序发起备份）：

   - 当指定tag为incr_1_2的一级增量备份恢复时，必须保证tag为incr_0的零级增量备份以及tag为incr_1_1的普通一级增量备份的备份文件保存目录存在且完整，否则将会触发YAS-00313错误。

- 假如零级增量备份指定tag为incr_0，累积一级增量备份指定tag为incr_1_1、incr_1_2、……（按顺序发起备份）：

   - 当指定tag为incr_1_2的一级增量备份恢复时，必须保证tag为incr_0的零级增量备份的备份文件保存目录存在且完整，否则将会触发YAS-00313错误。

- 假如零级增量备份指定tag为incr_0，累积一级增量备份指定tag为incr_1_1，普通一级增量备份指定tag为incr_1_2、累积一级增量备份指定tag为incr_1_3、普通一级增量备份指定tag为incr_1_4、……（按顺序发起备份）：

   - 当指定tag为incr_1_4的一级增量备份恢复时，必须保证tag为incr_0、incr_1_3的增量备份的备份文件保存目录存在且完整，否则将会触发YAS-00313错误。

   - 当指定tag为incr_1_3的一级增量备份恢复时，必须保证tag为incr_0的零级增量备份的备份文件保存目录存在且完整，否则将会触发YAS-00313错误。

如果连续增量备份集中包含LSC表的slice文件，连续restore必须严格遵循备份生成顺序，否则可能导致slice文件丢失。如果某次restore失败，再次使用同一个备份集重复restore时，可能会因为已存在slice文件导致restore再次失败，此时需先手动清除对应slice文件后再继续执行restore。

基于tag的增量备份集恢复有2个可选关键字：

- INCREMENTAL NOREDO：指定该关键字时，不恢复备份集中的redo和归档日志文件，完成恢复操作后数据库仍不可开启正常使用，需继续恢复同一增量备份集链路中的其他增量备份集，整个链路中最后一次恢复时不可指定INCREMENTAL NOREDO。

- INCREMENTAL：指定该关键字时，表示是基于增量备份集的完全恢复，完成恢复操作后，将数据库启动至MOUNT阶段执行RECOVER后，可以启动至OPEN。

示例（单机部署）

```sql
-- 1. 在NOMOUNT阶段执行RESTORE DATABASE
-- 基于增量备份集恢复首次必须恢复LEVEL 0的备份集，指定INCREMENTAL NOREDO参数可加快恢复速度
RESTORE DATABASE INCREMENTAL NOREDO FROM '/data/backup/incr_0_20211209193516';

-- 2. 在此基线恢复成功的基础上，可连续恢复同一数据库的增量备份集，但最后一次恢复时不可指定INCREMENTAL NOREDO
RESTORE DATABASE INCREMENTAL FROM '/data/backup/incr_1_20211209193740';

-- 3. 启动数据库至MOUNT阶段执行RECOVER DATABASE
ALTER DATABASE MOUNT;
RECOVER DATABASE;
-- 完成恢复后不可再执行增量备份集恢复

-- 4. 启动数据库至OPEN阶段
ALTER DATABASE OPEN;
```

## 归档恢复

归档恢复是指在数据库完整恢复（RESTORE DATABASE）后但暂未进行日志恢复（RECOVER DATABASE）时，将归档备份集中的文件恢复到数据库的归档目录并注册到数据库中，尽可能补充数据库备份集中缺失的归档日志，使数据库恢复更多的数据。

详细语法请查阅[RESTORE ARCHIVELOG](../../../开发手册/SQL参考手册/SQL语句（yashan模式）/RESTORE ARCHIVELOG)。

### 操作说明

- 共享集群部署中，只能在主实例（V$INSTANCE视图中INSTANCE_ROLE字段为MASTER_ROLE的实例）上执行归档恢复操作。

- 归档日志只能恢复成现有归档备份集的全集或子集，且指定恢复范围的方式（SCN、SEQUENCE或时间）不受备份范围指定方式约束。

- 如需恢复多个归档备份集时，可通过FROM SEARCHDIR指定集合的文件夹（备份集目录的上一层）。

- 如果归档备份集采用加密备份，恢复时需指定DECRYPTION关键字及解密密码。若多个备份集的密码不同，指定FROM SEARCHDIR集合恢复时会跳过密码不同的备份集，可根据密钥分批执行恢复操作。

- 恢复前数据库环境准备：

  - 数据库已完成RESTORE DATABASE且启动至MOUNT阶段，但暂未执行RECOVER DATABASE。

  - 确保恢复归档日志文件的目标路径存在，省略TO destpath时默认恢复至ARCHIVE_LOCAL_DEST参数所配置的路径（默认值为$YASDB_DATA/archive）。

### 全恢复

全恢复是指恢复现有归档日志备份集中的所有归档日志，指定ALL关键字时表示执行全恢复。

示例（单机、共享集群部署）

```sql
-- 此时数据库已完成RESTORE DATABASE操作并启动至至MOUNT阶段，但暂未完成RECOVER DATABASE
RESTORE ARCHIVELOG ALL FROM BACKUPSET '/data/backup/all_20211209191000';
-- RESTORE ARCHIVELOG后再按需执行RECOVER DATABASE
```

### 基于SCN恢复

基于SCN恢复是指通过SCN指定此次需要恢复的归档日志范围，具体目标范围可以使用如下关键字进行指定：

- FROM SCN n：表示恢复范围为[n日志所在文件,当前备份集的终点文件]。

- SCN BETWEEN n AND m：表示恢复范围为[n,m]日志所在归档日志文件。

- UNTIL SCN n：表示恢复范围为[当前备份集的起点文件,n日志所在文件]。

示例（单机、共享集群部署）

```sql
-- 此时数据库已完成RESTORE DATABASE操作并启动至至MOUNT阶段，但暂未完成RECOVER DATABASE
RESTORE ARCHIVELOG FROM SCN 505411989407080448 FROM BACKUPSET '/data/backup/scn_20211209191000';
-- RESTORE ARCHIVELOG后再按需执行RECOVER DATABASE
```

### 基于SEQUENCE恢复

基于SEQUENCE恢复是指通过归档日志文件的序列号SEQUENCE指定此次需要恢复的归档日志范围，语句中指定的文件必须存在。具体目标范围可以使用如下关键字进行指定：

- FROM SEQUENCE x：表示恢复范围为[x,当前备份集的终点文件]。

- SEQUENCE BETWEEN x AND y：表示恢复范围为[x,y]区间的所有归档日志文件。

- UNTIL SEQUENCE x：表示恢复范围为[当前备份集的起点文件,x]。

通过V$ARCHIVED_LOG视图可以获取当前已存在的归档日志文件的序列号（SEQUENCE#字段）以及其他详细信息。

示例（单机、共享集群部署）

```sql
-- 此时数据库已完成RESTORE DATABASE操作并启动至至MOUNT阶段，但暂未完成RECOVER DATABASE
RESTORE ARCHIVELOG UNTIL SEQUENCE 10 FROM BACKUPSET '/data/backup/seq_20211209191000';
-- RESTORE ARCHIVELOG后再按需执行RECOVER DATABASE
```

### 基于时间恢复

基于时间恢复是指通过时间指定此次需要恢复的归档日志范围，实际会将指定时间点对应的某条日志所在的整个归档日志文件进行恢复。

时间格式可以为：

- `'2021-12-09 19:35:55'`：此格式需要与当前会话的DATE_FORMAT参数所指定格式匹配。

- `TO_DATE('2021-12-09 19:35:55','yyyy-mm-dd hh24:mi:ss')`：使用TO_DATE函数转换。

- `TO_TIMESTAMP('2021-12-09 19:35:55','yyyy-mm-dd hh24:mi:ss')`：使用TO_TIMESTAMP函数转换。

具体目标范围可以使用如下关键字进行指定：

- FROM TIME t：表示恢复范围为[t时间点起第1条日志所在文件,当前备份集中最新的归档日志文件]。

- TIME BETWEEN t1 AND t2：表示恢复范围为[t1,t2]期间的所有日志记录所在归档日志文件。

- UNTIL TIME t：表示恢复范围为[当前备份集中最早的归档日志文件,t时间点前最后1条日志所在文件]。

示例（单机、共享集群部署）

```sql
-- 此时数据库已完成RESTORE DATABASE操作并启动至至MOUNT阶段，但暂未完成RECOVER DATABASE
RESTORE ARCHIVELOG UNTIL TIME TO_DATE('2024-10-28 08:14:01','yyyy-mm-dd hh24:mi:ss') FROM BACKUPSET '/data/backup/time_20211209191000';
-- RESTORE ARCHIVELOG后再按需执行RECOVER DATABASE
```

## 基于时间点恢复

基于时间点的恢复（PITR）是指基于数据库备份集还原的数据库文件和归档日志文件将数据库恢复到备份时间点至最新时间点期间某一时刻的状态。

### 操作说明

- RESTORE DATABASE语句仅SYS用户才可执行。

- 共享集群部署中，只能在主实例（V$INSTANCE视图中INSTANCE_ROLE字段为MASTER_ROLE的实例）上执行恢复操作。

- 如果LSC表在备份集后生成了slice文件，在以下场景可能导致恢复后该LSC表存在数据不一致现象：

  - 数据库原来的slice文件全部存在，但是使用老的时间点恢复，此时该LSC表会多出部分slice文件。

  - 数据库原来的slice文件被清理，使用基于时间点的恢复，LSC表可能丢失存储在slice文件中的数据。

- 恢复前数据库环境准备：

  - 数据库实例处于NOMOUNT阶段。

  - 在单机一主一备部署中，若已开启[yasom仲裁选主](../../../工具手册/yasboot/yasboot命令介绍/yasboot election)，需先关闭仲裁选主再进行恢复操作，待恢复完成后再按需还原对应配置。

  - 在高可用部署中，若已开启自动降备功能（主节点上的HA_ELECTION_LEADER_LEASE_ENABLED为TRUE），需先关闭此功能再进行恢复操作，待恢复完成后再按需还原对应配置。

  - 恢复到与备份集不同的数据库文件或日志文件路径（例如高可用部署中的主备复制）时，需要先配置DB_FILE_NAME_CONVERT和REDO_FILE_NAME_CONVERT参数指定文件路径转换。
  
  - 需手动清理已有数据文件：单机部署中要求$YASDB_DATA/dbfiles中不存在数据文件，共享集群部署中则要求+DG0目录（安装时默认的第一个磁盘组名称，调整为其他值时此处相应修改）下不存在数据文件，否则将触发YAS-00311错误。

  - 执行基于时间点的恢复前，需确保归档日志文件（默认路径为$YASDB_DATA/archive）存在，例如通过RESTORE ARCHIVELOG恢复归档日志。

  - 如果备份集中存在加密对象，需先打开对应的密钥钱包文件，再进行恢复操作。

### 操作步骤

1. 执行[RESTORE DATABASE](../../../开发手册/SQL参考手册/SQL语句（yashan模式）/RESTORE DATABASE)语句，基于指定的数据库备份集还原出数据库文件。

2. 执行[RESTORE ARCHIVELOG](../../../开发手册/SQL参考手册/SQL语句（yashan模式）/RESTORE ARCHIVELOG)语句，基于指定的归档日志备份集还原并注册归档日志文件至数据库。

3. 执行[RECOVER DATABASE UNTIL](../../../开发手册/SQL参考手册/SQL语句（yashan模式）/RECOVER DATABASE)语句，基于数据库文件和归档日志恢复数据库到备份时间点至最新时间点期间某一时刻（通过时间或SCN指定）的状态。

4. 重置redo时间线。

示例（单机、共享集群部署）

```sql
-- 1. 基于数据库备份集恢复数据库文件
RESTORE DATABASE FROM '/data/backup/full_20211209191000';

-- 2. 基于归档日志备份集恢复归档日志文件
RESTORE ARCHIVELOG ALL FROM BACKUPSET '/data/backup/all_20211209191000';

-- 3. 基于数据库文件和归档日志恢复数据库到指定时间点的状态
-- 方案一：指定日志序号时间点进行恢复
RECOVER DATABASE UNTIL TIME TO_DATE('2021-12-09 19:35:55','yyyy-mm-dd hh24:mi:ss'); 

-- 方案二：指定SCN（通过V$DATABASE视图获取）进行指定时间点恢复，假设258477020237086720是用户在数据库发生故障前记录下的SCN值
SELECT CURRENT_SCN FROM V$DATABASE;
RECOVER DATABASE UNTIL SCN 258477020237086720;
 
-- 重置redo时间线并打开数据库
ALTER DATABASE OPEN RESETLOGS;
```
