## Version Information

**Version Number**: v23.4.1.100

**Release Date**: May 8, 2025

## Version Positioning

YashanDB v23.4 is positioned as a Long-Term Support (LTS) version. The new version focuses on developing product capabilities around financial core business systems, aiming to provide a 1:1 replacement for Oracle, enhancing Oracle compatibility comprehensively, and building high availability capabilities for the financial industry, achieving seconds-level recovery with library-level flashback, etc. The release also introduces MySQL syntax mode functionality to improve performance, along with a complete set of data migration, monitoring operations, and developer tools to support market project scale sales and bulk replication.

## Feature Updates

YashanDB v23.4 inherits all functionality released in YashanDB v23.3.1 and adds the following key features:

### SQL Engine Enhancements

#### SQL Functionality Enhancements

- Support for TIMESTAMP with Time Zone type: A new TIMESTAMP with time zone data type is added to store date and time information, timezone offsets, or timezone names, suitable for scenarios requiring accurate timing and supporting cross-border operations.
- Support for JSON_VALUE function: A new JSON_VALUE function is added to extract a single scalar value (such as a string, number, or boolean) from JSON data.
- INSTR function supports CLOB type: Now supports searching for a specified string within CLOB type data and returns its position, enhancing the efficiency of processing large text data.
- Extended length of projection column field aliases: In version v23.4, the maximum length for projection column fields and aliases has been increased from 20B to 64B, improving usability by avoiding truncation and renaming conflicts in scenarios where long field names are used with * queries without specified aliases.

#### PL Functionality Enhancements

- PACKAGE supports PROCEDURE and FUNCTION overloading: It allows defining multiple procedures or functions with the same name in the same package, as long as their parameter lists differ in number, data type, or order. YashanDB determines the specific overloaded version to call based on the actual parameters passed at runtime, improving code readability, maintainability, and developer flexibility.
- Support for PIPELINED pipeline function: The PIPE ROW function returns data one row at a time to the caller without waiting for all data to be processed, improving performance in scenarios requiring fewer rows but with high computation.
- Cursor supports FOR UPDATE functionality: PL now supports the cursor for update functionality, used to lock rows in the result set of a query, preventing other transactions from modifying or deleting these rows. Combined with the CURRENT OF clause, it accurately locates the current cursor row for updates or deletions, addressing scenarios with high data consistency requirements and row-by-row processing.
- New MOD usage in PL: YashanDB introduces the MOD syntax for PL, allowing modulo operations similarly to the `%` operator in Oracle, enriching the usage scenarios and enhancing compatibility.
- Optimized PL parsing mechanism: In previous versions, when mixing PL statements and SQL statements, PL variable matching took precedence, leading to significant compatibility-related modifications when migrating Oracle code. The current version removes the pre-compilation step, prioritizing matching the table column resources in SQL statements before matching PL variable blocks.

#### SQL Performance Optimizations

- Enhanced optimization rules
  - Constant parameterization and parameter-based plan management: This version intelligently manages execution plans by reducing memory consumption in buffer pools through the two-level buffer mechanism for parent-child cursors, effectively lowering memory consumption by more than 80% in common SQL concatenation scenarios.
  - Support for COUNT(*) operator pushdown: In SQL queries where the projection column is count(*) or count(1), the count process can now be pushed down to the storage layer, reducing interaction times between the SQL layer and the storage layer, saving time and improving performance.
  - CTE query rewrites support plan sharing and materialization: In scenarios with multiple subqueries using CTE, the optimizer optimizes based on materialization/cost calculations/inline methods, achieving shared materialization of subqueries, reducing the number of CTE executions, and speeding up query efficiency.
  - Support for multi-column IN index optimization: In scenarios with multiple columns in IN, YashanDB optimizes the planner to evaluate plans using combination indexes on col1, col2, col3 and single-column indexes, executing based on the lowest cost indexes and scan methods to enhance execution efficiency.
  - Optimized sorting operator in subqueries: The optimizer eliminates sorting operations in subqueries if the parent query projection columns consist only of aggregates and constants. For instance, in SELECT COUNT(*) FROM (SELECT * FROM T1 ORDER BY 1), T1 does not need sorting, reducing sorting actions and enhancing execution efficiency.
  - LIKE variable `||'%'` supports index: If a filter is like variable `||'%'`, this version optimizes to utilize the index on the filter field in large table scans, enhancing query speed.

- Enhanced execution performance
  - Optimized algorithms for aggregate functions with DISTINCT: This version introduces a HASH deduplication algorithm for aggregate functions with DISTINCT, significantly improving performance in scenarios without sorting as data repetition increases.
  - Optimized multi-row subquery execution: In scenarios where the result set is multi-row, the use of subquery buffer reuse effectively reduces performance costs for large data volumes. Compared to earlier versions, complex subquery performance has improved more than threefold, satisfying high concurrency OLTP and complex analytical mixed load requirements.
  - Supported SORT GROUP BY STOPKEY operator: When the outer SQL layer has rownum or limit syntax returning only a few rows, and the inner layer has a large table group, supporting the SORT GROUP BY STOPKEY operator can accelerate SQL execution efficiency.
  - Optimized PL language FORALL INSERT data processing: The FORALL bulk insert technique improves scalar type write performance by an average of 85%, with significant enhancements in writing CLOB types exceeding those of Oracle; UDT types see an improvement of over 30%.
  - Optimized deterministic function calls: The version adjusts the execution of functions that are deterministic. When the input is a constant, it rewrites to a constant; when the input is a bound parameter, it participates in optimizing and executing dynamic constant feature buffers, resulting in significant performance improvements compared to Oracle.
  - Supported parallel full table scans with UDT: This version adds support for parallel scans on tables with Geometry columns during full table scans, and some GIS functions also support parallel capabilities, enhancing the performance of GIS functions and objects.

- DBLink Performance Optimizations
  - Reduced interaction latency, interaction counts, query projection optimizations, and internal protocol encoding/decoding optimizations for DBLink: By enhancing interaction latency, interaction counts, and internal protocol encoding/decoding, the time spent on each step is reduced, achieving performance optimizations. The enhancements lead to significant performance improvements while accessing Oracle via DBLink in specified scenarios.
  - DBLink supports collection and use of statistics: When accessing Oracle through DBLink, YashanDB can query and summarize the statistics of remote tables, allowing the optimizer to generate more accurate execution plans for complex queries involving DBLink.

#### GIS Capability Enhancements

- Before version v23.4, the CREATE TABLE syntax only supported ST_GEOMETRY types for creating GIS tables. This version allows the Geometry column to specify subtypes and SRID, e.g., `geometry(point, 4326)`, compatible with PostGIS syntax and behavior, and also supports the Geometry_Columns view for querying subtypes, SRID, and dimensions of Geometry data, improving usability.
- Support for ST_MakeValid function, which converts invalid Geometry objects into valid Geometry objects without losing vertices.
- Support for ST_CollectionExtract function, which extracts and returns specified types of Geometry objects from a (Multi) Geometry object.
- Support for ST_Centroid function, which calculates the centroid (geometric center) of a geometric shape.
- Support for ST_PointOnSurface function, which returns any point located inside a geometry instance.
- Support for ST_Transform function, which transforms and returns the coordinate reference system of the provided Geometry object to a specified coordinate reference system.

### Storage Engine Enhancements

#### Storage Capability Enhancements

- Support for [full database flashback](../../Development Guide/SQL Reference Manual/SQL Statements/ALTER DATABASE.md#flashbackdatabaseclauses): Based on flashback log snapshot point (Marker) technology, implementing full-library rollback to any point in time within seconds using the FLASHBACK DATABASE syntax clause. This is mainly used for system upgrade/rollback, safety event response, test environment reset, data auditing and analysis, data cleaning rollback, and logical error correction.
- YStream parsing DDL supports the inclusion of primary key information: YashanDB assembles primary key information into a JSON string written to redo logs, which YStream parses as a string, allowing YStream to derive primary key information when used, enriching usage scenarios.
- ALTER TABLE supports the UPDATE GLOBAL INDEXES functionality: ALTER TABLE implements the UPDATE GLOBAL INDEXES syntax clause, enabling the simultaneous update of related global indexes during DROP, SPLIT, TRUNCATE, and other partition operations on partitioned tables, preventing index failure due to partition operations and ensuring the correctness and performance of queries, simplifying management by eliminating the need for manual index rebuilding.
- Support for [merging partitions](../../Development Guide/SQL Reference Manual/SQL Statements/ALTER TABLE.md#mergetablesubpartitions): Through the addition of the MERGE PARTITIONS syntax clause, it supports merging adjacent partitions into a single partition, reducing the number of partitions. Merging partitions aids in data integration, especially when data no longer requires storage according to the original partitioning rules. Merging partitions will delete local index partitions that correspond to the selected partition and mark those corresponding local index partitions as UNUSABLE. Manual rebuilding of indexes can be performed or utilize the UPDATE GLOBAL INDEXES clause to update the global index. Effectively reducing the number of partitions simplifies management and reduces maintenance workload.
- Support for tablespace backup and recovery: The new BACKUP/RESTORE TABLESPACE syntax clause enables backup and recovery capabilities for tablespaces. This can effectively reduce backup recovery time, provide flexible backup recovery strategies, and also supports viewing tablespace backup set information through the DBA_DATAFILE_BACKUPSET view. The current version only supports tablespace backup and recovery on Standalone Deployment.
- By default, the recycle bin is enabled in this version, meaning that the recycle bin switch RECYCLEBIN_ENABLED is set to ON by default for recovery from misoperations.
- Enhancements in statistics capabilities:
  - Support for real-time collection of basic statistics (DML real-time updates statistics): A new global parameter OPTIMIZER_REAL_TIME_STATISTICS controls whether to enable real-time collection of statistics, defaulting to FALSE. Setting it to TRUE allows real-time collection of statistics during DML/DDL on tables, enabling real-time modification of basic statistics (such as row counts, min/max values) during SQL execution, improving accuracy and allowing the optimizer to avoid performance loss from using default statistics.
  - DBMS_STATS advanced package gather_schema_stats function adds options parameter: In version 23.4, using DBMS_STATS.GATHER_SCHEMA_STATS to collect statistics by SCHEMA would require a full re-collection of all objects. This version introduces the options setting capability to allow collecting statistics based on table dimensions as needed, improving the efficiency of gathering statistics.
  - Support for default sample rate auto_sample_size: A new DBMS_STAT.AUTO_SAMPLE_SIZE constant specifies the automatic sampling rate, which is effective during GATHER_DATABASE_STATS, GATHER_INDEX_STATS, GATHER_SCHEMA_STATS, and GATHER_DATABASE_STATS collection. This parameter does not apply to dynamic sampling, enhancing Oracle compatibility and improving user experience.
  - Statistics collection progress display: A new view, DBA_OPTSTAT_OPERATIONS, records the operational records of gather_table_stats, gather_index_stats, gather_schema_stats, and gather_database_stats procedures, including historical records of statistical operations executed using DBMS_STATS advanced packages and database level execution; a new view DBA_OPTSTAT_OPERATION_TASKS records target objects and information that the statistics parent operation needs to process. This view breaks down parent operations in DBA_OPTSTAT_OPERATIONS into sub-operations for each statistics collection object, which can include tables, indexes, or partitions. When manually triggering and scheduling tasks for statistics collection, users can query task progress, status, and starting time through these two views.

#### Performance Optimizations

- Support for SESSION-level BLOCK CACHE capability: When accessing global resources, locking is required to control concurrency. For reads, while requesting a shared lock, adding a shared lock typically leads to Spin Lock contention. In scenarios with high concurrency, the conflicts due to Spin Lock can be significant. By introducing a SESSION-level Block Lock Cache, the resource is localized, reducing global resource lock conflicts, thereby improving concurrent read performance. Additionally, multiple system parameters control the quantity of Block Lock Cache for each SESSION, with a new dynamic view V$SESSION_LOCK_CACHES added to check each SESSION's cache details, allowing users to adjust flexibly based on varying high concurrency scenarios.
- IO performance optimization for INSERT INTO SELECT scenarios: In cases where INSERT INTO SELECT operations insert into tables with multiple indexes, YashanDB optimizes its internal index transaction mechanisms in this version, reducing the number of REDO write IO operations and write wait times during processing small data volumes, thereby enhancing insert performance to match Oracle in this scenario.
- Support for setting table parallelism: This version adds support for configuring the parallelism of tables in CREATE/ALTER TABLE. Once the table's parallelism is set, full table scans default to parallel scans. Users can observe current parallelism through the degree field in the dba_tables view, effectively enhancing query performance when processing large-scale data queries.
- Support for parallel creation/validation of constraints: In scenarios with large data volumes and constraints on tables, considerable time is spent scanning large data amounts to check integrity of related conditions. Consequently, in full table scans for creating/checking constraints, adding parallel processing enhances processing efficiencies.

#### High Availability Enhancements

- Enhanced automatic switching capability for one-primary/one-standby custom configuration conditions: In a one-primary/one-standby standalone deployment scenario, election functionality based on the yasom process can ensure business continuity. This version supports conditional failover through new configuration parameters FAILOVER_HEALTH_CONDITION and FAILOVER_ERROR_CONDITION, representing switch conditions during specific anomalies (including archive disk full, redo write failures, DBWR dirty page flush failures, etc.) and when primary database throws certain error codes to the client. Upon triggering conditions, the primary database shuts down to implement automatic switching.

### YAC Product Capabilities

#### Multi-site Multi-center High Availability Capability

- The primary/standby cluster supports automatic failover in all instances of the primary cluster fail scenarios, enhancing product fault awareness and switching capabilities while reducing operational complexity and improving product usability.
- All instances of the standby cluster support read capabilities, improving read performance and stability of the standby cluster in read-write separation scenarios.
- Disaster recovery clusters support local disk deployment of single instances, reducing deployment and management costs in disaster recovery scenarios.
- Enhanced YAC IO split-brain protection: Previous versions provided the IO Fencing method based on in-transit IO protection algorithms; however, such algorithms could extend cluster RTO significantly. If storage devices exhibit poor IO performance or frequent IO bottlenecks, users might need to increase YAC's DISK_HB_KEEP_ALIVE configuration value to ensure the reliability of the algorithm. To better address this, version v23.4 introduces hardware IO protection built on SCSI and similar protocols, using persistent reservations in shared storage devices for comprehensive security and improved RTO.

#### Functionality Optimization and Improvement

- New support for online node scale out: As businesses grow, the existing database node specifications may not meet operational requirements; therefore, version v23.4 allows online scale out of database nodes in YACs to meet the need for database node scale out during business growth.
- Enhanced online DDL capabilities: YACs in version v23.4 provide online create/rebuild indexes and online shrink table capabilities, reducing operational complexity and improving product usability.
- New GIS capability support: The v23.4 version adds GIS capabilities, supporting complex spatial queries through a built-in geospatial data processing engine to meet the demands of smart cities, logistics tracking, and similar scenarios.
- New backup support for standby clusters: Previous versions only supported backups on the primary cluster in YACs, but due to the larger business scope in the primary cluster, execution of backups could impact performance and stability. Version v23.4 supports backup operations on the standby cluster, reducing the impact of backups on the primary cluster and enhancing system stability.
- Support for NOLOGGING capability: The ability to specify NOLOGGING when using *yasldr*, CREATE/ALTER INDEX, LOAD DATA and other operations, avoids generating REDO logs during the process, thereby enhancing performance in related scenarios.
- Enhanced YFS capabilities: Current YFS management is limited as it cannot distribute data across multiple disks, leading to IO load imbalance and poor performance. Version v23.4 introduces striping capabilities to YFS, supporting various file configurations for striping to balance the load across all disks in the disk group and reduce I/O latency. For example, parameters like DATA_STRIPING and REDO_STRIPING specify whether different data files are enabled for YFS striping functionality, improving overall performance.

#### Performance Optimizations

- Domestic performance optimization: The v23.4 version optimizes YACs for domestic CPUs such as Kunpeng and Haiguang under multi-NUMA scenarios. Testing in Kunpeng CPU and TPCC scenarios shows a scaling ratio exceeding 0.8 from 1 to 2 to 4 nodes. 
- UNDO data affinity: Each instance in YAC has its own UNDO tablespace. To reduce performance loss due to UNDO management during Cache Fusion, version v23.4 introduces **UNDO affinity** capability, binding specific transactions or data operations to a particular instance's UNDO tablespace, thereby lowering inter-instance lock contention and overhead on global buffer transmission, enhancing overall system performance and stability.

### Distributed Product Capabilities

#### Column Storage Capability Enhancements

- CREATE TABLE AS SELECT supports BULKLOAD: By adding /*+bulkload*/ hint after create table as select, batch insert functionality can be applied to column storage LSC tables during CTAS syntax, reducing redo generation and improving insert speed.
- Support for calculating OUTLINE LOB field lengths: It supports calculating the lengths of outline LOB fields in LSC tables, including LENGTH, CHAR_LENGTH, LENGTHB functions for character and byte length statistics.
- INSERT /*+BULKLOAD*/ INTO supports execution when AUTOCOMMIT is ON: Previously, inserts into LSC tables using INSERT /*+bulkload*/ required AUTOCOMMIT to be OFF; users needed to manually add transaction commits to avoid partial uncommitted transactions. The current version introduces the enable_bulkload_auto_commit parameter to control automatic commits, enhancing flexibility in scripts using the bulkload feature.
- INSERT INTO SELECT and CTAS support OUTLINE LOB: IN version v23.4, INSERT INTO SELECT and CREATE TABLE AS SELECT, commonly used in daily operations and business systems, are supported when operating on LOB columns exceeding 32000 bytes, improving flexibility and meeting data warehouse operational habits.
- Supports DUAL and list hybrid query (using column execution engine): Previous versions did not support hybrid queries combining the DUAL table with LSC tables; this version now supports this functionality to meet more business usage scenarios.
- CREATE TABLE AS SELECT supports retries: During the INSERT SELECT phase, if resources are insufficient, the previous version did not retry and simply returned an error to the client. The current version uses memory allocation, session resources, and related error information to implement automatic retries in certain scenarios if create table as select fails, requiring no user intervention. The maximum retry duration is 30 seconds, failing if not successful within that time.
- Support for SYS_GUID function: This function generates globally unique identifiers applicable to scenarios requiring unique identifiers within distributed systems, for use in generating primary key data and data synchronization, etc.
- Support for TABLESPACE SET space reclamation functionality: ISC Distributed Cluster Deployment allows ALTER TABLESPACE xxx SHRINK SPACE [KEEP xxx] syntax to enable TABLESPACE SET space compression while specifying the desired size after compression, enhancing data volume management and increasing resource utilization efficiency.

#### Performance Optimizations

- Support for parallel creation of standby databases: Through BUILD DATABASE [to standby (*)] [PARALLELISM integer] functionality, it enables multi-threaded concurrent creation of standby databases while optimizing LSC table slice file scanning and reading performance, significantly enhancing the speed of building distributed standby databases.

#### Distributed Maintenance Capabilities Enhancement

- New V$XFMR_STAT view shows all unfinished xfmr tasks information for columnar storage used to convert to stable data.
- New V$XFMR_HIS_STAT view shows all completed xfmr tasks information for converting to stable data, including resource usage like memory, quotas, input/output rates, execution time, etc., useful for analyzing both ongoing and completed historical xfmr tasks to see if behaviors meet expectations and if performance is affected.
- PQ_POOL_SIZE memory usage observability: PQ_POOL is primarily used for inter-thread data transfer in parallel environments, commonly used in distributed cross-node row-column execution and YAC global view query. This version elevates the PQ_POOL_SIZE parameter from a hidden parameter to a formal one for user configuration and enhances dynamic views with PQ_POOL-related metrics to boost usability and ease of diagnostic information retrieval.
- Timely reclamation and reuse of space in LSC tables: The LSC table space management is optimized to use reclaimable space first when requesting space, reducing expansion; when space is insufficient, background threads support forced reuse, ensuring successful operations; more proactive background space reclamation strategies increase execution efficiency.

#### New MySQL Data Types Supported

- BINARY data type: Used for storing binary strings, capable of storing any type of binary data, such as images, audio, video, files, preserving raw data accurately without character set conversion and encoding processing, avoiding issues related to character set transformations.
- FLOAT and DOUBLE data types: 4-byte single precision approximate numeric data with a maximum precision of 23 digits; 8-byte double precision approximate numeric data with a maximum precision of 53 digits.
- Variable-length character VARCHAR data type: Supports storing up to 65535 bytes, where the character count can be less than or equal to 65535, influenced by the character set.
- Unsigned data types, represented as positive numbers (the current version does not adapt arithmetic operations for FLOAT UNSIGNED, DOUBLE UNSIGNED, DECIMAL UNSIGNED).
  - TINYINT UNSIGNED: Used to store very small integers, occupying 1 byte, representing integers from 0 to 255.
  - SMALLINT UNSIGNED: Used to store small integers, occupying 2 bytes, representing integers from 0 to 65535.  
  - MEDIUMINT UNSIGNED: Used to store medium-sized integers, occupying 3 bytes, with a range from 0 to 16777215.  
  - INTEGER/INT UNSIGNED: Used to store integers, occupying 4 bytes, representing integers from 0 to 4294967295.  
  - BIGINT UNSIGNED: For storing larger integers, occupying 8 bytes, with a range from 0 to 18446744073709551615.  
  - DECIMAL UNSIGNED: For storing precise decimals, represented as DECIMAL[(M[,D])] [UNSIGNED], where M denotes total digits (precision) and D denotes digits beyond the decimal point (scale).  
  - FLOAT UNSIGNED: For storing floating point numbers, occupying 4 bytes, representing non-negative single-precision floating point numbers.  
  - DOUBLE UNSIGNED: For storing floating point numbers, occupying 8 bytes, representing non-negative double-precision floating point numbers.
- Time data types YEAR, DATE, and TIME: The YEAR type represents a 4-character year value. The DATE type represents values having a date part but no time part, retrieved and displayed in "YYYY-MM-DD" format, supporting a range from "1000-01-01" to "9999-12-31". The TIME type retrieves and displays the TIME value in 'hh:mm:ss' format (or 'hhh:mm:ss' for larger hour values), with a range from '-838:59:59' to '838:59:59'.

### Security Capabilities

- Supports table encryption capabilities: Through CREATE TABLE and the [table_encryption_clause](../../Development Guide/SQL Reference Manual/SQL Statements/CREATE TABLE.md#tableencryptionclause) syntax clause, encryption of specified tables is enabled, intercepting and encrypting data upon insertion or update, saved in an encrypted format, and decrypted automatically during retrieval. This encryption and decryption process is transparent to users.
- Supports [key management](../../Product Security/Encryption/Storage Encryption/Key Management): A new dual-level key management system allowing management of DEK and external wallet-managed MEK via internal mechanisms (system tables or data files). It enables on-demand generation of master keys and data encryption keys and assists in master key rolling, obsoleting old keys post-update, and securing otherwise non-recoverable keys.
- Supports tamper-proof capabilities: Through [HIST_CHECK](../../Development Guide/PL Reference Manual/Built-in Advanced PL Packages/HIST_CHECK) advanced package, it provides a set of built-in stored procedures/functions to enable/disable tampering functionality for specified tables and verify if any tampering has occurred.
- Supports configurable password strength: Prior to version 23.4, YashanDB's fixed password strength rules dictated a length of 8-64 characters and required the presence of numbers, uppercase letters, lowercase letters, and special characters. This version allows parameters to set password length controls, increasing flexibility in password management for different user security protocols.
- YashanDB supports auditing and recording user login/logout information via MySQL clients, bolstering audit information, making login/logout integral to diagnostic information, and enhancing security capabilities.

### Operations and Diagnostics

- Supports execution plan choice diagnostic functionality (event 10053): By supporting setting the 10053 event, such as '10053 TRACE NAME CONTEXT FOREVER, LEVEL 1', it records SQL generation execution plan processes, such as index selections, JOIN orders, operator choices, and similar information. It enables tracking internal events during SQL cost calculations for the optimizer to document how the CBO mode calculates SQL costs and generates respective execution plans. Detailed usage instructions can be found in [Tracing](../../Database Administration/Fault Diagnosis/Trace).
- Supports binding execution plans using SQL_ID: Through the addition of CREATE OUTLINE outline_name ON sql_id USING HINT hint syntax, allowing a specified SQL_ID to create an OUTLINE that fixes the SQL to a determined HINT guided execution plan while avoiding SQL alterations, enhancing flexibility.
- Performance reports snapshot storage optimization with top SQL setting: The addition of a modify_snapshot_settings function to dbms_awr allows the setting of the performance report's TOP SQL output line number through exec dbms_awr.modify_snapshot_settings(topnsql=>100), defaulting to 30, enabling more flexible displays of the performance report's TOP SQL data.
- Performance reports functionality storage optimization: Prior to version v23.4, performance reports data cleansing was performed through DELETE operations, which took considerable time with large data volumes. The current version enhances performance reports capabilities by transforming the corresponding system tables into partitioned tables, allowing historical data cleansing to occur via DROP partition operations, significantly increasing cleaning efficiency.
- V$SQL_BIND_CAPTURE view now records SQL binding variable information: Prior to version v23.4, YashanDB could not retrieve SQL binding variable records. This version introduces new fields in the V$SQL_BIND_CAPTURE view to record binding parameter values, facilitating SQL problem diagnostics.
- New V$TEMPSEG_USAGE view records the usage of temporary segments, which includes storage for intermediate results created by the database during sorting, hash joins, and index creation processes or during statistics operations. The storage also accommodates global temporary tables and private temporary tables, useful for performance monitoring and fault diagnosis.
- The SESSION view now displays client connection software version and protocol version: To enrich diagnostic information, the V$SESSION view adds multiple fields, such as CLIENT_PROTOCAL_VERSION, CLIENT_VERSION, CLIENT_DRIVER, MACHINE, and TERMINAL, providing more client information. During the login process, logs now support printing client software/protocol version information.
- V$SESSION now supports querying DDL statement text: New DTEXT fields in the V$SESSION view display the currently executing DDL statement text, truncating elements exceeding 200 bytes. When a session is not executing a DDL statement, this field appears as NULL.
- New DICT_COLUMNS, DICTIONARY, and DICT views: DICT serves as a synonym for DICTIONARY, which records information about system views and synonyms; DICT_COLUMNS records the column information of the DICTIONARY view. 
- DBA_TABLES adds INITIAL_EXTENT, NEXT_EXTENT, MIN_EXTENTS, and MAX_EXTENTS fields, indicating the size of the initial extent of the table, the size of the next allocated extent, measured in bytes, and measures minimum/maximum extent numbers in the segment; these fields are NULL for partitioned tables, useful for monitoring table storage space usage, predicting future growth trends, and identifying space resource planning scenarios.
- Supports ROLE_SYS_PRIVS and ROLE_TAB_PRIVS views: The new ROLE_SYS_PRIVS view displays the system privilege information granted to roles, while ROLE_TAB_PRIVS shows the object privilege information granted.
- Supports the DBA_EXTENTS view: The DBA_EXTENTS view helps observe the object information belonging to every extent, including the start position and size of the extent. Through this view, users can identify which objects' extents belong to data files' HWM for easier high water mark analysis and facilitate space reclaim adjustments to reduce bloating in tablespaces.
- Supports the DBA_TAB_HISTOGRAMS view for examining database table histogram information: New DBA_TAB_HISTOGRAMS view records histogram data generated during statistics collection for table columns, assisting the optimizer in estimating query result set sizes more accurately and generating more efficient execution plans.
- Installation now supports self-verifying installation package functionality.
  - While using OM to install and deploy databases, an algorithm checks to see if the installation package has been tampered with. If tampered, installation will forcibly terminate while further allowing *yasboot* to verify specific installation packages directly for evidence of tampering. Enhancing usability and security.
  - For scenarios with minimal resource requirements, YashanDB optimizes resource settings during DBMS_PARAM package recommendations, reducing default values and removing stress on performance/availability, enabling good performance even in lower memory configurations. This is supported by a new deployment method specifying memory size, optimizing database parameter configurations, enhancing ease of use.

### Drivers

#### JDBC

- Supports JDK 1.6/1.7 versions: Previous versions of the JDBC driver required JDK 1.8 and above; however, to accommodate more customer scenarios, YashanDB now supports JDK 1.6 and JDK 1.7 with the release of a new JDBC driver version.
- Supports dialect packages for GeoServer versions 2.23.3/2.25.5: To meet various scenario needs, YashanDB supports GeoServer versions 2.23.3/2.25.5 by providing gt-jdbc-yashandb-xxx dialect packages and the YashanDB JDBC driver, allowing users to configure YashanDB as the data source in GeoServer, facilitating vector data access and layer publishing operations.
- Supports standbyLoadBalance capability: The JDBC connection string can be configured with multiple IPs and the standby keyword for automatic identification of standby nodes and round-robin connections to the configured IP addresses while achieving load balancing effects.
- Adaptive DDL changes after PreparedStatement: Prior to version v23.4, obtaining a PreparedStatement would buffer it; altering the table structure while preparing, e.g., altering table to modify col from varchar2(30) to varchar2(32), would trigger a YAS-04007 Message: result set metadata changed exception. This version optimizes interaction between the driver and server, enabling JDBC to support successful executions of PreparedStatement statements even after metadata changes.
- JDBC supports the mapDataToTimestamp interface: A newly added mapDataToTimestamp interface allows conversion of data with an underlying date type obtained via getString to java.sql.Timestamp type, enhancing compatibility.

#### OCI

- Support for [LOB functions](../../Development Guide/C Language Family Drivers/OCI Driver/OCI Driver Interfaces/LOB Functions/00LOB Functions): LOB data type operations for storage and retrieval functionality are provided through the OCI driver via LOB functions.
- Support for [transaction functions](../../Development Guide/C Language Family Drivers/OCI Driver/OCI Driver Interfaces/Transaction Functions/00Transaction Functions): Transaction control setting and management functionalities via the OCI driver.
- Support for [numeric functions](../../Development Guide/C Language Family Drivers/OCI Driver/OCI Driver Interfaces/Numeric Functions/00Numeric Functions): This functionality handlesOCI NUMBER and various numeric type conversions via the OCI driver.
- Support for [string functions](../../Development Guide/C Language Family Drivers/OCI Driver/OCI Driver Interfaces/String Functions/00String Functions): Functions to handle strings and manage memory via the OCI driver.

#### ODBC

- Support for SQLExecDirectW function: It allows applications to directly submit SQL commands to the database (wide character version, with the W suffix denoting use of a wide-character Unicode version), achieving statement preparation and execution in one step, supporting SELECT, INSERT, UPDATE, etc.
- Support for SQLMoreResults function: Designed for handling multiple result sets, checking for additional result sets to process and moving to the next result set.
- Support for GUID data type: A globally unique identifier commonly used to identify objects in the database, typically represented as a string, e.g., {12345678-1234-1234-1234-1234567890AB}.
- Support for multiple calls to retrieve single-column data using SQLGetData interface: ODBC now supports multiple calls to SQLGetData for single-column data: through PHP pdo_odbc uses ODBC driver to retrieve data via SQLGetData in a loop fixed to 256 with support for retrieving single-column data exceeding 256. This version introduces this functionality to avoid memory overflow when processing large field data, enhancing performance and flexibility.
- SQLColAttributeW supports access to attributes SQL_DESC_BASE_TABLE_NAME and SQL_DESC_AUTO_UNIQUE_VALUE.
- SQLFetchScroll supports input parameter SQL_FETCH_FIRST.

#### Python

- Supports load balance: The Python driver supports load balance, auto-identifying the connection node with the fewest connections while connecting to standby nodes in high availability primary/standby and load balancing scenarios.
- Supports Django ORM framework: The Python driver also supports the Django ORM framework for version 3.2.25, facilitating developers in transitioning to YashanDB without extensive code modifications, enhancing code portability and development efficiency.

#### Other Driver Capabilities Enhancements

- Adapted to the Entity Framework 6 framework: The .NET ADO.NET driver now connects to YashanDB databases using the Entity Framework 6 framework's functionalities, effectively boosting development efficiency while enhancing maintainability.
- Supports Perl driver: The Perl language includes standard DBI modules for database communication, providing methods, variables, and constants for SQL querying, result processing, transaction management, and bringing advantages of efficient text processing and ease of learning and usage compared to other drivers.
- Supports .NET2.0 driver: New support for .NET2.0 driver realizes 32-bit application projects developed in VB.NET language, enriching the supported application scenarios.
- Support for GO driver and GORM framework: YashanDB supports the GO driver and adapts the GORM framework for developers to work with YashanDB databases using Go language while facilitating CRUD operations without needing to write complex SQL statements.
- C driver supports setting SQL execution timeout: By adding a statement handle attribute setting yacSetStmtAttr interface, the current stmt's SQL execution timeout can be set to effectively avoid connection failures or query timeouts caused by prolonged waiting.

### Tool Capabilities

- Yasboot supports primary/standby [rolling upgrade](../../Installation and Upgrade/Upgrade/Upgrade Procedure/Rolling Upgrade): Prior to version 23.4.1, only supported rolling upgrades from version 23.2.0.0 and newer versions with the same first three digits. This version broadens that support for rolling upgrades from version 23.4.0.0 and above to new versions with differing first three digits by first switching the standby database to a logical standby database, upgrading that, then switching primary/standby again to establish the original primary database as a physical standby, with an option to revert as necessary. The YashanDB management tool *yasboot* facilitates this one-click rolling upgrade operation, substantially reducing upgrade maintenance time while increasing usability.
- Yasboot supports rebuilding standby databases: In previous versions before 23.4, *yasboot* only enabled primary/standby deployments during initial setup but could not rebuild standby databases after failure. This version introduces new yasboot node build commands, enhancing ease of use to rebuild standby databases in a single step.
- Yasrman adds recovery commands specifying mapfile paths, enabling restoration of data files to designated positions as per path mapping information in those files, addressing scenarios with substantial discrepancies between target disk allocations and original backup environments, thus enhancing usability.
- Yasql supports @@ functionality and spool file names starting with numbers: The SPOOL command now supports naming output files with leading digits for saving outputs from *yasql* sessions, offering enriched use scenarios; prior to this version, using @ for calling operating system SQL files was enhanced to allow calling relative path scripts using @@ for nested scripts, simplifying multi-level script handling.
- Yasldr supports importing GIS data with multiple SRIDs: In versions prior to 23.4, *yasldr* could only use one specified SRID for importing GIS data in CSV format. The new version allows for differentiated SRID computation, enhancing the flexibility of GIS data imports.
