## Version Information

**Release Date**: July 7, 2026

**Version**: v23.5.4.100 AI Edition

## Version Positioning

YashanDB v23.5.4.100 is the AI first version released by YashanDB, with the goal of building an AI-Native database. Based on the original enterprise-level capabilities, this version addresses the paradigm shift in databases for the AI era, comprehensively upgrading around three major directions:

- Breaking through the structural defects of traditional "stitched" multi-model with a native multi-model unified architecture, allowing all data modalities to share a unified kernel, and providing unified storage and fusion query capabilities for multi-modal data for AI applications such as RAG, knowledge graphs, and intelligent search.

- Introducing kernel-level data sandbox technology to achieve "managing data like managing code," providing low-cost, parallelized data experimentation environments for AI agents, making "infinite attempts" by AI possible.

- Expanding model management and AI function ecosystem, enabling the database to evolve from a data storage engine to an AI inference foundation, supporting in-database AI inference such as Embedding vectorization, LLM generation, and Reranking, significantly simplifying the data pipeline for AI applications.

### Native Multi-Model

#### Vector Model

The data types are as follows:

| Data Type | Description |
|---|---|
| VECTOR(n) <br/> VECTOR(n, format) | Vector type, where format supports FLOAT32 (default) and FLOAT64, with maximum dimension 65535 |

HNSW Index: Significantly improves ANN retrieval efficiency through Hierarchical Navigable Small World (HNSW) indexing.

Vector conversion functions are as follows:

| Function | Description |
|---|---|
| TO_VECTOR(str) <br/> VECTOR(str) | Converts string to vector |
| FROM_VECTOR(v) <br/> VECTOR_SERIALIZE(v) | Converts vector to string or CLOB |
| VECTOR_DIMENSION_COUNT(v) <br/> VECTOR_DIMS(v) | Gets vector dimension |
| VECTOR_DIMENSION_FORMAT(v) | Gets vector storage type |

Distance metric functions are as follows:

| Function | Operator | Description |
|---|---|---|
| VECTOR_DISTANCE(v1, v2) | | General distance calculation function supporting multiple distance metrics |
| L2_DISTANCE(v1, v2) | <-> | Euclidean distance |
| COSINE_DISTANCE(v1, v2) | <=> | Cosine distance |
| INNER_PRODUCT(v1, v2) | Equals negative of <#> | Inner product |
| L2_SQUARED(v1, v2) | | Squared Euclidean distance |

Index example:

```sql

```

Approximate query example:


#### Graph Model

Based on the SQL 2023 SQL/PGQ standard, YashanDB constructs the graph model as a semantic abstraction layer over relational data, achieving "one storage, dual-mode queries":

- Zero-redundancy storage: The graph is not an independent engine; the physical data of nodes and edges is directly stored in ordinary SQL tables, where table columns are properties, with no data replication.

- Real-time consistency: INSERT/UPDATE/DELETE on underlying tables are immediately reflected in graph views. Graph and relational data are synchronized with zero delay, without ETL or materialization refresh.
- Intelligent query rewrite: Graph patterns are automatically converted to JOIN + recursive CTE, which can directly reuse existing indexes.
- High-performance execution: Based on foreign key elimination and batch parallel optimization technology, graph query performance is excellent.

Graph creation example:

```sql
-- Create property graph
CREATE PROPERTY GRAPH graph_name
VERTEX TABLES (
    table_name KEY (col1, col2) LABEL label_name PROPERTIES (col3, ...)
)
EDGE TABLES (
    edge_table KEY (edge_pk)
    SOURCE KEY (src_col1, src_col2) REFERENCES vertex_table(src_col1, src_col2)
    DESTINATION KEY (dst_col1, dst_col2) REFERENCES vertex_table(dst_col1, dst_col2)
    LABEL edge_label PROPERTIES (prop1, ...)
);
```

Graph query example:

```sql
-- Graph query (GRAPH_TABLE)
SELECT * FROM GRAPH_TABLE(graph_name
    MATCH (v is label_name)-[e is edge_label]->(f is node_label)
    COLUMNS(e.column_name)
);
```

#### Full-Text Model

YashanDB builds full-text search capability based on inverted indexes, providing native text search experience:

- Rich Boolean search: Supports AND/OR/NOT and combined expressions to flexibly express complex query intents.

- Intelligent tokenization: Chinese-English mixed tokenization, case-insensitive, configurable stop words. Built-in ambiguity resolution improves recall accuracy.
- Multi-type text support: Natively supports CHAR, VARCHAR, CLOB text column types, covering structured and unstructured text scenarios.
- LIKE zero-cost acceleration: LIKE expressions are automatically rewritten to full-text index scans when tokenization coverage is possible, with zero table returns and zero business SQL modifications, enabling application-transparent upgrades.

Full-text search functions are as follows:

| Function | Functionality |
|---|---|
| contains(column, 'expression') | Searches for keywords in the specified column |

Boolean search operators are as follows:

| Operator | Description |
|---|---|
| `&` (AND) | Logical AND, both terms must appear |
| `|` (OR) | Logical OR, either term can appear |
| `~` (NOT) | Logical NOT, exclude documents containing the term |
| `"phrase"` | Exact phrase matching |
| `=` | Equivalence matching |

Full-text index creation example:

```sql
CREATE SEARCH INDEX S_IDX ON table_name(content);
```

#### Document Model

YashanDB provides semi-structured document storage and query capabilities through JSON data types, flexibly handling business scenarios with changing schemas:

- Binary native storage: Stores in native binary rather than text, with pre-calculated offsets for high-frequency access paths. Queries can directly locate nested fields without fully parsing the document.

- Rich path functions: Provides path expressions conforming to SQL/JSON standards and functions such as JSON_EXISTS, JSON_VALUE, JSON_QUERY, JSON_TABLE, supporting extraction and filtering of nested fields.
- JSON function index acceleration: Creates B+ trees for JSON paths based on function indexes, converting nested field retrieval from full document scan to index positioning, significantly improving query performance.

Related interfaces are as follows:

| Function | Functionality |
|---|---|
| JSON(text) <br/> JSON_PARSE(text) | Parses text into JSON type |
| JSON_QUERY(json, '$.path' [RETURNING type] [PRETTY] [WITH | WITHOUT ARRAY WRAPPER]) | Retrieves JSON fragment by path |
| JSON_VALUE(json, '$.path' [RETURNING type]) | Extracts single scalar value by path |
| JSON_EXISTS(json, '$.path') | Determines if path exists |
| JSON_ARRAY_LENGTH(json) | Returns number of array elements |
| JSON_ARRAY_GET(json, index) | Gets array element by index |
| JSON_SERIALIZE(json [RETURNING type] [PRETTY]) | Serializes JSON to text |
| JSON_TABLE(json, '$.path' COLUMNS (...)) | Expands JSON to virtual relational table |
| JSON_EXTRACT(json_col, '$.path') | Matches multiple parts of path |

Index example:

```sql
-- JSON function index creation
CREATE INDEX idx ON table_name (
    JSON_VALUE(json_col, '$.field' RETURNING VARCHAR(100))
);
-- Index query
select * from table_name where JSON_VALUE(json_col, '$.field' RETURNING VARCHAR(100)) = 'china';
```

#### Unstructured File Management

YashanDB elevates files to "first-class citizens" on par with tables. Files are not external references to the database but native storage objects within the database:

- Hierarchical directory semantics: Preserves directory structure consistent with Linux file system. Files exist natively inside the database without requiring external object storage or file system mounting.
- Transaction consistency: CREATE/WRITE/REMOVE of files share the same ACID and MVCC mechanism as regular DML. They can be atomically committed or rolled back in the same transaction as business tables.
- Unified security and operations: File access is uniformly controlled by the database permission system. Operations are recorded in global audit logs; full/incremental backup and PITR simultaneously cover structured data and files without type differences.

DBMS_FS advanced package interfaces are as follows:

| Category | Interface | Functionality |
|---|---|---|
| Volume Management | CREATE_VOLUME(name, tablespace, bucket, size)<br/>DROP_VOLUME(name[, force])<br/>SET_VOLUME(name)<br/> GET_VOLUME(out name) | Create/delete/set/get storage volume |
| Directory Operations | MKDIR(path)<br/> RMDIR(path[, recursive])<br/>LISTDIR(path, out entries, out count) | Create/delete/list directories |
| File Operations | CREATE(path)<br/>WRITE(path, content) <br/>READ(path, offset, len, out buf, out len)<br/>REMOVE(path)<br/>EXIST(path, out flag)<br/>STAT(path, out filestat) | Write/read/delete/check existence/get metadata |

Storage volume example:

```sql
CREATE TABLESPACE ts_name DATABUCKET 'bucket_name' MAXSIZE 1G;
EXEC DBMS_FS.CREATE_VOLUME('vol_name', 'ts_name', 'bucket_name', 1073741824);
EXEC DBMS_FS.SET_VOLUME('vol_name');
```

#### Spatial Model

YashanDB's spatial model is a kernel-native GIS engine, deeply integrated from data types, spatial functions, spatial indexes to query optimizer.

- Type system: Supports Point, LINESTRING, POLYGON, MULTIPOINT, MULTILINESTRING, MULTIPOLYGON, GEOMETRY COLLECTION data types.

- R-Tree spatial index: Using Minimum Bounding Rectangle (MBR) approximation technology, queries first quickly eliminate non-intersecting MBRs through the hierarchical structure of the tree, performing precise geometric calculations only on a small number of candidate objects.

Spatial data types:

| Data Type | Description |
|---|---|
| GEOMETRY | Indicates that the column can be any subtype |
| GEOMETRY(subtype, srid) | Specifies subtype and coordinate system, where srid can be omitted and defaults to 0, for example `GEOMETRY(point, 4326)` |

Main spatial functions:

| Function | Description |
|---|---|
| ST_GeomFromText(wkt, srid) | Constructs Geometry object from input WKT format data |
| ST_AsText(geom, maxdecimaldigits) | Outputs Geometry object in WKT format |
| ST_Contains(geom1, geom2) | Determines if geom1 contains geom2 |
| ST_Collect(geomCol) | Aggregates geom data in geomCol into a single large geometric object |
| ST_MakeValid(geom) | Converts invalid geometry to valid geometry |
| ST_CollectionExtract(geom, t) | Extracts geometric objects of specified type |
| ST_Centroid(geom) | Calculates geometric centroid |
| ST_PointOnSurface(geom) | Returns any point inside the geometry |
| ST_Transform(geom, srid) | Coordinate system transformation |

Spatial index creation example:

#### Time-Series Model

Using YashanDB as a unified business entry, deeply integrating time-series components to achieve integrated installation and deployment of time-series data, cross-modal fusion analysis of relational data and time-series data, supporting industrial IoT system development and applications:

- Time-series-relational federation: TIME_SERIES_TABLE table function supports correlated queries between time-series data and relational data.

- Data model: Supports both hierarchical tree model and structured table model. Hierarchical tree model uses `root.company.factory.device.measurement point` style path naming, manages billion-level time series based on PBTree metadata, supports 5 categories 15 types of series-level permission controls. Structured table model supports standard SQL syntax, schema-less writes, unified management of static and dynamic data, four-dimensional fusion of time/tag/measurement/property.
- Time-series query capabilities: Provides downsampling (high-frequency data aggregated by period, e.g., average every 5 minutes), time-series segmentation (segment by change threshold/interruption interval, e.g., calculate device uptime), data filling/repair (valueFill for missing value filling, valueRepair for error value repair), UDF (UDSF/UDAF/UDTF), trend search, and other capabilities.

#### Multi-Modal Association Capability

YashanDB supports fusion queries of various modal data under unified SQL semantics. Multi-modal data can be jointly accessed, filtered, and calculated in a single statement. For example:

| Fusion Scenario | Technical Implementation | Business Value |
|---|---|---|
| Vector + Graph Joint Reasoning | Vector similarity filtering overlaid in graph traversal, reachable AND semantically similar | Enterprise risk control (fund chain association + industry semantics), intelligent recommendation (social relations + interest similarity) |
| Relational + Vector Deep Fusion | Optimizer coordinates B+ tree index and HNSW vector index, "filter first, then search" | Structured conditions compress vector retrieval range by two orders of magnitude, ensuring both precision and recall quality |
| Relational + Graph Deep JOIN | Graph nodes and relational tables are directly associated in unified storage engine, mixing graph paths and structured field conditions | One SQL completes graph traversal + correlated query + aggregate calculation without manual cross-database merging |
| Multi-Modal Joint Query | Cross-modal JOIN + full-modal index awareness + cross-modal predicate pushdown + unified snapshot isolation | One SQL completes relational table filtering + JSON extraction + vector sorting + graph association + aggregate calculation |

#### Multi-Modal Joint Query Example

```sql
drop table if exists tb_company;
create table tb_company(id int, name varchar(200), embedding vector(3));
CREATE VECTOR INDEX vidx1 ON tb_company (embedding) ORGANIZATION NEIGHBOR GRAPH DISTANCE COSINE;
create search index sidx2 on tb_company(name);
insert into tb_company values
    (1, 'oceanbase', '[1,0,0]'),
    (2, 'orcale database', '[1,0,3]'),
    (3, 'yashan database', '[1,0,2]'),
    (4, 'tidb', '[1,0,1]');
commit;

select id, name from tb_company where contains(name, 'database') > 0 ;
select id, name from tb_company order by cosine_distance(embedding, to_vector('[1, 1, 1]', 3)) FETCH APPROXIMATE FIRST 2 ROWS ONLY;
select id, name from tb_company where contains(name, 'database') > 0 union (select id, name from tb_company order by cosine_distance(embedding, to_vector('[1, 1, 1]', 3)) FETCH APPROXIMATE FIRST 2 ROWS ONLY);

create or replace view entity as select id, name from tb_company where contains(name, 'database') > 0 and id > 1 union (select id, name from tb_company order by cosine_distance(embedding, to_vector('[1, 1, 1]', 3)) FETCH APPROXIMATE FIRST 2 ROWS ONLY);

drop table if exists relation;
create table relation(r_id int, s_entity_id int, d_entity_id int, label varchar(20));
insert into relation values(1, 1, 2, 'label1');
insert into relation values(2, 1, 3, 'label2');
insert into relation values(3, 1, 4, 'label3');
insert into relation values(4, 3, 4, 'label4');
insert into relation values(5, 2, 3, 'label5');
insert into relation values(6, 3, 2, 'label6');
commit;

drop property graph if exists entity_graph;
create property graph entity_graph
VERTEX TABLES (
    entity key (id)
    LABEL entity_prop
    propertities (name)
)
EDGE TABLES (
    relation key (r_id)
    source key (s_entity_id) references entity(id)
    destination key (d_entity_id) references entity(id)
    LABEL relation_prop
    propertities (label)
);

SELECT aname, label_num, bname
FROM GRAPH_TABLE(entity_graph
    MATCH (a is entity_prop)-[r is relation_prop]->{1,2}(b is entity_prop)
    COLUMNS(a.name as aname, count(r.label) as label_num, b.name as bname)
);

SELECT aname, label, bname
FROM GRAPH_TABLE(entity_graph
    MATCH (a is entity_prop)-[r is relation_prop]->(b is entity_prop)
    COLUMNS(a.name as aname, r.label as label, b.name as bname)
);
```

### Data Branching

YashanDB extends a native data sandbox engine in the kernel. By introducing Branching technology, it provides users with a convenient, lightweight, and safe data environment management capability, enabling users to "manage data like managing code":

- Convenient: DBMS_BRANCH advanced package provides complete branch lifecycle management interfaces.

- Lightweight: Uses Copy-on-Write technology. When a new branch is created, it shares data blocks with the parent branch, and only truly copies modified data blocks when writing. Instant creation, shared storage, and cost does not grow linearly with the number of branches.
- Safe: Each branch has an independent data view. Transaction isolation, connection isolation, and permission isolation are naturally guaranteed. Misoperations can be rolled back through reset or restore functions.

Related interfaces are as follows:

| Interface | Functionality |
|---|---|
| CREATE(name, parent, checkout, default) | Creates branch (can specify parent branch, can switch immediately after creation) |
| CURRENT() | Gets current branch |
| CHECKOUT(name) | Switches branch |
| RENAME(old_name, new_name) | Renames branch |
| LIST() | Lists branches |
| RESET() | Resets current branch |
| RESTORE(timestamp_or_scn) | Restores branch to specified point in time |
| FREEZE(name) <br/> ACTIVATE(name) | Freezes/activates branch |
| SET_RESOURCE(name, util_limit, memory) | Sets branch resource limits (util_limit is concurrency, memory is memory limit) |
| SET_EXPIRATION(name, timestamp) | Sets branch expiration time |
| DELETE(name) | Deletes branch |
