General Description
----

The ALTER TABLESPACE statement is used to change the properties of an existing tablespace.

In ISC Distributed Cluster Deployment, when executing this statement, the system checks for any abnormal unrecovered DDL statements. If any exist, an error will be reported, and execution of this statement must wait until the corresponding DDL successfully recovers.

Statement Definition
----

**alter tablespace::=**

```ebnf
= ALTER TABLESPACE tablespace_name (datafile_clause|
databucket_clause|
shrink_clause|
offline_clause|
ONLINE|
rename_clause).
```

**[datafile\_clause](#datafiletempfileclauses)::=**

```ebnf
= ADD (DATAFILE|TEMPFILE) [file_specification {"," file_specification}]
| DROP (DATAFILE|TEMPFILE) file_name.
```

**[file\_specification](#filespecification)::=**

```ebnf
= "'file_name'" SIZE size_clause [AUTOEXTEND (OFF|(ON [NEXT size_clause] [MAXSIZE (UNLIMITED|size_clause)]))] [PARALLEL parallel].
```

**[databucket_clause](#databucketclause)::=**

```ebnf
= add_databucket_clause | alter_databucket_clause | drop_databucket_clause.
```

**[add_databucket_clause](#adddatabucketclause)::=**

```ebnf
= ADD DATABUCKET (bucket_clause {"," bucket_clause}).
```

**[bucket_clause](#bucketclause)::=**

```ebnf
= "'bucket_name'" [s3_bucket_clause] MAXSIZE size_clause.
```

**[s3_bucket_clause](#s3bucketclause)::=**

```ebnf
= S3 "(" URL "'url'" ["," REGION "'region'"] "," ACCESS KEY "'access_key'" "," SECRET KEY "'secret_key'" ")".
```

**[alter_databucket_clause](#alterdatabucketclause)::=**

```ebnf
= ALTER DATABUCKET "'bucket_name'" (READONLY | READWRITE).
```

**[drop_databucket_clause](#dropdatabucketclause)::=**

```ebnf
= DROP DATABUCKET "'bucket_name'".
```

**[shrink_clause](#shrinkclause)::=**

```ebnf
= SHRINK SPACE [KEEP size_clause].
```

**[offline\_clause](#offlineclause)::=**

```ebnf
= OFFLINE [NORMAL|TEMPORARY|IMMEDIATE].
```

**[rename\_clause](#renameclause)::=**

```ebnf
= RENAME TO space_name.
```

<span id="datafiletempfileclauses" name="datafiletempfileclauses"></span>

### datafile\_clause

This statement is used to modify the data files of a tablespace.

In ISC Distributed Cluster Deployment, adding/removing data files is only allowed for tablespaces created by the CREATE TABLESPACE statement. If a node failure occurs when modifying a data file of a tablespace, the recovery measures can be found in the [User Tablespace Management](../../../Database Administration/Storage Management/Logical Space Management/Tablespace Management/General Tablespace Management) chapter.

#### add (datafile|tempfile)

Add one or more data files to the tablespace (temporary files must use the TEMPFILE keyword).

In YAC/Distributed Cluster Deployment, when local temporary tablespaces or local SWAP tablespaces use local disk paths, adding one file equates to adding a group of files. The number of files in each group equals the number of cluster instances.

<span id="filespecification" name="filespecification"></span>

For the description of file_specification, please refer to [CREATE TABLESPACE](CREATE TABLESPACE).

When file_specification is not specified, the system automatically creates a data file according to the following rules:

- The file name is generated by combining the tablespace name and the sequence number of the data file in the tablespace, such as: tablespace_name1, tablespace_name2..., and is uniformly converted to uppercase.
- The default size of the file is 8192 BLOCKS, with the file path being the default data file path of the system.
- For non-MEMORY MAPPED tablespaces, the default file has automatic extension enabled, with next set to 8192 blocks and maxsize set to 64MB.
- If there is no explicit specification of extent allocation, the default allocation method for extents is automatic allocation by the system.

#### drop (datafile|tempfile)

Delete a data file from the tablespace (temporary files must use the TEMPFILE keyword).

In YAC/Distributed Cluster Deployment, when local temporary tablespaces or local SWAP tablespaces use local disk paths, deleting one file equates to deleting a group of files. The number of files in each group corresponds to the number of cluster instances.

The rules for deleting tablespace files are as follows:

- Deleting the first data file specified when creating the tablespace and non-ONLINE data files is not allowed.
- Deleting a data file from the UNDO tablespace is not allowed.
- Deleting a data file from the default SWAP tablespace is not allowed.
- To delete shadow files via DROP TEMPFILE, ensure that the database where the temporary file was created is the current primary database (if not, switch to the primary database first) and execute the DROP TEMPFILE statement on that primary database. Other standby databases will clean up the shadow records only after they receive the DROP TEMPFILE redo.

> **Note**: 
>
> After the data file of a MEMORY MAPPED tablespace is deleted, the internal ID and global ID of that file in the tablespace cannot be reused until the tablespace is deleted and the database is restarted.
>
> When adding a data file causes the internal ID of the file to reach the limit of the tablespace (63), deleting existing files will also not allow adding new data files to that tablespace.
>
> If a database outage occurs during the deletion of the data file, there may be residual files on the disk after restart, which need to be manually deleted.

***Example*** for Standalone/YAC/Distributed Cluster Deployment

```sql
ALTER TABLESPACE system ADD DATAFILE 'sys1' SIZE 4M AUTOEXTEND ON NEXT 4M MAXSIZE 1G;
 
ALTER TABLESPACE yashan ADD DATAFILE 'yashan_add1' SIZE 4M AUTOEXTEND ON NEXT 4M MAXSIZE 1G;

ALTER TABLESPACE yashan ADD DATAFILE 'yashan_add2' SIZE 4M AUTOEXTEND ON NEXT 4M MAXSIZE 1G PARALLEL 4;

ALTER TABLESPACE yashan ADD DATAFILE;
 
ALTER TABLESPACE system DROP DATAFILE 'sys1';
 
ALTER TABLESPACE yashan DROP DATAFILE 'yashan_add1';
```
<span id="databucketclause" name="databucketclause"></span>

### databucket_clause

This statement is used to modify the databucket (data bucket) information of the tablespace.

<span id="adddatabucketclause" name="adddatabucketclause"></span>

#### add_databucket_clause

Add databuckets to the tablespace, allowing multiple to be mounted at the same time, separated by commas. The description and constraints for newly created databuckets are the same as those in the [databucket_clause](CREATE TABLESPACE.md#databucketclause) of CREATE TABLESPACE.

<span id="bucketclause" name="bucketclause"></span>

##### bucket_clause

Described in the [databucket_clause](CREATE TABLESPACE.md#databucketclause) of CREATE TABLESPACE.

<span id="s3bucketclause" name="s3bucketclause"></span>

###### s3_bucket_clause

Described in the [s3_bucket_clause](CREATE TABLESPACE.md#s3bucketclause) of CREATE TABLESPACE.

***Example*** for Standalone Deployment and ISC Distributed Cluster Deployment

```sql
ALTER TABLESPACE lsc_tb ADD DATABUCKET '?/local_fs/lscfile_add3' MAXSIZE 1G;
```

<span id="alterdatabucketclause" name="alterdatabucketclause"></span>

#### alter_databucket_clause

This statement is used to modify the read/write properties of the databucket. The created databuckets are by default read/write.

##### bucket_name

Described as related to bucket_name in the [bucket_clause](CREATE TABLESPACE.md#bucketclause) of CREATE TABLESPACE.

##### readonly|readwrite

readonly indicates read-only, while readwrite indicates read/write.

Note that once the databucket is changed to read-only, it does not support any form of write operation, but DML statements executed by users (excluding Bulkload operations) are not affected. During a Bulkload operation, if there are no writable databuckets under the tablespace, an error will occur due to the need to generate SCOL data.

***Example*** for Standalone Deployment

```sql
ALTER TABLESPACE lsc_tb ALTER DATABUCKET '?/local_fs/lscfile_add3' READONLY;
```

<span id="dropdatabucketclause" name="dropdatabucketclause"></span>

#### drop_databucket_clause

Delete a particular databucket from the tablespace, only one databucket can be specified for deletion at a time.

##### bucket_name

Described in the [alter_databucket_clause](#alterdatabucketclause).

***Example*** for Standalone Deployment

```sql
ALTER TABLESPACE lsc_tb DROP DATABUCKET '?/local_fs/lscfile_add3';
```

<span id="shrinkclause" name="shrinkclause"></span>

### shrink_clause

This statement is used to reclaim free space based on the space utilization of each data file, shrinking the size of the tablespace.

In YAC/Distributed Cluster Deployment and Distributed In Memory Database, execution of shrink_clause is not allowed.

> **Note**: 
>
>- The UNDO tablespace cannot execute this statement.
>- Shrinking SWAP and TEMP tablespaces on the primary database will not synchronize to the standby database.

#### keep size_clause

Shrink the tablespace to a specified size. If the actual usage of the tablespace exceeds this size, the shrink operation will fail and return an error.

If KEEP is not specified, the system will maximize the tablespace shrink.

***Example*** for Standalone Deployment and ISC Distributed Cluster Deployment

```sql
ALTER TABLESPACE system SHRINK SPACE KEEP 100M;
 
ALTER TABLESPACE system SHRINK SPACE;
```

<span id="offlineclause" name="offlineclause"></span>

### offline_clause

Adjust the tablespace created by the user to an offline state. After the tablespace is offline, all data files under this tablespace will be unreadable and unwritable, and DDL operations cannot be performed on this tablespace, including operations such as adding or deleting data files.

The usage rules for the tablespace offline functionality are as follows:

- Operations on built-in tablespaces are not allowed, including SYSTEM, SYSAUX, UNDO, SWAP, TEMPORARY, etc.

- An offline tablespace and its data files remain part of the database. Therefore, it is not possible to create a tablespace or data file with the same name.

<span id="offline_option" name="offline_option"></span>

#### NORMAL|TEMPORARY|IMMEDIATE

The offline option can be omitted and defaults to NORMAL.

|Offline Options |NORMAL                                            |TEMPORARY                                      |IMMEDIATE                                      |
| ---------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| Prerequisite Constraints     | All data files of the target tablespace must be online; otherwise, an error will be reported. | None                                                         | The database must be in archive mode; otherwise, an error will be reported. |
| Objects of Operation         | Tablespace and all its non-shadow-state data files. <br />This type of operation always skips shadow files  (see the SHADOW field in the V$DATAFILE view). | The tablespace and all its online non-shadow-state data files. <br />This type of operation always skips shadow files. | Same as TEMPORARY                                            |
| Operation Mechanism          | Wait for data to be flushed to disk before going offline     | Same as NORMAL                                               | Go offline immediately.<br />**May lead to irrecoverable situations. Use with caution.** |
| Online Recovery              | No recovery operation is required, and it can be online directly. | Same as NORMAL                                               | Depends on the state of the data files in the target tablespace (see the STATUS field in the V$DATAFILE view):<br />- All in OFFLINE state: Same as NORMAL<br />- One or more in RECOVER state: See the introduction below. |

When executing OFFLINE IMMEDIATE, inconsistencies may occur because the archive or redo logs have not been fully applied to the target data file (the target data file will be placed in the RECOVER state). Data files in this state cannot be directly brought online again. **Exercise caution when operating**.

For tablespaces with data files in the RECOVER state, the subsequent handling solutions and **precautions** are as follows:

- Data files in the RECOVER state within non-temporary tablespaces in Standalone Deployment: An attempt can be made to restore the tablespace through the [RECOVER command](../../../Tools Guide/yasrman/User Guide for yasrman/RECOVER) of yasrman. Only after a successful recovery can these data files be brought online again. Both the RECOVER command and the subsequent online operation must be executed on the same node where the offline operation was originally performed. Recovery across nodes is not possible.

- In other scenarios: Such files cannot be directly recovered. If there is an available backup set prior to the tablespace going offline, an attempt can be made to restore the tablespace, that is, the data files to a normal state by restoring the database.
  
- In primary-standby HA deployment, if a primary-standby switch occurs when there are data files in the RECOVER state, performing the online operation of the target tablespace on the new primary database will cause an anomaly in the standby database where the data file in the RECOVER state is located. It is necessary to build the standby database for repair.

> **Warn**:
> 
> The tablespaces in the following scenarios do not support the [tablespace recovery function](../../../Tools Guide/yasrman/User Guide for yasrman/RECOVER). Exercise caution when performing the offline operation. After recovery, the data file and its corresponding tablespace can only be dropped and cannot be restored to the online state:
> 
> - All tablespaces in YAC/Distributed Cluster Deployment
> 
> - Temporary tablespaces in other deployment forms

***Example***

```sql
ALTER TABLESPACE yashan OFFLINE;
 
ALTER TABLESPACE yashan1 OFFLINE NORMAL;

ALTER TABLESPACE yashan2 OFFLINE TEMPORARY;

ALTER TABLESPACE yashan3 OFFLINE IMMEDIATE;
```

### online

Adjust the offline tablespace to an online state to make it normally available.

The usage rules for the tablespace online functionality are as follows:

- The objects of this operation are the target tablespace and all its data files (shadow files are excluded, as this operation always skips them). If there are data files that cannot be brought online, the entire operation will fail and return an error.

- In primary-standby HA deployment, if a tablespace on the standby database has data files in the RECOVER state, performing the online operation of this tablespace on the primary database will cause an anomaly in the standby database, and it will be necessary to build the standby database for repair.

***Example***

```sql
ALTER TABLESPACE yashan ONLINE;
```

<span id="renameclause" name="renameclause"></span>

### rename_clause

This statement is used to rename a tablespace or a data file, with the following restrictions:

- It is not allowed to rename a tablespace to an existing tablespace name.
- It is not allowed to use this statement to rename built-in tablespaces.
- It is not allowed to rename an OFFLINE tablespace using this statement.
- It is not allowed to rename a SWAP tablespace that is currently in use; to rename it, first modify the DEFAULT_SWAP_TABLESPACE configuration parameter, and then perform the rename operation.
- In ISC Distributed Cluster Deployment, renaming of tablespaces or data files is not allowed.

***Example*** for Standalone/YAC/Distributed Cluster Deployment

```sql
ALTER TABLESPACE yashan1 RENAME TO yashanDb;
```
