The constraint is used to define rules for the data in the table. Only data that meets the constraint definition can be generated; otherwise, the system will prompt a constraint violation error.

Constraints are defined based on column properties and are applied in syntax related to CREATE TABLE, ALTER TABLE, and other column property definitions.

YashanDB provides two methods for defining constraints: inline (inline_constraint) and out-of-line (out_of_line_constraint), depending on their position in the statement. However, the NOT NULL constraint can only be defined as an inline constraint.

<span id="inlineconstraint" name="inlineconstraint" class="yaslink"></span>

## inline\_constraint

Inline constraints are defined alongside the column property definitions.

The constraint_name can be specified using CONSTRAINT constraint_name, and if omitted, a default name will be generated by the system.

The constraints that can be defined inline include:

* [UNIQUE](#UNIQUE): applicable to all tables.
* [PRIMARY KEY](#PRIMARYKEY): applicable to all tables.
* [FOREIGN KEY](#REFERENCES): applicable to HEAP tables.
* [CHECK](#CHECK): applicable to HEAP and TAC tables.
* [NOT NULL](#NOTNULL): applicable to all tables.

***Example*** for Heap tables

```sql
-- Create parent table area_parent
CREATE TABLE area_parent
(area_no CHAR(2) NOT NULL PRIMARY KEY,
area_name VARCHAR2(60) CHECK (area_name IS NOT NULL),
DHQ VARCHAR2(20) DEFAULT 'ShenZhen' NOT NULL);
  
-- Create child table branches_child with foreign key constraint on area_no referencing area_parent's area_no
CREATE TABLE branches_child
(branch_no CHAR(4) PRIMARY KEY,
branch_name VARCHAR2(200) NOT NULL,
area_no CHAR(2) CONSTRAINT c_branches_child1 REFERENCES area_parent(area_no) ON DELETE SET NULL,
address VARCHAR2(200));
```

***Example*** for TAC tables

```sql
DROP TABLE IF EXISTS area_tac;
CREATE TABLE area_tac
(area_no CHAR(2) NOT NULL PRIMARY KEY,
 area_name VARCHAR2(60) CHECK (area_name IS NOT NULL),
 DHQ VARCHAR2(20) DEFAULT 'ShenZhen' NOT NULL);
```

***Example*** for LSC tables

```sql
CREATE TABLE area_lsc
(area_no CHAR(2) NOT NULL,
 area_name VARCHAR2(60),
 DHQ VARCHAR2(20) DEFAULT 'ShenZhen' NOT NULL);
```

<span id="outlineconstraint" name="outlineconstraint" class="yaslink"></span>

## out\_of\_line\_constraint

Out-of-line constraints are defined separately from the column property definitions.

The constraint_name can be assigned using CONSTRAINT constraint_name, and if omitted, a default name will be generated by the system.

The constraints that can be defined out-of-line include:

* [UNIQUE](#UNIQUE): applicable to all tables.
* [PRIMARY KEY](#PRIMARYKEY): applicable to all tables.
* [FOREIGN KEY](#REFERENCES): applicable to HEAP tables.
* [CHECK](#CHECK): applicable to HEAP and TAC tables.

***Example*** for Heap tables

```sql
-- Create child table branches_child1 with a foreign key constraint equivalent to that defined inline
CREATE TABLE branches_child1
(branch_no CHAR(4) PRIMARY KEY,
branch_name VARCHAR2(200) NOT NULL,
area_no CHAR(2),
address VARCHAR2(200),
CONSTRAINT c_branches_child2 FOREIGN KEY (area_no) REFERENCES area_parent(area_no) ON DELETE SET NULL);
```

***Example*** for TAC tables

```sql
CREATE TABLE area_tac1
(area_no CHAR(2) NOT NULL,
 area_name VARCHAR2(60),
 DHQ VARCHAR2(20) DEFAULT 'ShenZhen' NOT NULL,
 CONSTRAINT c_area_tac1 PRIMARY KEY(area_no),
 CONSTRAINT c_area_tac2 CHECK (area_name IS NOT NULL));
```

## Constraint Types

<span id="NOTNULL" name="NOTNULL" class="yaslink"></span>

### NOT NULL

Defines a non-null constraint for a specific column, indicating that the value of the column cannot be null.

NULL or NOT NULL is only supported for inline constraints.

For HEAP tables, new columns with the NOT NULL constraint cannot be created if they are not null.

NULL does not define a constraint; it merely explicitly allows the column to contain null. 

If neither NOT NULL nor NULL is specified, the default value is NULL.

<span id="UNIQUE" name="UNIQUE" class="yaslink"></span>

### UNIQUE

Defines a unique constraint for a specific column or a combination of columns, indicating that the values in that column or combination must be unique in the current table.

The following restrictions apply when adding a unique constraint:

- If there is already duplicate data in the column or combination of columns, the constraint cannot be added successfully.
- If the unique constraint is added successfully, the system will automatically create a unique index based on the unique column. If an index (including unique and non-unique) already exists on the column or combination, no new index will be created.
- In ISC Distributed Cluster Deployment when creating Sharded tables, if there are multiple unique constraint keys, such as primary or unique keys, all unique constraint keys must have at least one common field (the default partition key takes the first suitable data type field from the common subset of unique constraint keys); failure to comply will return an error.
- In ISC Distributed Cluster Deployment when adding unique constraints (including primary and unique constraints) in Sharded tables, the partition key must also be included.

<span id="PRIMARYKEY" name="PRIMARYKEY" class="yaslink"></span>

### PRIMARY KEY

Defines a primary key constraint for a specific column or a combination of columns, indicating that the column or combination will serve as the table's primary key.

Since inline constraints are defined for a single column, a single-column primary key can only be defined inline, while a multi-column composite primary key must be defined out-of-line.

The following restrictions apply when adding a primary key constraint:

- A primary key has a non-null characteristic; thus, it cannot be added successfully if any column in the column combination contains null data.
- A primary key has a uniqueness feature; thus, it cannot be added successfully if duplicate data exists in the column or combination.
- A table can have only one primary key; therefore, if a primary key already exists on the table containing the column or combination, it cannot be added successfully.
- If the primary key is added successfully, the system will automatically create a unique index based on the primary key column; if an index (including unique and non-unique) already exists on the column or combination, no new index will be created.

<span id="CHECK" name="CHECK" class="yaslink"></span>

### CHECK

The CHECK constraint is used to validate the conditions of the data being inserted into the table; only data that returns true for the condition can be successfully inserted into the table.

When a new CHECK constraint is added to an existing data table, the system will also perform a check on the current data (unless NOVALIDATE is specified); if any existing data fails the check, the constraint cannot be successfully added.

In inline constraints, the CHECK condition can only specify the current column, while conditions involving multiple columns can only be defined in out-of-line constraints.

Please refer to SQL general syntax [condition](condition) for the content description that CHECK conditions can include.

<span id="REFERENCES" name="REFERENCES" class="yaslink"></span>

### FOREIGN KEY

Establishes a foreign key constraint for a column or combination of columns in one table (the child table) to another table (the parent table), indicating that the values in the child table's column or combination must exist in the corresponding column of the parent table. If the value in the child table is NULL, it is considered to exist within the parent table.

Since the inline constraint is defined for a single column, a single-column foreign key can only be defined inline, while a composite foreign key must be defined out-of-line.

The following are the restrictions on using foreign keys:

- FOREIGN KEY cannot be established for temporary tables, nor can a foreign key to other tables referencing a temporary table.
- Encrypted columns cannot have FOREIGN KEY created.

<span id="referencesclause" name="referencesclause" class="yaslink"></span>

#### references\_clause

When defining a foreign key constraint, REFERENCED specifies the parent table to which the foreign key points, as well as the corresponding columns in the parent table that are aligned with the child table's foreign key columns. If only the parent table name is indicated while the column name is omitted, the foreign key will automatically reference the primary key of the parent table, and the foreign key column must align with the primary key column.

The following restrictions apply when adding foreign key constraints:

- The foreign key constraint requires that the data in the foreign key column of the child table must exist in the corresponding column of the parent table. When adding a new foreign key constraint to an existing data child table, the system will perform this check on the existing data in the child table (unless NOVALIDATE is specified); if any data fails this check, the constraint cannot be successfully added.
- The foreign key constraint requires that the corresponding column in the parent table must meet the uniqueness constraint (PRIMARY KEY or UNIQUE must be defined on the corresponding column), otherwise it cannot be successfully added.
- If a foreign key constraint already exists on the foreign key column of the child table pointing to the corresponding column in the parent table, the constraint cannot be added successfully.
- For partitioned tables, it is not allowed to add foreign key cascade constraints on update cascade/on update set null.

##### ON DELETE 

After establishing a foreign key constraint, when a value in the corresponding column of the parent table is deleted, the system will check whether that value exists in the foreign key column of the child table. If it does, data in the parent table cannot be deleted. If ON DELETE is specified in the constraint definition, the system will allow the aforementioned operation on the parent table while performing the following actions based on different options:

- Specifying ON DELETE RESTRICT (which is the default behavior) will report an error when trying to delete parent data that exists in the child table.
- Specifying ON DELETE CASCADE will allow the deletion of parent data that exists in the child table, and also delete corresponding data in the child table.
- Specifying ON DELETE SET NULL will allow the deletion of parent data that exists in the child table, and set corresponding data in the child table to NULL.

>  **Note**: 
>
> If the column on which the foreign key must be established in the child table has a NOT NULL constraint, the ON DELETE SET NULL option cannot be specified.

Moreover, the following options are available solely for syntax compatibility:

- ON DELETE NO ACTION (behavior consistent with RESTRICT)

##### ON UPDATE

After establishing a foreign key constraint, when a value in the corresponding column of the parent table is updated, the system will check whether that value exists in the foreign key column of the child table. If it does, data in the parent table cannot be updated. If ON UPDATE is specified in the constraint definition, the system will allow the aforementioned operation on the parent table while performing the following actions based on different options:

- Specifying ON UPDATE RESTRICT (which is the default behavior) will report an error when trying to update parent data that exists in the child table.
- Specifying ON UPDATE CASCADE will allow the update of parent data that exists in the child table and update corresponding data in the child table.
- Specifying ON UPDATE SET NULL will allow the update of parent data that exists in the child table and set corresponding data in the child table to NULL.

> **Note**: 
>
> If the column on which the foreign key must be established in the child table has a NOT NULL constraint, the ON UPDATE SET NULL option cannot be specified.

<span id="constraintstate" name="constraintstate" class="yaslink"></span>

## Constraint Attributes

YashanDB provides a series of options to define the properties of a constraint, among which the following options are used for syntax compatibility but have no actual meaning:

- NOT DEFERRABLE
- INITIALLY IMMEDIATE
- RELY|NORELY

<span id="usingindexclause" name="usingindexclause" class="yaslink"></span>

### using\_index\_clause

This statement is used solely as a property option for PRIMARY KEY or UNIQUE constraints to specify the index or index attributes corresponding to the constraint. Using this statement with other constraints will result in an error.

In YashanDB, when creating PRIMARY KEY or UNIQUE constraints, the system will automatically create a corresponding unique index (if that unique index already exists, it will not create it). Using this statement will modify the system's automatic operation to a user-specified one, and the effects are slightly different, described in more detail below.

#### USING INDEX

This statement is only used when the existing constraint is disabled, it enables the constraint and automatically creates an index with the same name as the constraint.

#### USING INDEX [schema.]index\_name

Assigns an existing index to the constraint; this index must satisfy the following conditions:

-  The table and columns on which the index is based must be the same as those of the constraint.
- It cannot be a descending index.

If the specified index is not a unique index, it will be rebuilt as a unique index when the constraint is created.

Using this method to specify the index differs from the automatically created index in that if subsequent delete operations are performed on the constraint, the automatically created index will be deleted, while the user-specified index will not be deleted.

***Example*** for Heap tables

```sql
-- Create table area_using_index
CREATE TABLE area_using_index
(area_no CHAR(2) NOT NULL,
 area_name VARCHAR2(60),
 DHQ VARCHAR2(20) DEFAULT 'ShenZhen' NOT NULL);

-- Create unique index idx_area_using_index_1
CREATE UNIQUE INDEX idx_area_using_index_1 ON area_using_index(area_no);

-- Create a primary key for table area_using_index and specify the index
ALTER TABLE area_using_index ADD PRIMARY KEY(area_no) USING INDEX idx_area_using_index_1;
```

#### USING INDEX index\_attr\_clause

Using this statement indicates that a unique index will still be automatically created by the system when creating the constraint, but the relevant properties of that index will be specified.

When not using using_index_clause and there is no existing unique index, the system will automatically create a unique index with default properties, such as using the same tablespace as the table. This statement avoids the hassle of separately building the index while also accommodating practical needs for physical isolation between the index and the table.

It should be noted that the premise for using this statement is that there cannot be an existing unique index on the constraint column; otherwise, the system will not use that index directly and will return an error.

**index_attr_clause**

Indicates the syntax for specifying index attributes, which is consistent with the syntax in [CREATE INDEX](../SQL Statements (yashan Mode)/CREATE INDEX).

***Example*** for Heap tables, Standalone Deployment TAC tables

```sql
-- Create table area_index_attr while specifying the index tablespace
CREATE TABLE area_index_attr
(area_no CHAR(2) PRIMARY KEY USING INDEX TABLESPACE yashan,
 area_name VARCHAR2(60),
 DHQ VARCHAR2(20) DEFAULT 'ShenZhen' NOT NULL);
```

#### USING INDEX create\_index\_clause

Using this statement is equivalent to allowing the system to automatically create a unique index. However, unlike the system's automatic creation with default values, this statement can specify the index's name, properties, and other details.

**create_index_clause**

The syntax for creating an index, except for descending indexes, is consistent with [CREATE INDEX](../SQL Statements (yashan Mode)/CREATE INDEX).

It should be noted that when a unique index already exists on the constraint column, the index_name in create_index_clause must match the name of the existing index, and the index_attr_clause specified properties must be the same as those of the existing index; otherwise, it will return an error.

***Example*** for Heap tables and Standalone Deployment TAC tables

```sql
-- Create table area_create_index
CREATE TABLE area_create_index
(area_no CHAR(2) NOT NULL,
 area_name VARCHAR2(60),
 DHQ VARCHAR2(20) DEFAULT 'ShenZhen' NOT NULL);

-- Create a primary key for table area_create_index and create an index
ALTER TABLE area_create_index 
ADD PRIMARY KEY(area_no) 
USING INDEX (CREATE INDEX idx_area_create_index_1 ON area_create_index(area_no) TABLESPACE yashan);

-- Creating a descending index will return an error
ALTER TABLE area_create_index DROP PRIMARY KEY;
ALTER TABLE area_create_index 
ADD PRIMARY KEY(area_no) 
USING INDEX (CREATE INDEX idx_area_create_index_2 ON area_create_index(area_no DESC) TABLESPACE yashan);

YAS-02210 specified index cannot be used to enforce the constraint
```

###  VALIDATE|NOVALIDATE

Specifies whether to check existing data in the table for the constraint when defining a constraint. VALIDATE indicates a check is conducted; NOVALIDATE indicates no check is conducted. This can be omitted, with the default being VALIDATE.

For UNIQUE/PRIMARY KEY/NOT NULL constraints, the system will always assume VALIDATE, performing constraint checks even if NOVALIDATE is specified.

***Example*** for Heap tables and TAC tables

```sql
-- Current data in area
SELECT area_no,area_name,DHQ FROM area;
AREA_NO AREA_NAME                         DHQ         
------- --------------------------------- ------------
01      EastChina                            Shanghai      
02      WestChina                            Chengdu       
03      SouthChina                            Guangzhou     
04      NorthChina                            Beijing       
05      CentralChina                            Wuhan  

-- Adding CHECK constraint to the table
ALTER TABLE area ADD CHECK (LENGTH(area_name)>10);
YAS-02255 cannot validate constraint - check constraint violated

-- Adding CHECK constraint with NOVALIDATE
ALTER TABLE area ADD CHECK (LENGTH(area_name)>10) NOVALIDATE;
```

### ENABLE|DISABLE

Specifies whether to enable the constraint when defining it; ENABLE indicates the constraint is enabled, while DISABLE indicates it is disabled. This can be omitted, with the default being ENABLE.

When defining UNIQUE/PRIMARY KEY constraints and specifying DISABLE, the system will not create the corresponding index.

***Example*** for Heap tables and TAC tables

```sql
-- Current data in area
SELECT area_no,area_name,DHQ FROM area;
AREA_NO AREA_NAME                         DHQ         
------- --------------------------------- ------------
01      EastChina                            Shanghai      
02      WestChina                            Chengdu       
03      SouthChina                            Guangzhou     
04      NorthChina                            Beijing       
05      CentralChina                            Wuhan  

-- Adding CHECK constraint in a disabled state
ALTER TABLE area ADD CONSTRAINT ck CHECK (LENGTH(DHQ)>10) DISABLE;

-- Inserting a value that violates the constraint, but must follow the CHECK constraint outlined above
INSERT INTO area VALUES ('06','NorthChinaNorthChinaNorthChinaNorthChinaNorthChina1','tianjing');

-- Enabling CHECK constraint
ALTER TABLE area MODIFY CONSTRAINT ck ENABLE;
YAS-02255 cannot validate constraint - check constraint violated
```
