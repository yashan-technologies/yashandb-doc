Database runtime log is controlled by the log level for recording switches and strategies. When the level is set to OFF, no runtime logs are recorded.

## Set storage path for runtime logs

You can modify the storage path of runtime logs by setting the RUN_LOG_FILE_PATH parameter.

SQL statement to modify the storage path of runtime logs:

```sql
SHOW PARAMETER RUN_LOG_FILE_PATH;

NAME                                  VALUE             
------------------------------------- ------------------------------------------
RUN_LOG_FILE_PATH                     /data/yashan/yasdb_home/log/db-1-1/run 

ALTER SYSTEM SET RUN_LOG_FILE_PATH='<path>' SCOPE=SPFILE;
```

This parameter requires a database restart to take effect.

> **Warn**:
>
> The new path set for the runtime logs must already exist and have write privilege; otherwise, the database will fail to start.

## Set log file retention count

You can modify the retention count of runtime logs by setting the RUN_LOG_FILE_COUNT parameter. When the number of logs reaches the value set by this parameter (default 10), the system will automatically delete the oldest logs.

Command to modify the log file retention count:

```sql
ALTER SYSTEM SET RUN_LOG_FILE_COUNT=<retention count> SCOPE=SPFILE;
```

This parameter requires a database restart to take effect.

You can enter the log file storage location to observe the number of retained files:

```shell
$ ls -l /data/yashan/yasdb_home/log/db-1-1/run
```

## Set maximum log file size

You can modify the maximum size of runtime logs by setting the RUN_LOG_FILE_SIZE parameter. When the size reaches the value set by this parameter (default 20M), the log file will be automatically archived.

Command to modify the maximum log file size:

```sql
ALTER SYSTEM SET RUN_LOG_FILE_SIZE=<log file size> SCOPE=SPFILE;
```

This parameter requires a database restart to take effect.

## Runtime log level management 

The order of the runtime log levels is as follows:

ERROR < WARN < INFO < DEBUG < TRACE < ALL

From left to right, the log levels increase sequentially, with higher log levels including lower ones.

The command to view the current log level is:

```sql
show parameter RUN_LOG_LEVEL;
```

### ERROR level

When the database generates a critical error that can be handled, it will output ERROR logs. These errors generally cannot be returned to the client, such as errors generated by background threads.

The command to set the log level to ERROR is:

```sql
ALTER SYSTEM SET RUN_LOG_LEVEL=ERROR;
```

When YashanDB loses a tablespace data file, the log in run.log appears as follows: (This article takes Standalone Deployment as an example; specific logs are subject to actual circumstances)

```verilog
2022-06-17 19:20:56.981 20098 [ERROR] [MONITOR]
/data/yashan/yasdb_data/db-1-1/dbfiles/temp metadata changed, for example, permissions, timestamps, extended attributes, 
and user/group ID, etc
2022-06-17 19:21:55.839 20308 [ERROR][errno=00313]: open file /data/yashan/yasdb_data/db-1-1/dbfiles/temp failed, errno 2, 
error message "No such file or directory"
```

### WARN level

WARN level records warning information during database operation, indicating potential issues that do not affect normal database operation.

The command to set the log level to WARN is:

```sql
ALTER SYSTEM SET RUN_LOG_LEVEL=WARN;
```

***Example***

```verilog
// If the corresponding dirty pages have not been flushed to disk by Checkpoint before the redo is reused:
2026-04-02 03:54:10 - 2026-04-02 03:54:10.833 23186 [WARN] [CKPT] checkpoint not complete
```

### INFO level

The default log level used by YashanDB is INFO.

INFO level records critical events occurring during the normal operation of the database, primarily including:

- Database state changes: for example, start, shutdown, upgrade, demotion.
- Changes to critical database resources: for example, adding or deleting tablespaces and users.
- Changes in database resources: for example, starting and stopping threads.
- Critical database activities: for example, restart recovery, residual transactions.
- Changes in database parameters: modifying system configurations.

The command to set the log level to INFO is:

```sql
ALTER SYSTEM SET RUN_LOG_LEVEL=INFO;
```

### DEBUG level

### TRACE level

TRACE level records detailed tracing information during database operation for in-depth problem analysis. This level outputs very detailed logs, including function call chains, performance data, etc.

The command to set the log level to TRACE is:

```sql
ALTER SYSTEM SET RUN_LOG_LEVEL=TRACE;
```

***Example***

```verilog
// When executing SQL statements, the log in run.log appears as follows:
2026-04-02 13:40:23.365 21566 [TRACE] [DSTB DDL] ddl status: 0 clean
```

### ALL level

ALL level records all log information and is the highest level of log level mode.

The command to set the log level to ALL is:

```sql
ALTER SYSTEM SET RUN_LOG_LEVEL=ALL;
```
