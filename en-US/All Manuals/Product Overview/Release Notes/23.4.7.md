## Version Positioning

YashanDB v23.4.7 enriches the new features and continues to optimize performance based on v23.4.6, serving as a version available for long-term service support.

## Version Information

**Version Number**: v23.4.7.100

**Release Date**: February 26, 2026

## New Functionality

YashanDB v23.4.7 inherits all functionalities released in YashanDB v23.4.6 and adds the following key features:

### SQL Engine Enhancements

- SQL and PL Capability Enhancements

    - Added ROWID range query support: Prior to v23.4.7, in scenarios such as migration and pagination display for large tables without a primary key, users typically used ROWID as a condition to achieve sharding. However, YashanDB could only perform a full table scan, resulting in low processing efficiency for large tables. In this release, the capability of sequential ROWID range scan is added. It can read data that is physically adjacent in batches, effectively reducing I/O overhead and significantly improving query performance in such scenarios.

    - The DBMS_SESSION package adds the RESET_PACKAGE function: The DBMS_SESSION package now supports the RESET_PACKAGE function, which can reset all loaded PL packages in the current session, release the state of package-level variables, and restore the packages to their initial loaded state. This feature effectively releases related resources, resolves package state residue issues in specific scenarios, and further improves compatibility with Oracle.

    - New DBMS_XMLGEN package and accompanying functions: v23.4.7 introduces the DBMS_XMLGEN package, along with supporting functions including NEWCONTEXT, GETXMLTYPE, GETXML, CONVERT, CLOSECONTEXT, SETSKIPROWS, SETNULLHANDLING, SETMAXROWS, and GETNUMROWSPROCESSED. It supports direct conversion (generation) of SQL query result sets into XML-formatted data, providing a concise and efficient API. This enables quick conversion of relational data to XML data without manual XML tag concatenation, improving development efficiency, reducing maintenance costs, and enhancing compatibility with Oracle.

    - The DBMS_LOB package adds CONVERTTOBLOB and CONVERTTOCLOB functions: The DBMS_LOB package now includes CONVERTTOBLOB and CONVERTTOCLOB functions for mutual conversion between Character Large Objects (CLOB/NCLOB) and Binary Large Objects (BLOB). The conversion process automatically handles character set encoding conversion and data format adaptation, resolving the pain point of inability to directly assign values between the two large object types, ensuring encoding consistency, simplifying development processes, and improving compatibility with Oracle.

    - Optimization of the NOCOPY parameter function for procedure bodies: Prior to v23.4.7, YashanDB already achieved syntax compatibility for the NOCOPY parameter of procedure bodies. This version further optimizes the parameter attribute capability by implementing logic that avoids deep copying for IN-direction parameters when pushing to the function stack frame, and performs deep copying for IN OUT-direction parameters only when popping from the function stack frame, effectively improving system performance in specific scenarios.

- GIS Capability Enhancement

    The pgRouting plugin is newly added in v23.4.7, providing a series of dedicated functions to efficiently meet core scenario requirements such as geographic network routing calculation and path analysis. It improves GIS geospatial analysis capabilities and adapts to business scenarios like road networks and geographic navigation.

    - New PGR_CREATETOPOLOGY function added: It is used to create a topological structure for road network data stored in the database, laying the foundation for subsequent routing analysis.

    - New PGR_DIJKSTRA function added: It calculates the shortest path from a single source node to one or more target nodes in a graph, supports handling undirected and directed graphs, and allows users to customize edge weights.

    - New PGR_DIJKSTRACOST function added: It focuses on returning the total cost of the shortest path without returning specific path information, effectively reducing unnecessary data transmission and improving analysis efficiency.

    - New PGR_DRIVINGDISTANCE function added: It calculates all nodes or areas reachable from one or more starting points within a given cost limit.

- Optimizer Enhancement
  
    - Optimization of batch execution framework: This version enhances the accuracy of cost calculation for operator batch execution and optimizes the Cost model. Combined with the built-in parameter _BATCH_MODE=1, the optimizer's adaptive capability can be enabled. When generating execution plans, the optimizer can independently determine and select either row-by-row or batch execution architecture. This not only ensures the generation of more optimal execution plans but also further improves ease of use, eliminating the need for manual intervention to adjust execution modes.

    - New capability for multi-plan selection based on bind parameters added: Prior to v23.4.7, when YashanDB received different input values for bound parameters or different parameter values generated by constant substitution, it could only use a fixed execution plan. In specific data distribution scenarios, this easily led to suboptimal SQL execution plans. This version introduces the new parameter _OPTIMIZER_ADAPTIVE_CURSOR_SHARING, which can control the impact of parameter values on plan generation. It supports generating corresponding optimal plans based on different bound parameter values and parameter values after constant substitution, and automatically selects the optimal solution combined with Cost evaluation. This optimization effectively addresses SQL performance adaptation issues caused by dynamic changes in data distribution, diverse business query scenarios, and fluctuations in hardware resources. It achieves significant improvement in the stability of SQL performance without manual intervention.

### Storage Engine Enhancements

Added virtual column support: Virtual columns can now be generated from expressions or functions based on existing physical columns using the new GENERATED ALWAYS clause. Virtual columns do not consume physical disk space and are computed dynamically at query time. This improves query performance in specific scenarios, simplifies business logic, saves storage resources, and reduces system maintenance costs.

### YAC Capability

- YFS supports online full repair after disk failure: Disk failures may occur in actual operation and require disk replacement. Before v23.4.7, YFS ensured continuous online service during disk failures, but did not support automatic data repair and replica reconstruction after new disks were added. This version introduces online data recovery and replica reconstruction for newly replaced disks, further improving system and data reliability to better meet high availability requirements.

- Added support for online addition and removal of standby clusters: In some customer scenarios, disaster recovery architectures need to be adjusted by adding or removing standby clusters online due to cost considerations or changing disaster recovery requirements. To minimize impacts on business continuity, v23.4.7 supports online addition and removal of standby clusters for YAC with one-click commands, allowing flexible cluster scale adjustment and reducing risks from manual operations.

- Added support for instance scale-in: In scenarios such as retail promotions, databases are often scaled out before peak events and scaled in afterward to avoid resource waste. Based on the existing online scale-out capability, v23.4.7 introduces online database instance scale-in for YAC, reducing unnecessary resource costs and improving resource utilization when business load decreases.

###  MySQL Compatibility

- Added table renaming (RENAME) support in mysql mode: Two syntaxes (ALTER TABLE RENAME AS and RENAME TO) are now supported for direct table renaming, further improving syntax compatibility with MySQL.

- Added BINARY keyword support for _bin collation in mysql mode: The BINARY keyword is now available in column definitions of ALTER TABLE/CREATE TABLE statements in mysql mode. It forces the column collation to use the _bin version of the corresponding character set (e.g., UTF8MB4_BIN), replacing the default case-insensitive collation for regular VARCHAR columns (e.g., UTF8MB4_GENERAL_CI). This aligns with MySQL's column sorting logic and enhances compatibility.

- Added ON UPDATE CURRENT_TIMESTAMP support in mysql mode: Automatic update rules can now be configured for TIMESTAMP and DATETIME columns using the ON UPDATE CURRENT_TIMESTAMP keyword. When a record is modified via an UPDATE statement (without explicitly updating this column), the column value is automatically updated to the current system timestamp. This eliminates the need for manual SQL logic to update timestamps, simplifies maintenance of data update times, and ensures the accuracy of data modification trails.

### Usability

- Optimized character set compatibility for *yasldr* and *imp* import tools: Prior to v23.4.7, importing CSV files with *yasldr* or metadata files with *imp* required the file character set to match the database character set; otherwise, the import would fail. This version optimizes the tools to support successful imports even when character sets are inconsistent, resolving import failures caused by character set mismatches. It improves import efficiency and reduces adaptation costs in heterogeneous database migration scenarios.

- New column added to DBA_TAB_COLUMNS view: The CHAR_COL_DECL_LENGTH column is newly added to this view, which records the declared length (in characters, not bytes) of character-type columns (CHAR/VARCHAR/NCHAR/NVARCHAR) at table creation. This allows users to quickly check the original defined specifications of columns, distinguish between declared character length and actual stored byte length, efficiently verify character column definitions in table structures, troubleshoot data truncation issues, and enhance compatibility with Oracle.

- Enhanced capabilities of parallel hints: Prior to v23.4.7, parallel hint syntax required specifying a specific table name to enable parallelism (e.g., /*+parallel(t 8)*/). This version enhances hint capabilities: users only need to specify the parallel keyword and parallelism degree (e.g., /*+parallel(8)*/) to enable parallelism for multi-table operations and other related operations, significantly improving the ease of use and flexibility of parallel hints.

### Driver

JDBC driver enhancements: 

- Added support for named parameter binding in CallableStatement: Prior to v23.4.7, the JDBC CallableStatement interface only supported positional parameter binding when executing stored procedures. This version introduces named parameter binding, resolving pain points such as parameter order dependency, poor readability, and difficult maintenance associated with positional binding. It improves the flexibility and maintainability of stored procedure/function calls and expands applicable usage scenarios.

- New getClientInfo-related interfaces added: Interfaces for retrieving client information (Client Info) of the current database connection are newly added. Client information is stored as key-value pairs, which can be used to identify the connection source, purpose, and client attributes. This helps database administrators track connection context, conduct audit work, and perform performance optimization.

- Optimized performance of the Stmt.Close interface: Prior to v23.4.7, each call to the JDBC Stmt.Close interface required a separate network interaction. This version optimizes the interface by caching the stmts to be closed locally. When prepare, execute, or DirectExecute operations are performed next time, the IDs of the stmts to be closed are sent to the server in a single batch, with no need to wait for a response after sending. By reducing the number of network interactions, the performance of the statement close operation is significantly improved— the higher the network latency, the more pronounced the optimization effect.
