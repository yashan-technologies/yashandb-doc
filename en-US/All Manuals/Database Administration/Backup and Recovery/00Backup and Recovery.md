Common scenarios for using backup and recovery are as follows:

- **Data Protection**: Factors such as system crashes, disk failures, application errors, or human errors may lead to data loss. Performing regular backups of the database and restoring when necessary can mitigate the impact of data loss on business operations.
- **Data Migration**: Due to certain requirements, data in the database needs to be migrated to another primary database. At this time, the backup and recovery functionality can be utilized to accomplish the data migration.

As the foundation of business systems, databases must ensure the safety of their data. For database administrators, formulating an appropriate backup strategy is crucial.

Traditional backup methods are divided into cold backup (offline backup, where the database stops serving) and hot backup (online backup, where the database operates normally). This chapter will focus on YashanDB's hot backup capabilities. Database administrators can refer to these documents while using the system and make appropriate adjustments based on their own circumstances to ensure the safety of enterprise data.

The backup and recovery capabilities supported by YashanDB mainly include the following:

* **Full Backup**: A complete copy of all target data at a certain point in time (for all primary nodes in ISC Distributed Cluster Deployment) is performed without relying on previous backup sets. A full backup set can restore all data, with the shortest recovery time and the most convenient operation.
* **Incremental Backup**: The initial baseline backup (Level 0) is performed, and each subsequent backup only requires backing up incremental data (Level 1), which is highly efficient and saves disk space. Recovery must start from the baseline backup set and sequentially restore all incremental backups.
* **Archival Backup**: A complete copy of the archive log files generated by the currently operational database can be flexibly specified in terms of the range of archive files to back up (including SEQUENCE, SCN, TIME), generating an independent backup set for that range.
* In Standalone Deployment, it is also possible to back up/recover tablespaces on demand (e.g., backing up only the tablespace containing critical data), thus streamlining operations and reducing storage costs.
* **Full Recovery**: After performing recovery from the backup set, if the archive log files and online logs generated after this backup set are continuous and complete, YashanDB will apply all logs and recover the database to the latest point in time of continuous log sequence numbers. If there are no retained archive log files generated after this backup set, only data from the backup set timestamp can be restored. In ISC Distributed Cluster Deployment, full recovery means all nodes can recover to the backup timestamp and open all nodes after recovery.
* **Archival Recovery**: By specifying an existing archive log files backup set and the recovery range (including SEQUENCE, SCN, TIME), the database can be restored.
* **Point-in-Time Recovery**: After performing recovery from the backup set, if the archive log files and online logs generated after this backup set are continuous and complete, you can specify that YashanDB continues to recover the database to any point in time.
* Use **Parallelism** settings to improve backup and recovery efficiency.
* **Backup Compression**: When the amount of data to back up is large, disk space is tight, or there are other data compression needs, compressed backups can be executed to improve disk utilization.
* **Backup Encryption**: If there are high security requirements for the backed-up data content, different encryption algorithms can be specified during backup to encrypt the backup data set, ensuring the security of the backup data set.

For Standalone/YAC/Distributed Cluster Deployment, backups can be performed using either [SQL statements](Backup and Recovery Using SQL Statements/00Backup and Recovery Using SQL Statements) or the [yasrman tool](Backup and Recovery Using yasrman/00Backup and Recovery Using yasrman); for ISC Distributed Cluster Deployment, backup and recovery can only be performed using the [yasrman tool](Backup and Recovery Using yasrman/00Backup and Recovery Using yasrman).

> **Note**: 
>
> If there are local temporary tablespaces or local SWAP tablespaces in the database, the files for these tablespaces will not be created directly after backup and recovery. The corresponding files will only be created when the database is triggered to the open state.

Common scenarios for recovering the database from an abnormal state to normal using backup sets include:

- **Scenario 1: Database Fails to Start**

  Possible causes:

  - Control file is corrupted or lost

  - Critical data file is corrupted or lost

  - Online log file is corrupted or lost

  Recovery method: It is recommended to perform a full complete recovery.

- **Scenario 2: Table Misoperation**

  Possible causes:

  - Delete or update misoperation leads to deletion or modification of table data

  - Truncate results in clearing the table data

  - Drop leads to table deletion

  Recovery methods:

  - If the misoperation that caused data loss is detected in a timely manner, it is recommended to use [Flashback](../故障处理/闪回/全库闪回/00全库闪回) to recover table data (refer to the specific meanings of UNDO_RETENTION/UNDO_FORCE_RETENTION).

    - For delete or update misoperations, if the undo is overwritten, flashback may fail.

      ```sql
      FLASHBACK TABLE {table_name} TO SCN {SCN};
      FLASHBACK TABLE {table_name} TO TIMESTAMP {TIMESTAMP};
      ```

    - For truncate misoperation, ensure that the recycle bin is enabled; if the recycle bin is overwritten, flashback may fail.
          
      ```sql
      FLASHBACK TABLE TO BEFORE TRUNCATE;
      ```

    - For drop misoperation, ensure that the recycle bin is enabled; if the recycle bin is overwritten, flashback may fail.
          
      ```sql
      FLASHBACK TABLE TO BEFORE DROP
      ```

  - If flashback cannot be used, it is recommended to perform point-in-time recovery to restore to the time before the table misoperation.

- **Scenario 3: In primary/standby mode, when the primary database crashes, the standby database automatically promotes to the primary database; a new standby database is built**

  Possible causes:
  
  - Operating system of the primary database crashes  
  - Critical files of the database are mistakenly deleted  
  - Network issues prevent connection to the primary database

  Recovery method: If the data volume is large, it is recommended to use complete recovery to rebuild the standby database; otherwise, the build database method can be used to rebuild the standby database.

- **Scenario 4: Data Migration**

  Possible causes:
  
  - Primary database system crashes and needs to perform recovery on another machine
  - Database cloning

  Recovery methods: Both complete recovery and point-in-time recovery can complete the database restoration; choose the recovery method based on actual needs.
