To configure a logical standby database/standby cluster, you need to first create the standby database/standby cluster (which is a physical standby database/standby cluster by default) and then execute related operations to convert it to a logical standby database/standby cluster.

To standardize terminology, in YAC Deployment, "primary database" refers to the primary cluster, and "standby database" refers to the standby cluster.

## Prerequisites

- The current environment is not an ISC Distributed Cluster.

- The table types, data types, etc. of the primary database must meet the [logical replication scope](00Data Synchronization.html#scope).

- Ensure that the current environment and the environment after configuring the logical standby database still meet the [operating requirements for logical standby databases](00Data Synchronization.html#requirement).

## Operation Steps

### Step 1: Create Standby Database

Create a standby database/standby cluster and record the relevant information of the target node for future reference (e.g., node ID, connection information, etc.).

- In Standalone Deployment, please refer to [Standbys Scaling](../../安装和升级/扩缩容/单机主备扩缩容/备库扩缩容.html#Scalingbysql) to create a new standby database in an existing environment, or refer to [Standalone Deployment Installation Guide](../../安装和升级/安装部署/YashanDB服务端安装（命令行）/单机（主备）部署) to directly deploy a new primary-standby environment. At this time, the standby database is in a physical standby database state.

- In YAC Deployment, please refer to [YAC Deployment Installation Guide](../../安装和升级/安装部署/YashanDB服务端安装（命令行）/共享集群部署) to deploy the primary-standby cluster environment. The standby cluster defaults to a physical standby cluster during initialization.

### Step 2: Add Standby Log Files to the Standby Database

Standby log files are used to store redo logs generated by the logical standby database. You need to plan for the space usage, file paths, and number of standby log files before constructing the logical standby database.

Each logical standby database requires at least 3 standby log files. If standby log files have been configured in the current environment, this operation can be skipped.

::: tabs
== Standalone Deployment

1. Connect and log in to the primary database as a DBA user.


2. Execute the following statements in the primary database to create standby log files:

   ```sql
   ALTER DATABASE ADD STANDBY LOGFILE 'REDO11' SIZE 128M;
   ALTER DATABASE ADD STANDBY LOGFILE 'REDO12' SIZE 128M;
   ALTER DATABASE ADD STANDBY LOGFILE 'REDO13' SIZE 128M;
   ```

== YAC Deployment

1. Log in to an instance of the primary cluster as a DBA user.


2. Execute the following statements in the master instance to create standby log files:

   ```sql
   ALTER DATABASE ADD STANDBY LOGFILE 'REDO11' SIZE 128M;
   ALTER DATABASE ADD STANDBY LOGFILE 'REDO12' SIZE 128M;
   ALTER DATABASE ADD STANDBY LOGFILE 'REDO13' SIZE 128M;

   -- In YAC Deployment, standby redo log files can also be added on the master instance for offline instances (using instance 2 as an example in this document).
   ALTER DATABASE ADD STANDBY LOGFILE THREAD 2 'REDO23' SIZE 128M;
   ```

3. Repeat the above operation to create three STANDBY LOG files for each instance.
:::

### Step 3: Stop Physical Apply (redoApply) on the Standby Database

Before converting the physical standby database to a logical standby database, you need to stop the redo apply on the physical standby database to avoid interference with the subsequent construction of the logical standby database.

Log in to the standby database/master instance of the standby cluster and execute the following statement on the standby database to stop the redo apply:

```sql
ALTER DATABASE RECOVER MANAGED STANDBY DATABASE CANCEL;
```

### Step 4: Execute DBMS\_LOGSTDBY.BUILD Operation

1. Log in to the target node as a DBA user.

   - Standalone Deployment: the primary database  

   - YAC Deployment: the master instance of the primary cluster (instance with INSTANCE_ROLE set to MASTER_ROLE in the V$INSTANCE view)  

2. Execute DBMS_LOGSTDBY.BUILD:

   - You need to wait for all active transactions to complete before executing DBMS_LOGSTDBY.BUILD. Long-running transactions in the primary database can affect the execution efficiency of this command.

   - After executing DBMS_LOGSTDBY.BUILD, the primary database will automatically enable the database-level supplemental logging, and the logging mode will be PRIMARY KEY.

   - In YAC Deployment, ensure that all active instances are in the OPEN state (not NOMOUNT or MOUNT). The BUILD process will briefly block instances from joining the cluster.

   ```sql
   EXECUTE DBMS_LOGSTDBY.BUILD;
   ```

3. Check to confirm that the BUILD operation has been synchronized to the standby database.

   1. ) Check the current log flush sequence number (the `FLUSH_LFN` field in the [GV$ARCHIVE_DEST_STATUS](../../参考手册/系统视图/动态视图/GV$ARCHIVE_DEST_STATUS) view) on the primary database.

      ```sql
      SELECT THREAD#, CONNECTION, STATUS, FLUSH_LFN FROM GV$ARCHIVE_DEST_STATUS ORDER BY THREAD#;

      THREAD# CONNECTION        STATUS                        FLUSH_LFN 
      ------- ----------------- ----------------- --------------------- 
            1 CONNECTED         NORMAL                             3026
            2 CONNECTED         NORMAL                               32
            3 CONNECTED         NORMAL                               30
      ```

   2. ) Check the current log reception sequence number (the `RECEIVED_LFN` field in the [V$REPLICATION_STATUS](../../参考手册/系统视图/动态视图/V$REPLICATION_STATUS) view) on the standby database. If it exceeds the log flush sequence number of the primary database, it can be considered that log synchronization is complete.  

      ```sql
      SELECT THREAD#, CONNECTION, STATUS, RECEIVED_LFN FROM V$REPLICATION_STATUS ORDER BY THREAD#;

      THREAD# CONNECTION        STATUS                     RECEIVED_LFN 
      ------- ----------------- ----------------- --------------------- 
            1 CONNECTED         NORMAL                             3026
            2 CONNECTED         NORMAL                               32
            3 CONNECTED         NORMAL                               30
      ```

### Step 5: Convert Standby Database Type

Restart the standby database to the mount stage and execute related statements to convert it to a logical standby database.

####  Scenario 1: Build a Regular Logical Standby Database

The role of the standby database will change to LOGICAL STANDBY, and the database's DB_NAME and DBID will also change.

It applies only to Standalone Deployment.



1. Log in to the standby database server using the installation user.

2. Restart the standby database to the MOUNT stage.

   ```shell
   # Specify the node ID of the standby database and restart the standby database, e.g., 1-3
   $ yasboot node restart -c yashandb -n 1-3 -m mount
   ```

3. Log in to the standby database as a DBA user.


4. Perform the logical standby database conversion.

   ```sql
   ALTER DATABASE RECOVER TO LOGICAL STANDBY new_db_name;
   ```

5. Start the database to OPEN.

   ```sql
   ALTER DATABASE OPEN;
   ```

####  Scenario 2: Rolling Upgrade

The role of the standby database will change to LOGICAL STANDBY, and the database's DB_NAME and DBID will not change.

== Standalone Deployment



1. Log in to the standby database server using the installation user.

2. Restart the standby database to the MOUNT stage.

   ```shell
   # Specify the node ID of the standby database and restart the standby database, e.g., 1-3
   $ yasboot node restart -c yashandb -n 1-3 -m mount
   ```

3. Log in to the standby database as a DBA user.




4. Perform the logical standby database conversion.

   ```sql
   ALTER DATABASE RECOVER TO LOGICAL STANDBY KEEP IDENTITY;
   ```

5. Start the database to OPEN.

   ```sql
   ALTER DATABASE OPEN;
   ```


== YAC Deployment

1. Log in to any server of the standby cluster using the installation user.

2. Restart the standby cluster.  

   ```shell
   # Check the database instance startup method (AUTO_START parameter)
   $ ycsctl get AUTO_START
   YCS AUTO_START = ALWAYS
         
   # Stop the database cluster
   $ yasboot cluster stop -c yashandb

   # Start the database instance on the current server to MOUNT stage
   # If AUTO_START = ALWAYS (default value), execute the following command to directly start YCS instance and database instance
   $ ycsctl start ycs -m mount

   # If AUTO_START = NEVER, execute the following two commands to start YCS instance first, then the database instance
   $ ycsctl start ycs 
   $ ycsctl start instance -m mount
   ```

3. Log in to the instance as a DBA user.



4. Perform the logical standby database conversion.

   ```sql
   ALTER DATABASE RECOVER TO LOGICAL STANDBY KEEP IDENTITY;
   ```

5. Start the database to OPEN.

   ```sql
   ALTER DATABASE OPEN;
   ```


:::

### Step 6: Enable Logical Apply (SQL Apply) on the Logical Standby Database

By default, logical apply functionality is not enabled on a logical standby database. You need to enable logical apply on the standby database (i.e., to apply redo data to the logical standby database).

1. Log in to the target node as a DBA user.

   - Standalone Deployment: the standby database  

   - YAC Deployment: the master instance of the standby cluster (instance with INSTANCE_ROLE set to MASTER_ROLE in the V$INSTANCE view)  

2. Enable logical apply:

   ```sql
   ALTER DATABASE START LOGICAL STANDBY APPLY IMMEDIATE;
   ```
