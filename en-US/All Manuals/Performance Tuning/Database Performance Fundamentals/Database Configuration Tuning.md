## Installation and Deployment Phase of YashanDB
During the [installation and deployment](../../Installation and Upgrade/Installation and Deployment/00Installation and Deployment) process of YashanDB, database performance can be improved by using the [recommended configuration](../../Development Guide/PL Reference Manual/Built-in Advanced PL Packages/DBMS_PARAM), modifying the database creation parameters, and using [resource management](../../Database Administration/Resource Management/00Resource Management).

## Initialization of Configuration Parameters

YashanDB provides a series of performance parameters that can meet the performance requirements under different hardware environments and business models. During database initialization, these parameters should be assigned appropriate initial values based on application requirements and environmental resources; at the same time, it may be necessary to adjust these parameters during subsequent database operations to address identified performance bottlenecks.

In addition to parameter optimization during database operation based on identified bottlenecks, the database should also initialize appropriate parameter values according to application requirements during initialization.

The following table lists the configuration parameters that require special attention when deploying a database instance. The initial values of these parameters are crucial for database performance:

|Parameter Name |Parameter Description |
|:---------------------------| :----------------------------------------------------------- |
| VM_BUFFER_SIZE               | VM is used to store intermediate results of data operations, such as order by and group by. If configured too small, it may lead to frequent VM swapping (resulting in IO).<br/>It is recommended to configure a reasonable VM size based on actual application needs. |
| REDOFILE_IO_MODE             | The IO mode of the redo file; different disks may have significant performance differences under different IO modes. Setting a reasonable IO mode can fully utilize disk performance.<br/>It is recommended to use the default value; if significant performance issues occur, suitable IO modes can be found through performance testing. |
| REDO_BUFFER_SIZE             | The size of the redo buffer; setting a larger buffer can improve the efficiency of redo flushing and redo application.<br/>It is recommended to set REDO_BUFFER_SIZE to 64M. |
| REDO_BUFFER_PARTS            | The number of partitions in the redo buffer; the redo generated by a session is hashed into a unique partition. Setting a reasonable number of partitions can reduce concurrent conflicts.<br/>It is recommended to set REDO_BUFFER_PARTS to 8. |
| COLUMNAR_BUFFER_SIZE         | The size of the stable data cache available for objects (such as LSC tables) that use stable data cache, plus the memory used by vectorization calculation. Increasing it can enhance read hit rate, import performance, and computational performance of LSC tables. It is recommended to buffer Slice metadata and frequently accessed small tables in memory.<br/>For HEAP/TAC tables, it is recommended to configure this parameter to the default value.<br/>For LSC tables, it is recommended to refer to [parameter sizes](#para) for configuration. |
| SCOL_CACHEABLE_SCAN_ROWS     | The maximum number of records scanned using stable data buffer for LSC tables. If the query plan evaluates the scanned record count to exceed this value, the stable data cache will not be used.<br/>It is recommended to adjust this configuration based on stable data buffer size, current business buffer effects, and overall query performance. |
| DBWR_COUNT                   | Database Writer is used to flush dirty blocks generated by the database to disk. This parameter configures the number of Database Writers. Generally, (especially on SSDs), increasing the number of Database Writers can enhance IO efficiency.<br/>It is recommended to set a suitable number of Database Writers based on the actual hardware environment and business pressure. |
| DB_BLOCK_SIZE                | The block size for organizing data, including the size of blocks in files and in Data Buffer. YashanDB provides three different specifications of block sizes: 8K, 16K, and 32K for configuration.<br/>Smaller data blocks can reduce data access conflicts under high concurrency, while larger blocks can enhance IO efficiency. Therefore, it is recommended to configure smaller block sizes for transaction processing scenarios and larger block sizes for data warehousing scenarios.<br/>The block size specified during database creation cannot be changed unless a new database is created. |
| DATA_BUFFER_SIZE             | The size of the data buffer; this value is critical for database performance. A reasonable buffer configuration will effectively reduce IO overhead.<br/>It is recommended to refer to [parameter sizes](#para) for configuring DATA_BUFFER_SIZE.<br/>Setting this parameter too small may result in startup or creation failures. The minimum value is approximately calculated using the formula: (UNDO_SEGMENTS * 99 + 1K) * DB_BLOCK_SIZE, where UNDO_SEGMENTS and DB_BLOCK_SIZE are referenced from CREATE DATABASE, with UNDO_SEGMENTS taking a minimum value of 64 during calculation. |
| COMPRESSION                  | The default compression method for LSC tables. If no compression method is specified during table creation, this configuration will be used. This value can be set to UNCOMPRESSED for no compression, LZ4 for compression, or ZSTD for compression.<br/>It is recommended to use compression, which can reduce storage space usage and lower IO overhead. In terms of compression ratio, ZSTD outperforms LZ4; in terms of compression and decompression time, LZ4 outperforms ZSTD. |
| CHECKPOINT_TIMEOUT           | The interval for Checkpoint, indicating that an incremental Checkpoint is executed after a period of time.<br/>Increasing the Checkpoint frequency can reduce the risk of redo lag and decrease downtime restart time, but it will increase disk IO. Conversely, this may increase the risk of redo lag and increase downtime restart time.<br/>It is recommended to set this value to between 10 to 30 seconds, but if in a short duration extreme performance testing scenario, a larger value can be set to avoid triggering Checkpoint. |
| CHECKPOINT_INTERVAL          | The threshold size of Checkpoint redo, indicating that an incremental Checkpoint will be executed when the total size of redo covered by Checkpoint (the redo needed for restart apply) exceeds this value.<br/>Setting a smaller threshold can increase Checkpoint frequency and reduce redo lag risk and downtime restart time.<br/>It is recommended to set this value to the average size of redo files, but if in a short duration extreme performance testing scenario, a larger value can be set to avoid triggering Checkpoint. |
| MEX_POOL_SIZE                | This memory is used for SQL batch execution and JSON; operations such as hash join, hash group by, order by will prioritize attempting to compute entirely in memory.<br/>It is recommended to configure a reasonable size based on actual application needs. |

### Parameter Correlation

Most parameters in YashanDB are independent; however, certain parameters have correlations, and the sizes of some files depend on parameter settings.

- REDO_BUFFER_PARTS is related to the REDO_BUFFER_SIZE parameter, and unreasonable configuration may lead to database startup errors. For details, please refer to [configuration parameters](../../Reference Manual/Configuration Parameters).
- The minimum size of double writing files depends on DBWR_COUNT, DBWR_BUFFER_SIZE, and DB_BLOCK_SIZE. When these parameters are increased, the database startup may report double writing file too small errors; at this time, [resize](../../Development Guide/SQL Reference Manual/SQL Statements (yashan Mode)/ALTER DATABASE) the double writing files.
- The minimum size of redo files depends on REDO_BUFFER_SIZE, MAX_SESSIONS, and DB_BLOCK_SIZE. For details, please refer to [ALTER DATABASE](../../Development Guide/SQL Reference Manual/SQL Statements (yashan Mode)/ALTER DATABASE) and [configuration parameters](../../Reference Manual/Configuration Parameters).

### Parameter Size

Resource-related parameters should not be set too large, as this may prevent the database from starting due to inability to allocate resources. Memory-related parameters require even more attention; although larger settings may improve performance, the total system memory is limited, and reasonable allocation of this memory is essential to maximize database performance. Among them, DATA_BUFFER_SIZE, COLUMNAR_BUFFER_SIZE, and VM_BUFFER_SIZE consume the most memory, and their proportions vary across different business scenarios. The following are suggested configurations for different types of tables in both Standalone Deployment and ISC Distributed Cluster Deployment scenarios:

**Standalone Deployment Scenario**

- If all table types are HEAP, it is recommended that DATA_BUFFER_SIZE account for about 80%, VM_BUFFER_SIZE be allocated based on business type, while COLUMNAR_BUFFER_SIZE and COLUMNAR_DATA_BUFFER_PERCENT use default values.
- If all table types are TAC, it is recommended that DATA_BUFFER_SIZE account for about 60%, COLUMNAR_BUFFER_SIZE account for about 30%, VM_BUFFER_SIZE be allocated appropriately, and COLUMNAR_DATA_BUFFER_PERCENT set around 99.
- If all table types are LSC, it is recommended that COLUMNAR_BUFFER_SIZE account for about 75%, DATA_BUFFER_SIZE account for about 10%, VM_BUFFER_SIZE be allocated appropriately, and COLUMNAR_DATA_BUFFER_PERCENT set around 70.

**ISC Distributed Cluster Deployment Scenario**

For CN Nodes:

-  If all table types are HEAP, it is recommended that VM_BUFFER_SIZE be allocated based on business type, while DATA_BUFFER_SIZE, COLUMNAR_BUFFER_SIZE, and COLUMNAR_DATA_BUFFER_PERCENT use default values.
- If all table types are TAC, it is recommended that COLUMNAR_BUFFER_SIZE account for about 70%, VM_BUFFER_SIZE be allocated appropriately, DATA_BUFFER_SIZE use default value, and COLUMNAR_DATA_BUFFER_PERCENT set around 99.
- If all table types are LSC, it is recommended that COLUMNAR_BUFFER_SIZE account for about 75%, VM_BUFFER_SIZE be allocated appropriately, DATA_BUFFER_SIZE use default value, and COLUMNAR_DATA_BUFFER_PERCENT set around 99.

For DN Nodes:

-  If all table types are HEAP, it is recommended that DATA_BUFFER_SIZE account for about 90%, VM_BUFFER_SIZE be allocated based on business type, while COLUMNAR_BUFFER_SIZE and COLUMNAR_DATA_BUFFER_PERCENT use default values.
- If all table types are TAC, it is recommended that DATA_BUFFER_SIZE account for about 50%, COLUMNAR_BUFFER_SIZE account for about 35%, VM_BUFFER_SIZE be allocated appropriately, and COLUMNAR_DATA_BUFFER_PERCENT set around 99.
- If all table types are LSC, it is recommended that COLUMNAR_BUFFER_SIZE account for about 85%, DATA_BUFFER_SIZE account for about 5%, VM_BUFFER_SIZE be allocated appropriately, and COLUMNAR_DATA_BUFFER_PERCENT set around 60.

For MN Nodes: it is recommended that DATA_BUFFER_SIZE, COLUMNAR_BUFFER_SIZE, VM_BUFFER_SIZE, and COLUMNAR_DATA_BUFFER_PERCENT all use default values.

These are just suggested configurations and may not achieve optimal performance for all business models. Recommendations for adaptive generation and application can refer to [DBMS_PARAM](../../Development Guide/PL Reference Manual/Built-in Advanced PL Packages/DBMS_PARAM).

## Initialization of Redo Files

For performance considerations, YashanDB uses the Write-ahead Logging (WAL) mechanism to ensure data persistence, and the database performance is therefore closely related to the size of the redo files. Generally, larger redo files lead to better overall database performance. When redo files are smaller, the checkpoint mechanism needs to be triggered frequently to free up redo space, which can impact database performance.

Redo files are reused cyclically, and before an old redo file can be reused, all dirty pages corresponding to that redo must be flushed to disk. If the corresponding dirty pages have not been flushed to disk by Checkpoint before the redo is reused, the system will throw a "checkpoint not complete" warning log, and business execution will be blocked, resulting in a redo lag phenomenon.

When business volume surges, the speed of redo generated may exceed that of Checkpoint, leading to redo lag after some time. Generally, larger redo files can provide a longer lag cache time.

Redo files should not be too small, or it will result in frequent switching of redo files.

It is recommended to initially create at least six redo files, with the size of each redo file set according to disk resources, within the range of 100MB to 100GB, and the redo block size set to the system-supported IO block size. The empirical reference for redo file size settings is that under normal database load, the interval for automatic switching of redo files should be at least 5 minutes.

## Initialization of Tablespaces

YashanDB has different tablespaces for different purposes, and database performance is closely related to each type of tablespace. For built-in tablespaces, if information is not specified in the database creation SQL, the system will create built-in tablespaces with default sizes, which are generally far smaller than normal application requirements. Therefore, users should configure reasonable initial sizes for all built-in tablespaces based on data volume, concurrency, application scenarios, and other factors when creating the database.

### Permanent Tablespace

Permanent tablespaces are used to store user data. In configuring the tablespaces, SYSTEM and SYSAUX tablespaces are generally used to store the database's metadata, while it is recommended to use separate user tablespaces for user data (using the default USERS tablespace or creating new user tablespaces).

Users should have a pre-planned approach to data storage space, as both too small or too large of storage space can bring issues:

- Too small tablespace: If the actual utilized space exceeds the capacity of the tablespace, it may cause application errors. Enabling auto-extension can prevent errors, but may lead to fluctuations in application performance.
- Too large tablespace: Significant space wastage may cause resource exhaustion.

When planning data storage space, consider the following factors:

- Number of tablespaces: Generally, only one tablespace is needed, but in some scenarios, such as data partitioning, different tablespaces can be chosen for data storage to improve performance and reliability.
- Number of data files mounted to the tablespace: YashanDB's default maximum size for a single data file is 512G; when the data volume exceeds this value, it is necessary to consider adding multiple data files.
- Size and attributes of data files: To avoid automatic extensions during operation, the initialized value should meet the required data file size as much as possible. When configuring auto-scaling properties, the maximum data volume should be kept within the planned disk capacity to avoid resource exhaustion.  

YashanDB adopts a space pre-allocation strategy when creating data files, which may take longer during initialization, so it is recommended to create multiple tablespaces simultaneously to improve initialization efficiency.

### Undo Tablespace

The undo tablespace (i.e., the undo tablespace in built-in tablespaces) is used to store undo data, applicable in scenarios such as rollbacks and consistent reads.

Unlike user data storage, the storage of undo data employs a cyclic reuse mechanism, meaning that undo data exceeding the retention period (controlled by the UNDO_RETENTION parameter) may be overwritten. This requires users to configure a reasonable size for the UNDO tablespace based on actual scenarios; if configured too small, errors such as "snapshot too old" may occur; if configured too large, it may lead to wasted space in the UNDO tablespace.

It is recommended to configure the UNDO tablespace initialization based on the value of the UNDO_RETENTION parameter:

- Generally, larger UNDO_RETENTION values necessitate larger planning for the UNDO tablespace.
- The initial value for the UNDO tablespace can be relatively small (e.g., 1G) while configuring reasonable extension attributes.
- Opening the undo's self-maintenance mechanism via parameters UNDO_SHRINK_ENABLED and UNDO_SHRINK_INTERVAL can reduce the difficulty of maintaining the UNDO tablespace.

### Temporary Tablespace

The temporary tablespace is used to persist temporary table data when necessary, and its initial size configuration depends on how temporary tables might be used within the application system. It is recommended to not set the initial value too large; enabling auto-extension is sufficient unless the application system has explicit temporary table requirements.

In YashanDB, the storage space for temporary tables is pre-allocated but is only used when there is inadequate BUFFER to swap out, and it is reset after database restarts. Therefore, users can consider the following two aspects for tuning:

- When the temporary tablespace is insufficient, its capacity can be increased using RESIZE or ADD DATAFILE.
- When the temporary tablespace is excessive, a SHRINK operation can be executed to release physical space.

### Swap Tablespace

The swap tablespace is used as the physical swap space for the VM BUFFER. In scenarios such as SORT, GROUP BY, HASH JOIN, etc., the VM BUFFER may be consumed, and when the VM BUFFER is insufficient, it needs to swap in and out using the Swap tablespace.

Users should configure a suitable initial value for the size of the Swap tablespace based on the VM_BUFFER_SIZE parameter value and their business conditions. When unable to accurately evaluate, it can initially be set to a smaller value with auto-extension enabled.

The Swap tablespace may be temporarily expanded by certain SQL operations; when such situations are discovered, users can release physical space through SHRINK functionality after the space becomes idle.
