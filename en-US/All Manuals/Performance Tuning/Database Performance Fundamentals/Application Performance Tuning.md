## System Architecture

In bridge design, the strength of the bridge depends on its weakest part. Performance design is similar; every component of the application system, from top to bottom, must meet performance requirements. Users need to consider different load scenarios to design the architectures of various components, which primarily include hardware architecture and software architecture.

**Hardware Architecture**

When designing hardware architectures related to database performance, the following factors should be considered primarily:

- CPU: Determines the execution capability and parallel processing capacity of the database.
- MEMORY: The database uses a large amount of memory to buffer data, reducing I/O access.
- I/O: There are significant performance differences among various disks. Some disks also provide fault tolerance capabilities, which need to be chosen based on database requirements.
- NETWORK: Determines the communication efficiency of the database, with a focus on bandwidth and latency.

**Software Architecture**

Typically, application systems consist of the following software components:

- User Interface
- Business Logic
- Resource Management
- Transaction Processing

When designing these software components, users should also consider database performance, with the principle of minimizing pressure on the database.

## Application Design Principles

**Data Model Design**

Applications plan and design business data models and relationships by creating database tables. Improper data model design can have a very adverse effect on database performance and may be difficult to optimize later using SQL. When designing the data model for YashanDB, attention should be paid to the following points:

1. Choose the appropriate table type:
    - For analyzing massive stable data, it is recommended to use LSC tables, utilizing key technologies such as sparse indexing, predicate pushdown, and data compression to achieve exceptional query performance.

    - For real-time analysis business scenarios, TAC tables can be chosen, which support indexing, in-place updates, and vectorization calculation capabilities for fast data updating and querying.

    - For transactional business scenarios, HEAP tables can be selected to achieve extreme performance in high-concurrency online transaction processing.

2. Establish reasonable indexes:
    - Design index columns reasonably to avoid multiple indexes including the same columns excessively on the table.

    - When creating composite indexes, be mindful of the order of fields and place the fields that filter the most records in the first position.

3. Choose appropriate data types:
    - Opt for smaller data types, for example, INT types perform better than NUMBER types.

    - Choose suitable data types; for character types, if the length variation is significant, it is advisable to use VARCHAR, which saves space and reduces I/O pressure. If the data is of fixed length or very close, CHAR should be used for special performance optimization effects.

4. Choose appropriate table partition attributes:
    - YashanDB supports hash partitioning, range partitioning, and list partitioning.

    - With the partition pruning feature, data can be quickly filtered during access, greatly reducing the amount of data accessed and improving performance.

    - The partition feature can enhance parallel scanning capabilities.

5. In ISC Distributed Cluster Deployment, choose appropriate table distribution attributes:
    - For tables with smaller data volumes, consider creating them as duplicated tables to reduce cross-node joins.

    - Determine the partition key based on data distribution and access balance to fully utilize resources across all DNs, improving performance.

    - Make full use of the distribution pruning feature, which can quickly filter data during access, significantly reducing the amount of data accessed and enhancing performance.

**System Development Architecture Design**

In any system's design and architecture building phase, developers should ensure sufficient attention is paid to the execution efficiency of SQL.

The system development architecture should follow these recommendations:

1. Good database connection management:

    Establishing database connections is very costly and has poor scalability. Therefore, the number of concurrent connections to the database by applications should be kept as low as possible. For high-concurrency systems, ensure that database connections are pooled to reuse connections rather than re-establishing them for each user request.

2. Good cursor usage and management:

    Reducing SQL parsing and maintaining database connections is equally important. SQL parsing typically includes syntax parsing, semantic analysis, syntax checking, query rewriting, and query optimization phases. The execution plan generated by parsing is stored in the shared pool. SQL parsing is divided into hard parsing and soft parsing:

    - Hard parsing: Hard parsing occurs when a SQL statement is submitted and its execution plan is not found in the shared pool. The database will then perform a full SQL parsing, analysis, and checking operation. Hard parsing is resource-intensive.

    - Soft parsing: Soft parsing occurs when a SQL statement is submitted and its execution plan is found in the shared pool. The database will directly utilize the buffer to execute the SQL statement, thereby skipping parsing, analysis, and checking steps, enhancing performance.

    The number of parses should be minimized, so developers need to design SQL programs that can be parsed once and executed multiple times. A common practice is to use bound parameters to replace the changing parts of SQL executed each time, rather than directly concatenating changing strings into SQL. Otherwise, the probability of SQL statement reuse will be low, and it may not be reused by other users after parsing.

    For example, avoid using string constant SQL in programs: "SELECT * FROM AREA WHERE AREA_NAME = 'Beijing'"; instead, use bound variable SQL: "SELECT * FROM AREA WHERE AREA_NAME = :1".
