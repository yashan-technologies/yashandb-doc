The optimizer is the core of the SQL engine. Before understanding SQL tuning, one should familiarize themselves with the optimizer.

The purpose of the optimizer is to generate the best execution plan for SQL. The default optimizer for YashanDB is CBO (Cost-Based Optimizer), and its core rule is to choose the plan with the lowest cost among all possible alternative execution paths.

SQL is a non-procedural language; therefore, the optimizer can freely merge, reorganize, and process SQL statements in any order. It determines the optimal plan for SQL statements by examining various access methods (e.g., full table scan or index scan), different join methods (e.g., nested loops or hash joins), different join orders, and possible transformations.

For a given SQL query and hardware environment, the optimizer assigns a relative numerical cost to each possible plan step. It then aggregates these values to generate an overall cost estimate for the plan. The optimizer selects the plan with the lowest cost estimate (i.e., the optimal execution plan). The cost calculation is based on statistics and associated conditions, while in specific environments, the cost calculation also considers CPU, IO, and network communication.

Statistics are crucial for the CBO to make correct choices. Therefore, when the optimizer finds that the statistics are unreasonable, incomplete, or unavailable, it triggers dynamic statistics collection, overriding the old statistics. In certain special cases, if users identify through performance diagnostics that the optimizer has not updated the statistics, they can manually collect statistics.

As a key component affecting performance, the optimizer is always dedicated to generating the optimal execution plan. However, in a complex environment where various factors (such as metadata changes, data volume changes, etc.) intertwine, the optimizer's judgment may deviate. When the database environment is normal, but the execution plan generated by the optimizer is not optimal or desired, manual intervention may be required for tuning.

To further explore the optimizer's process of selecting execution operators, one can set and enable event 10053 and analyze the output trace file. For more details, please refer to [10053](../../../数据库管理/故障诊断/追踪.html#trace).
