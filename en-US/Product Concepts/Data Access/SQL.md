## Introduction to SQL
Structured Query Language (SQL) is an operation language for relational databases used for data access, data querying, data processing, and relational database system management. SQL provides an interface for operating relational databases and has a built-in security access mechanism check. All applications can access data in the YashanDB database using SQL statements.

SQL is a non-procedural declarative language that only describes the purpose of the statement (what kind of data operation to perform) without providing the implementation process. Therefore, when processing SQL, YashanDB first uses the SQL compiler to generate a procedure structure—execution plan based on the SQL target, and then operates on the database, ultimately executing operators to obtain the corresponding result set.

The existence of SQL helps users focus solely on data processing without overly concerning themselves with the implementation process. For example, to calculate the average salary of all confirmed employees in a company's departments, an example SQL statement is as follows:

```SQL
SELECT DEPARTMENT_ID, AVG(SALARY) FROM EMPLOYEE E GROUP BY DEPARTMENT_ID HAVING E.ATTR = "Confirmed" ORDER BY DEPARTMENT_ID
```

In this query statement, `GROUP BY` completes the departmental grouping operation, `HAVING` completes the filtering of confirmed employees, `AVG` calculates the average salary, and `ORDER BY` implements sorting by department. When the statement is executed, the database will automatically organize data from the EMPLOYEE base table, performing grouping, filtering, sorting, aggregation, and projection operations row by row, and finally returns the expected result set.

All SQL statements are generated by the optimizer according to the specific cost model of YashanDB to produce the optimal execution plan, which is influenced by statistics, cost calculation formulas, HINTs, OUTLINE, and other functionalities.

All execution of plans is completed by YashanDB's execution engine, including the Volcano execution engine and the vectorized execution engine. The execution targets are the various execution operators defined by the execution plan.

## SQL Standards

SQL is a standardized language jointly defined by the American National Standards Institute and the International Organization for Standardization, with the main industry standards being `SQL92` and `SQL99`. In 2023, the `ISO/IEC 9075:2023` SQL standard was published. It has evolved from table definitions, data types, and various query functionalities to the latest inclusion of JSON semi-structured data standards.

However, the mainstream databases in the industry have differences in SQL implementations, so the term "dialect" is often used to refer to SQL languages that deviate from the standard due to specific implementation differences in databases.

## SQL Statement

In the YashanDB database, the SQL statement is the primary means of data processing. An SQL statement is a declarative statement that carries the purpose of data manipulation and consists of keywords, identifiers, binding parameters, literals, etc.

- **Keywords**
   
   Keywords are words used in SQL statements to delineate syntax positions or identify data types and other special purposes, which cannot be used arbitrarily. Keywords form the syntactical purpose of the SQL statement. For example, `INTEGER` is a keyword representing the integer data type and cannot be used as a column name.

- **Identifiers**

   Identifiers are words used in SQL statements to identify specific resources. Identifiers represent the targets of syntax processing in SQL statements.
   
   For example, in the following table creation statement, `EMPLOYEE` is the identifier representing the table name, while `DEPARTMENT_ID` and `SALARY` are identifiers representing column names.
   ```SQL
   CREATE TABLE EMPLOYEE(DEPARTMENT_ID INTEGER, SALARY NUMBER);
   ```

- **Binding Parameters**
   
   Binding parameters are used in SQL statements to reduce repetitive or similar SQL operations, saving compilation time by replacing variable parts in similar SQL operations with binding parameters.
   
   For example, in the following DML statement, the symbol `?` signifies a binding parameter that can be assigned different values.
   ```SQL
   SELECT * FROM EMPLOYEE E WHERE E.DEPARTMENT_ID = ? AND E.SALARY >= ?;
   ```

- **Literals**
   
   Literals refer to specific values, strings, and constants of particular types directly represented in SQL statements through strings that make up the SQL statement. When a literal represents a string, it must be enclosed in single quotes `''` for escape purposes.
   
   For example, in the following DML statement, the strings `'10'` and `'20000'` represent specific values used for filtering certain columns.
   ```SQL
   SELECT * FROM EMPLOYEE E WHERE E.DEPARTMENT_ID = '10' AND E.SALARY >= '20000';
   ```

SQL statements must be complete and comply with syntactic branch requirements. When SQL statements do not meet YashanDB's syntax requirements, an error will be reported.

The SQL statements provided by YashanDB include:

- Data Definition Language (DDL): Provides operations for creating, modifying, and deleting database objects.

- Data Manipulation Language (DML): Provides capabilities for adding, deleting, modifying, and querying data.

- Data Control Language (DCL): Provides operations for transaction mechanisms, privilege control, access control, etc.

### Data Definition Language (DDL)

Data Definition Language (DDL) provides operations for creating, modifying, and deleting database objects. Database objects include users, tablespaces, tables, indexes, views, sequences, synonyms, stored procedures, UDFs, triggers, advanced packages, and the database itself.

After the YashanDB database installation is complete, it initially enters the NOMOUNT phase upon the first startup, requiring the execution of a DDL statement to create a database before it can provide database services.

Common DDL statements include CREATE, ALTER, and DROP database objects, TRUNCATE to empty table data, and SHUTDOWN for the database.

Before executing DDL statements, the database will trigger a transaction commit operation to end the transactions prior to the DDL statement. This prevents any metadata change transactions caused by the current DDL statement from conflicting with previous transactions that may have already existed. Regardless of whether the current DDL statement executes successfully or not, earlier transactions will be committed and completed.

### Data Manipulation Language (DML)

Data Manipulation Language (DML) provides the ability to INSERT, UPDATE, DELETE, MERGE data, and SELECT queries, allowing operations on single or multiple tables.

INSERT statements can be executed as standalone SQL statements and can also use binding parameters for batch execution or use INSERT INTO TABLE SELECT to directly obtain data from a query result set.

DML modifies the data state, and when a transaction includes DML statements, the transaction is automatically initiated by executing the first DML statement. The AUTO_COMMIT parameter can control whether each DML statement commits automatically. Update and delete statements will first scan the target data in the database based on filter conditions before modification, and if a consistency check fails during modification, the SQL statement will restart, rescan the data, and then make modifications.

According to SQL specifications, data modifications executed within a transaction are visible to subsequent SQL statements within the current transaction.

To strengthen the capability of a single SQL modification to the database, YashanDB supports the merge operation (MERGE INTO), allowing for a composite syntax of INSERT, UPDATE, and DELETE, thus modifying data more efficiently and flexibly by reusing the result set of a single query.

SELECT can query multiple or single tables or views and undergo a series of calculations to ultimately obtain a result set. Regardless of whether querying HEAP tables, LSC tables, or TAC tables, the organization of the result set is the same. The execution process of a query is essentially the execution flow of the plan tree. The query plan tree consists of a series of operators, and to speed up the query, operators can be divided into multiple stages, with each stage transferring data through data exchange operators. Multiple stages can execute simultaneously, and each stage's instances can also execute in parallel. To further enhance query efficiency, query acceleration may be performed in many scenarios through vectorization calculation.

### Data Control Language (DCL)

Data Control Language (DCL) provides operations for transaction mechanisms, privilege control, access control, etc.

Transaction control statements can commit transactions (COMMIT), roll back transactions (ROLLBACK), set save points for rollback (SAVEPOINT), and perform rollbacks based on save points (ROLLBACK TO SAVEPOINT).

Authorization and revocation statements include GRANT for granting privileges and REVOKE for revoking them, which is based on user or role for granular privilege control.

Access control statements provide dynamic management of session properties after a user builds a connection. A session represents a connection status of a logged-in user in the database instance. After the user inputs their username and password and goes through privilege authentication, the database allocates a session to provide services until the user disconnects, thereby ending the session service. Throughout the entire session process, the current session can be adjusted using the ALTER SESSION statement.

DCL statements also include the capability to ALTER SYSTEM to change database instance-level parameter properties.

## Optimizer

The optimizer is the core component of the SQL engine, responsible for converting user input statements into execution representations (execution plans) for the database. The engine executes based on the optimized execution plan.

The optimizer formulates efficient execution plans by analyzing user input statements and data stored in the database, with analysis focusing on query condition analysis, potential access paths, system configuration parameters, data statistics, whether to use HINT suggestions, etc.

The optimizer primarily includes the following optimization operations:

- Condition supplement and movement; for example, `A = B AND A = 5` will supplement to output `B = 5`, filtering data related to B.

- Statement REWRITE and dynamic rewriting, transforming statements into representations that can expand into more paths based on algebraic equivalence.

- Determination of join order based on the commutative and associative laws of joins.

- Access path expansion.

- Path evaluation and selection, which calculates the cost of each path and chooses the one with the lowest cost as the optimal path.

The optimizer aims to expand all possible execution methods for each SQL statement and then selects the one with the lowest cost as the final query execution plan through cost calculations. Before actual SQL execution, users can print the optimizer's execution plan to assess the execution efficiency of statements.

If the plan does not meet expectations, a series of methods can be used to influence the execution plan:

- Adjusting statistics to make them closer to actual data distribution.

- Adjusting database-related parameters.

- Using hints for suggestions.

### Optimizer Components

The optimizer mainly includes the following components:

- Static optimization and transformation components

   These transform queries into equivalent forms of representation that help produce a better plan. For example, converting `outer join` to `inner join`.

- Dynamic transformation components

   These dynamically convert statements to produce as many equivalent forms as possible (but without certainty about which form is better), and can select the optimal form through cost plans, such as pushdown of `group by`.

- Cardinality estimation and cost calculation modules
   
   These assess the selection rate, cardinality, and corresponding execution costs of each operator in the plan.

- Plan selection components
   
   These traverse the costs of all available plans and select the one with the lowest cost as the final execution plan.

### Optimizer Statistics

Statistics is a comprehensive description of all objects in the database and the distribution and structure of data within various objects, differing from dynamic views during execution. The optimizer uses statistics to understand the data situation of specific objects and thus select suitable execution algorithms.

Common statistics include:

- Table statistics: number of rows, number of blocks, average row length, etc.

- Column statistics: counts of distinct values, null values, maximum and minimum values, and data distribution represented in histograms.

- Index statistics: index levels, number of leaf node blocks, and the clustering relationship between indexes and data.
   
Once statistics are collected, they are stored in corresponding field tables. When significant changes to the data occur, statistics need to be updated accordingly to reflect the actual data more accurately.

### Optimizer Hints

In certain scenarios, database administrators or application developers may understand the specific distribution of application data better than the optimizer and may know more clearly which plan would be better under such distribution. In this case, hints can be added to SQL statements to suggest to the optimizer how to perform the execution.

Hints represent advisory actions and cannot guarantee that the optimizer will execute as instructed. If invalid hints are provided, the optimizer will ignore their presence.

Major hints supported by the optimizer include:

- Data scanning methods, such as table scans or index scans.

- Join methods and join order, such as hash joins or nested loop joins, etc.

- Parallel and batch-related hints.

## SQL Processing

YashanDB converts SQL statement text into database objects and operation sequences to enable access and modification of the database.

### SQL Processing Stages

1. Soft Parse (SOFT PARSE) Stage: The plan buffer verification. YashanDB compares the SQL statement text with a copy in the plan buffer. If they match and the plan buffer does not contain invalidated database objects, the planner directly uses the plan in the buffer.

2. Parse (PARSE) Stage: If the plan buffer lookup fails, the parser reads the SQL text from front to back based on the SQL syntax tree, performing syntax validation and generating an abstract syntax tree.

3. Semantic Verification (VERIFY) Stage: The abstract syntax tree is translated into database objects, accompanied by semantic verification, such as verifying whether the table contains the queried fields.

4. Rewrite (REWRITE) Stage: Equivalent transformations are applied to the abstract syntax tree using static rewriting rules.

5. Optimize (OPTIMIZE) Stage: Usually involves optimizing the query section, including the query statement and query clauses in DML. The optimizer implements this based on cost models, generating a query plan tree with the lowest query cost. At this point, the optimizer has determined how to execute based on self-calculations or HINT suggestions, such as whether to use vectorization calculation acceleration.

6. Dynamic Rewrite (TRANSFORM) Stage: Equivalent transformations are applied based on statistics and dynamic query plans.

7. Execute (EXECUTE) Stage: The executor iterates execution based on the plan tree.
   
   The leaf nodes of the plan tree are usually scan operators, which need to obtain data from the storage layer, resulting in I/O operations. Intermediate operators of the plan tree often need to buffer the result sets of lower-level operators (such as grouping, sorting, deduplication, etc.), which are referred to as materialized operators. The area for buffering result sets is called the materialization area. When memory is insufficient, materialized operators will swap some data out to storage media, thus also resulting in I/O operations.

### DML SQL Processing

DML utilizes cursor technology to complete iterative data processing operations.

The query operation retrieves data sequentially based on the iteration capabilities of the cursor, iterating layer by layer and using projection expressions to calculate, ultimately presenting the result set externally. Ensuring read consistency, the result set of the query is a snapshot of the database at the initiation of the query.

Operations for data insertion/deletion/modification/merging will modify the database's data state and support read concurrency. However, modifications are always based on the latest state of the database and must control modification concurrency through locking, while logging modification information ensures the transaction's ACID features.

YashanDB reduces the chances of conflicts between DML concurrency by minimizing lock granularity and increasing transaction throughput capability.

### DDL SQL Processing

DDL modifies the metadata state of the database. Before executing DDL operations, it automatically triggers a commit of the previous transactions. DDL also verifies the availability of sufficient privileges and resources to adjust metadata.

DDL operations will only use hard parsing. Once parsed, they do not enter the plan buffer, and the optimizer will not perform any unnecessary optimization on DDL. The generated DDL plan will mainly come from parsing the DDL statement, executing immediately, and then being discarded afterward.

It is recommended to minimize concurrency between DDLs and between DDL and DML to improve execution success rates. YashanDB offers the capability for ONLINE DDL, allowing for minimal concurrent execution without significantly impacting the overall performance and throughput of the database.
