*yfscmd* manages data disks through the `exec` subcommand, and YFS defines disk management statements in a DDL format similar to SQL.

>**Note**:
>
> After the YAC/Distributed Cluster deployment is completed, configurations related to the system DiskGroup cannot be modified. 

- In non-interactive mode of *yfscmd*, the parameter modification statement must be enclosed in quotes and passed as a single parameter, without requiring a semicolon (`;`) at the end. The command format is: `yfscmd exec "CREATE ..."`.

- In interactive mode of *yfscmd*, the command format is `exec CREATE ...;`. In interactive mode, the `exec` subcommand supports multi-line input until terminated by `;`.

## CREATE DISKGROUP

This statement is used to create a new DiskGroup.

Prerequisites for creating a DiskGroup are as follows:


- The I/O fencing mode used by YAC has been confirmed. This can be viewed using the `ycsctl show fence` command.

- The storage device has been [prepared](../../Installation and Upgrade/Installation and Deployment/Pre-Installation Preparation/Preparing the Servers.md#Storage) according to requirements, and the hardware devices planned for each FailureGroup must meet the [fault isolation standard](../../Product Concepts/YAC Infrastructure/Yashan File System.md#FailureGroup).

- The storage device has been [configured](../../Installation and Upgrade/Installation and Deployment/Pre-Installation Preparation/Configuring the Storage Devices) according to requirements (e.g., partitioning, mounting, etc.), and the disks must be bound under the same parent directory as the existing disk (e.g., `/dev/yfs`).

- If [SCSI I/O Fencing](../../Database Administration/Cluster Management/IO Fencing/SCSI IO Fencing) is used, it is recommended to first run the [fenceScsiCheck](../../Database Administration/Cluster Management/IO Fencing/SCSI IO Fencing.md#fenceScsiCheck_usage) script to verify that the disks meet the requirements before creating the DiskGroup.



**CREATE DISKGROUP::=**

```ebnf
= CREATE DISKGROUP dgname [redundancy_clause] fg_clause {" " fg_clause} [attribute_clause].
```


**redundancy_clause::=**

```ebnf
= (EXTERNAL|NORMAL|HIGH) REDUNDANCY.
```

**fg_clause::=**

```ebnf
= [[REGULAR|QUORUM] FAILGROUP fgname] DISK disk_clause {"," disk_clause}.
```

`QUORUM` and `REGULAR` are only for syntax compatibility and have no practical meaning.

**disk_clause::=**

```ebnf
= "'" diskpath "'" [NAME disk_name] [SIZE size_clause] [FORCE|NOFORCE].
```

The size_clause is the same as the [size_clause](../../Development Guide/SQL Reference Manual/General SQL Syntax/size_clause) in the SQL syntax.


**attribute_clause::=**

```ebnf
= ATTRIBUTE "'"au_size"'" "=" ("'1M'" | "'4M'" | "'8M'" | "'16M'" | "'32M'").
```

### dgname

Specify the name of the DiskGroup to be created. This must be globally unique in YFS, cannot be omitted, and must conform with YashanDB's [object naming conventions](../../Development Guide/SQL Reference Manual/Basic SQL Elements/Identifiers).

### redundancy_clause

This statement is used to specify the redundancy level of the DiskGroup. It can be omitted, with the default being NORMAL.



The redundancy level is divided into External, Normal, and High, with increasing levels of high availability and reliability. If set to External, there is no data redundancy, and data reliability relies on external mechanisms, such as RAID.

The relationship between redundancy level and file replica count is shown in the table below.

|Redundancy | System DiskGroup<br/>Number of file replicas | Data DiskGroup<br/>Number of user data replicas | Data DiskGroup<br/>Number of YFS metadata replicas |
| ---------- | ------ | ----------- | --------------- |
| External   | 1      | 1           | 1               |
| Normal     | 3      | 2           | 2 ~ 3           |
| High       | 5      | 3           | 3 ~ 5           |


The redundancy level of each DiskGroup is independent and must be specified when creating the DiskGroup; it cannot be changed afterward.



### fg_clause

This statement is used to create FailureGroups. Each clause creates one FailureGroup, and multiple clauses are separated by spaces.

The number of FailureGroups is related to the DiskGroup's redundancy level — the number of FailureGroups must be greater than or equal to the number of replicas required by the redundancy level.

#### FAILGROUP fgname

This statement is used to specify the name of the FailureGroup, which must be unique within the DiskGroup and must comply with YashanDB's [object naming conventions](../../Development Guide/SQL Reference Manual/Basic SQL Elements/Identifiers).

If it is omitted, the names of the FailureGroups will be automatically generated by the system based on the DiskGroup name and the sequential number of the FailureGroups (starting from 0). For example, if the DiskGroup name is DG1, the automatically generated FailureGroup names will be DG1_0 and DG1_1.

#### disk_clause

This statement is used to specify the disk information under a FailureGroup. Multiple disks are separated by commas (`,`).

Disk configuration rules are as follows:


- The number of disks under each FailureGroup within the same DiskGroup must remain consistent.  

- The available capacity of all disks under each FailureGroup within the same DiskGroup must be identical.

- A disk can belong to only one FailureGroup and cannot be specified multiple times.

- Each FailureGroup should, as much as possible, achieve [fault isolation](../../Product Concepts/YAC Infrastructure/Yashan File System.md#FailureGroup).



##### diskpath

The disk path specification allows input paths up to a maximum length of 31 bytes.

>**Caution**:
>
> Please ensure that primary/standby node disk paths are consistent and have read/write privileges, otherwise this may cause the standby process to exit.

##### disk_name

Specify the disk name, which must be unique within the DiskGroup and conform to YashanDB's object naming conventions. This can be omitted; if omitted, the system will automatically generate a default name.

##### SIZE size_clause

Specify the disk capacity that can be managed and used by the DiskGroup. The specified value must not exceed the total capacity of the target disk. This can be omitted, with the default being the total capacity of the disk.

##### FORCE

This keyword is used to forcibly format the disk. For example, when YFS detects that the disk already contains a YFS, it will by default refuse to add the disk to prevent accidental data erasure. If `FORCE` is specified, the disk can be forcibly added, but any existing data will be formatted and lost.

### attribute_clause

This statement is used to specify the AU size of the disk space allocated by YFS when creating the DiskGroup; it is optional and defaults to an AU size of 1M.



The allocation unit granularity options include 1MB (default), 4MB, 8MB, 16MB, and 32MB. This attribute is specified when creating a DiskGroup and cannot be changed afterward.

Larger allocation unit granularities allow for larger files and better contiguous I/O performance, but they also consume more memory and waste some disk space. In practice, you should choose an appropriate allocation unit granularity based on your workload characteristics. Configuration recommendations are as follows:

- If the system primarily handles small files, a smaller AU size is recommended.

- If the system primarily handles large files, a larger AU size is recommended.

- Better performance can be obtained when AU size is greater than or equal to the vast majority of I/O sizes.



***Example*** for YAC Deployment

```shell
YFSCMD > exec CREATE DISKGROUP DG2 NORMAL REDUNDANCY 
DISK '/dev/DISK_NAME5' SIZE 700M 
FAILGROUP FG_1 DISK '/dev/DISK_NAME10' NAME disk4 SIZE 700M 
FAILGROUP FG_2 DISK '/dev/DISK_NAME4' SIZE 700M 
ATTRIBUTE 'au_size'='4M';

YFSCMD > exec DROP DISKGROUP DG2;

YFSCMD > exec CREATE DISKGROUP DG2 NORMAL REDUNDANCY 
FAILGROUP FG_1 DISK '/dev/DISK_NAME10' NAME disk4,'/dev/DISK_NAME12' 
FAILGROUP FG_2 DISK '/dev/DISK_NAME4','/dev/DISK_NAME11';
```

## ALTER DISKGROUP

This statement is used to modify the properties of an existing DiskGroup, including unmounting, mounting the DiskGroup, adding disks, deleting disks, renaming disks, etc.

**alter diskgroup::=**

```ebnf
= ALTER DISKGROUP dgname (DISMOUNT [FORCE] | MOUNT | add_disk_clause | drop_disk_clause | rename_disk_clause | offline_disk_clause |  online_disk_clause |  replace_disk_clause | rebalance_modify | resize_disk_clause).
```

In all clauses, `QUORUM` and `REGULAR` are only for syntax compatibility and have no practical meaning.

**[add_disk_clause](#add_disk_clause)::=**

```ebnf
= ADD fg_clause {" " fg_clause}.
```

**fg_clause::=**

```ebnf
= [[REGULAR|QUORUM] FAILGROUP fgname] DISK disk_clause {"," disk_clause}.
```

`QUORUM` and `REGULAR` are only for syntax compatibility and have no practical meaning.

**disk_clause::=**

```ebnf
= "'" diskpath "'" [NAME disk_name] [SIZE size_clause] [FORCE|NOFORCE].
```

The size_clause is the same as the [size_clause](../../Development Guide/SQL Reference Manual/General SQL Syntax/size_clause) in the SQL syntax.

**[drop_disk_clause](#drop_disk_clause)::=**

```ebnf
= DROP (([REGULAR|QUORUM] DISK disk_name [FORCE|NOFORCE] {"," disk_name [FORCE|NOFORCE]})|(DISKS IN [REGULAR|QUORUM] FAILGROUP failuregroup_name [FORCE|NOFORCE] {"," failuregroup_name [FORCE|NOFORCE]})).
```

**[rename_disk_clause](#rename_disk_clause)::=**

```ebnf
= RENAME  ((DISKS ALL) | (DISK old_disk_name TO new_disk_name {"," old_disk_name TO new_disk_name})). 
```

**[offline_disk_clause](#offline_disk_clause)::=**

```ebnf
= OFFLINE (([REGULAR|QUORUM] DISK disk_name {"," disk_name })|(DISKS IN [REGULAR|QUORUM] FAILGROUP failuregroup_name {"," failuregroup_name })).
```

**[online_disk_clause](#online_disk_clause)::=**

```ebnf
= ONLINE [REGULAR|QUORUM] DISK disk_name [POWER integer] [WAIT|NOWAIT].
```

**[replace_disk_clause](#replace_disk_clause)::=**

```ebnf
= REPLACE DISK disk_name WITH "'" diskpath "'" [FORCE|NOFORCE] [POWER integer] [WAIT|NOWAIT].
```

**[rebalance_modify](#rebalance_modify)::=**

```ebnf
= REBALANCE (MODIFY POWER [integer]|CANCEL).
```

**[resize_disk_clause](#resize_disk_clause)::=**

```ebnf
= RESIZE (([REGULAR|QUORUM] DISK disk_name [SIZE size_clause] {"," disk_name [SIZE size_clause] })| ALL [SIZE size_clause]).
```

### dgname

Specifies the name of an existing data DiskGroup. `SYSTEM` cannot be specified, meaning that ALTER DISKGROUP operations cannot be performed on the system DiskGroup.

### DISMOUNT|MOUNT

This statement is used to perform mount or unmount operations on the DiskGroup.

The usage rules for this operation are as follows:

- This operation cannot be performed on the system DiskGroup (named `SYSTEM`).

- During the mount operation, please ensure that the disk names are consistent and possess read/write privileges between primary/standby nodes; otherwise, the standby process may exit during the mount.

### FORCE

If files in the DiskGroup are already open and not yet closed, the DiskGroup cannot be DISMOUNTED; `FORCE` must be explicitly specified to force execution.

>**Caution**:
>
> Forcefully DISMOUNTING a DiskGroup may cause database anomalies and data loss, **please exercise caution with this operation**.

<span id="add_disk_clause" name="add_disk_clause"></span>

### add_disk_clause

This statement is used to add disks to the FailureGroup within the DiskGroup.

The prerequisites for adding disks (i.e., preparations for new disks) are as follows:



- The I/O fencing mode used by YAC has been confirmed. This can be viewed using the `ycsctl show fence` command.

- The storage device has been [prepared](../../Installation and Upgrade/Installation and Deployment/Pre-Installation Preparation/Preparing the Servers.md#Storage) according to requirements, and the hardware devices planned for each FailureGroup must meet the [fault isolation standard](../../Product Concepts/YAC Infrastructure/Yashan File System.md#FailureGroup).

- The storage device has been [configured](../../Installation and Upgrade/Installation and Deployment/Pre-Installation Preparation/Configuring the Storage Devices) according to requirements (e.g., partitioning, mounting, etc.), and the disks must be bound under the same parent directory as the existing disk (e.g., `/dev/yfs`).

- If [SCSI I/O Fencing](../../Database Administration/Cluster Management/IO Fencing/SCSI IO Fencing) is used, it is recommended to first run the [fenceScsiCheck](../../Database Administration/Cluster Management/IO Fencing/SCSI IO Fencing.md#fenceScsiCheck_usage) script to verify that the disks meet the requirements before creating the DiskGroup.



The usage rules for adding disks are as follows:



- This operation cannot be performed on the system DiskGroup (named `SYSTEM`).

- The target DiskGroup to be operated on has been mounted.


- If the number of disks in the target DiskGroup exactly meets the redundancy requirements (for example, the redundancy level is NORMAL and the number of disks is 4), and some disks are in an offline state, this operation cannot be performed at this time.

- If the specified FailureGroup name already exists, disks are added to the existing FailureGroup.

- If the specified FailureGroup name does not exist, or no FailureGroup name is specified, a new FailureGroup is created, and disks are added to it.

Other details are consistent with those described in [CREATE DISKGROUP](#CREATEDG).

<span id="drop_disk_clause" name="drop_disk_clause"></span>

### drop_disk_clause

This statement is used to delete one or more disks from the DiskGroup. It can also delete one or more FailureGroups from the DiskGroup.

The usage rules for this operation are as follows:



- This operation cannot be performed on the system DiskGroup (named `SYSTEM`).

- The target DiskGroup to be operated on has been mounted.


- Only **empty disk(s)** are allowed to be deleted.

- It is necessary to ensure that after deleting the disks, the number of remaining FailureGroups meets the redundancy requirements of the DiskGroup, and the number of disks in each remaining FailureGroup is the same. If the remaining number fails to meet the requirements, YFS will block the delete operation (the operation will not succeed).

>**Note**:
>
> The deleted disk will immediately be disengaged from its partner disk. This may cause some disks to lack available partner disks for creating data replicas, and the storage space of such disks cannot be used by YFS. At this time, sufficient disks can be added to the DiskGroup (the relationship of the disks can be queried through the [V\$YFS_DISK](../../Reference Manual/System Views/Dynamic Performance Views/V$YFS_DISK) view), and the system will automatically assign new partner disks for that type of disk after adding new disks.

#### DISK disk_name

Specify to delete several disks.

#### DISK IN FAILGROUP failuregroup_name

Specify to delete all disks in several FailureGroups.

<span id="rename_disk_clause" name="rename_disk_clause"></span>

### rename_disk_clause

This statement is used to rename the disks within a DiskGroup.

The usage rules for this operation are as follows:



- This operation cannot be performed on the system DiskGroup (named `SYSTEM`).

- The target DiskGroup to be operated on has been mounted.


- If the number of disks in the target DiskGroup exactly meets the redundancy requirements (for example, the redundancy level is NORMAL and the number of disks is 4), and some disks are in an offline state, this operation cannot be performed at this time.

#### DISK old_disk_name TO new_disk_name

Specify several disks to be renamed, and the new names need to be manually specified.

The disk naming specifications are as follows:

- The disk name can be up to 31 characters long.

- The new disk name must be unique within the DiskGroup.

#### ALL

Rename all disks. The new names will be specified by the system, in the format of `DGNAME_DISKID`.

<span id="offline_disk_clause" name="offline_disk_clause"></span>

### offline_disk_clause

This statement is used to take one or more disks within the DiskGroup offline. It may also take one or more FailureGroups within the DiskGroup offline.

The usage rules for this operation are as follows:



- This operation cannot be performed on the system DiskGroup (named `SYSTEM`).

- The target DiskGroup to be operated on has been mounted.


- When taking disk(s) offline, it is necessary to ensure that the number of remaining FailureGroups meets the redundancy requirements of the DiskGroup. If the remaining number fails to meet the requirements, YFS will block the offline operation (the operation will not succeed).

#### DISK disk_name

Specify to take several disks offline.

#### DISK IN FAILGROUP failuregroup_name

Specify to take all disks in several FailureGroups offline.

<span id="online_disk_clause" name="online_disk_clause"></span>

### online_disk_clause

This statement is used to re-online an offline disk in a DiskGroup.

The usage rules for this operation are as follows:





- This operation cannot be performed on the system DiskGroup (named `SYSTEM`).

- The target DiskGroup to be operated on has been mounted.


- A single operation can only re-online one offline disk.

- Each disk can have at most one pending repair-type operation task at a time, including: ONLINE, REPLACE.

- Each DiskGroup can have up to 64 repair-type operation tasks concurrently (either in progress or queued).



#### disk_name

Specify the name of the disk to be brought online.



#### POWER integer

Specify the data migration intensity for the current task. The valid range is [0,1024], where a higher value indicates greater intensity. The default is 1; 0 indicates pause, and 1024 indicates full-power execution.

This intensity can be modified online via the [rebalance_modify](#rebalance_modify) clause, but the modification will affect all tasks within the current DiskGroup simultaneously.

#### WAIT|NOWAIT

Whether to wait for the command execution result after running; default is `NOWAIT`.

You can view the status and detailed information of the task using the `show job` command.



<span id="replace_disk_clause" name="replace_disk_clause"></span>

### replace_disk_clause

This statement is used to add a new disk to replace an offline disk in a DiskGroup.

The prerequisites for disk replacement (i.e., preparations for the new disk) are as follows:



- The I/O fencing mode used by YAC has been confirmed. This can be viewed using the `ycsctl show fence` command.

- The storage device has been [prepared](../../Installation and Upgrade/Installation and Deployment/Pre-Installation Preparation/Preparing the Servers.md#Storage) according to requirements, and the hardware devices planned for each FailureGroup must meet the [fault isolation standard](../../Product Concepts/YAC Infrastructure/Yashan File System.md#FailureGroup).

- The storage device has been [configured](../../Installation and Upgrade/Installation and Deployment/Pre-Installation Preparation/Configuring the Storage Devices) according to requirements (e.g., partitioning, mounting, etc.), and the disks must be bound under the same parent directory as the existing disk (e.g., `/dev/yfs`).

- If [SCSI I/O Fencing](../../Database Administration/Cluster Management/IO Fencing/SCSI IO Fencing) is used, it is recommended to first run the [fenceScsiCheck](../../Database Administration/Cluster Management/IO Fencing/SCSI IO Fencing.md#fenceScsiCheck_usage) script to verify that the disks meet the requirements before creating the DiskGroup.



The usage rules for this operation are as follows:





- This operation cannot be performed on the system DiskGroup (named `SYSTEM`).

- The target DiskGroup to be operated on has been mounted.


- A single operation can only replace one offline disk.

- The new disk cannot be one that is already part of any DiskGroup.

- Each disk can have at most one pending repair-type operation task at a time, including: ONLINE, REPLACE.

- Each DiskGroup can have up to 64 repair-type operation tasks concurrently (either in progress or queued).

> **Note**:
> 
> - The essence of a disk replacement operation is to update the path of a disk in a DiskGroup and then re-online the disk. If a replacement task is interrupted (e.g., manually canceled), the disk path may have changed, and YFS will not automatically roll back this change. Manual intervention is required to re-initiate the replacement task to restore the original path.
>
> - When replacing a disk, if the disk path of the new disk is mistakenly specified as the original path of the disk named `disk_name`, YFS will not report an error or block the operation. In this case, the operation degrades to simply re-onlineing the target disk. 



#### disk_name

Specifies the name of the disk to be replaced.

#### diskpath

Specifies the disk path of the new disk.

#### FORCE|NOFORCE

Whether to forcibly format the disk. The meaning and effect are the same as the FORCE|NOFORCE keywords in CREATE DISKGROUP.



#### POWER integer

Specify the data migration intensity for the current task. The valid range is [0,1024], where a higher value indicates greater intensity. The default is 1; 0 indicates pause, and 1024 indicates full-power execution.

This intensity can be modified online via the [rebalance_modify](#rebalance_modify) clause, but the modification will affect all tasks within the current DiskGroup simultaneously.

#### WAIT|NOWAIT

Whether to wait for the command execution result after running; default is `NOWAIT`.

You can view the status and detailed information of the task using the `show job` command.



<span id="rebalance_modify" name="rebalance_modify"></span>

### rebalance_modify

This statement is used to manually adjust the load of repair-type operation tasks, including adjusting the data migration intensity or canceling all repair-type operation tasks.

This operation affects all repair-type operation tasks that are currently executing or queued in the current DiskGroup.

#### POWER integer

Specifies the data migration intensity for the current DiskGroup. The valid range is [0,1024], where a higher value indicates greater intensity. The default is 1; 0 indicates pause, and 1024 indicates full-power execution.

#### CANCEL

Cancels all repair-type operation tasks in the current DiskGroup.

<span id="resize_disk_clause" name="resize_disk_clause"></span>

### resize_disk_clause

This statement is used to readjust the capacity of one or more disks in the DiskGroup.

The usage rules for this operation are as follows:



- This operation cannot be performed on the system DiskGroup (named `SYSTEM`).

- The target DiskGroup to be operated on has been mounted.


- This operation can only be performed on disks in the normal status (status = NORMAL).

- The new disk capacity requirements vary depending on the redundancy level (you can view the DiskGroup redundancy information redundancy through the [show diskgroup command](./Status Inspection Commands)):

    - For DiskGroups with an EXTERNAL redundancy level: Disks can be adjusted to different capacities.

    - For DiskGroups with a NORMAL or HIGH redundancy level: The capacity of all disks must always be consistent.

> **Note**:
>
> If the task of readjusting the capacity is interrupted due to factors such as malfunctions, the capacity adjustment of only some disks may be completed. Subsequently, a new round of adjustment tasks can be initiated to adjust the capacity of the remaining disks. However, for DiskGroups with a redundancy level of NORMAL or HIGH, during the period when the disk capacities are inconsistent, their available capacity depends on the disk with the smallest capacity in the DiskGroup.

#### DISK disk_name

Specify the name of the disk whose capacity needs to be adjusted.

#### ALL

This keyword indicates that the capacity of all disks in the current DiskGroup will be adjusted.

When adjusting the capacity of disks in a DiskGroup with a redundancy level of NORMAL or HIGH, it is recommended to use the `ALL` keyword to specify all disks for the operation.

#### SIZE size_clause

Specify the new capacity that can be managed and used by the DiskGroup. This can be omitted, and the default value is the actual total capacity of the disk.

If the specified value is not an integer multiple of the au_size of the current DiskGroup, it will be rounded down. The valid value range of the new capacity is as follows:

- Upper limit: MIN(actual total capacity of the disk, maximum capacity of the current disk that can be used by YFS)

- Lower limit: Not lower than the highest offset of the currently used space on the disk.

If the configured capacity (including the default value) does not meet the requirements of the valid value range, the system will report an error, and the capacity configuration will not take effect. The error message will prompt the optional value range. At this point, you can re - execute the command and specify an appropriate value.

***Example*** for YAC Deployment

```shell
-- Unmount DiskGroup
YFSCMD > exec ALTER DISKGROUP DG2 DISMOUNT;
-- Mount DiskGroup
YFSCMD > exec ALTER DISKGROUP DG2 MOUNT;
-- Add disks
YFSCMD > exec ALTER DISKGROUP DG2 ADD FAILGROUP FG_3 DISK '/dev/DISK_NAME13' NAME DISK13,'/dev/DISK_NAME14' NAME DISK14 FAILGROUP FG_4 DISK '/dev/DISK_NAME15' NAME DISK15,'/dev/DISK_NAME16' NAME DISK16;
-- Delete all disks from FailureGroup
YFSCMD > exec ALTER DISKGROUP DG2 DROP DISKS IN FAILGROUP FG_3, FG_4;
-- Delete specified disks
YFSCMD > exec ALTER DISKGROUP DG2 DROP DISK DISK13, DISK14;
-- Rename specified disks
YFSCMD > exec ALTER DISKGROUP DG2 RENAME DISK DISK13 to DISK13NEW, DISK14 to DISK14NEW;
YFSCMD > exec ALTER DISKGROUP DG2 RENAME DISKS ALL;
-- Take disks offline
YFSCMD > exec ALTER DISKGROUP DG2 OFFLINE DISK DISK13, DISK14;
YFSCMD > exec ALTER DISKGROUP DG2 OFFLINE DISKS IN FAILGROUP FG_3, FG_4;
-- Take the specified disk online
YFSCMD > exec ALTER DISKGROUP DG2 ONLINE DISK DISK13 POWER 10 WAIT;
-- Replace the specified disk
YFSCMD > exec ALTER DISKGROUP DG2 REPLACE DISK DISK14 WITH '/dev/disk14' POWER 10 WAIT;
-- Adjust the data migration intensity
YFSCMD > exec ALTER DISKGROUP DG2 REBALANCE MODIFY POWER 8;
-- Cancel all repair tasks for the DiskGroup
YFSCMD > exec ALTER DISKGROUP DG2 REBALANCE CANCEL;
-- Readjust the capacity of all disks in DG1
YFSCMD > exec ALTER DISKGROUP DG1 RESIZE ALL;
-- Readjust the capacity of some disks in DG1
YFSCMD > exec ALTER DISKGROUP DG1 RESIZE DISK DISK1 SIZE 300G, DISK2 SIZE 200G;
```

## DROP DISKGROUP

This statement is used to delete a DiskGroup.

The DiskGroup to be deleted must be in the MOUNT state; otherwise, the deletion will fail, and the state of the DiskGroup can be changed using the ALTER DISKGROUP statement.

**drop diskgroup::=**

```ebnf
= DROP DISKGROUP dgname [INCLUDING CONTENTS] [FORCE].
```

### dgname

Specifies the name of an existing DG.

### INCLUDING CONTENTS

If there are files or directories in the DiskGroup, `INCLUDING CONTENTS` must be explicitly specified to force deletion, otherwise, the deletion will fail.

### FORCE

If files in the DiskGroup are open but not closed, the DiskGroup cannot be dropped; `FORCE` must be explicitly specified to force execution. Note that forcefully dropping a DiskGroup may cause database anomalies; please exercise caution with this operation.

***Example*** for YAC Deployment

```shell
YFSCMD > exec DROP DISKGROUP DG2;

YFSCMD > exec DROP DISKGROUP DG2 INCLUDING CONTENTS;
```
