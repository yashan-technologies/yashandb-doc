The RESTORE command can be used to recover from backup sets generated by *yasrman*, including full database recovery, recovery of a specific tablespace, and recovery of archive logs.

In Standalone/YAC/Distributed Cluster Deployment, when performing a RESTORE operation, the system will first automatically conduct an environmental pre-check, which includes checking the accessibility of the recovery file path and whether there is sufficient disk space at the target location. If the checks are passed, the RESTORE will proceed; if the checks fail, the operation will exit immediately.

## Common Recovery Attributes

<span id="restoreCommonSpecifier" name="restoreCommonSpecifier"></span>
**restoreCommonSpecifier::=**

```ebnf
= ((DECRYPTION password)|
(PARALLELISM integer)|
(PARAMS xbsa_parameter)|(DEST (SERVER|CLIENT))) 
{ " " ((DECRYPTION password)|
(PARALLELISM integer)|
(PARAMS xbsa_parameter)|(DEST (SERVER|CLIENT)))}.
```

### DECRYPTION

This statement is used to specify decryption when recovering a backup set, requiring a decryption password to be specified simultaneously.

### PARALLELISM

This statement is used to specify the degree of parallelism for multi-threaded recovery, with a range of [1,16]. If omitted, the default is 2.

### PARAMS

This statement is used for recovering streaming backup sets and specifies the configuration parameters for the XBSA interface. When using this statement, the storage location of the backup set must be specified as client (DEST CLIENT).

This statement cannot be used in ISC Distributed Cluster Deployment.

The format is as follows:
'XBSA_LIBRARY=xbsa_library_path, TOKEN=token_value, ENV=(key1=val1,key2=val2,...)'

- xbsa_library_path: The absolute path of the XBSA dynamic link library, currently only supporting Linux dynamic libraries.
- token_value: The token parameter for the BSAInit interface.
- keyX, valX: The env parameters for the BSAInit interface, with the total maximum length of all key-value pairs being less than 4096.

***Example*** for Standalone/YAC/Distributed Cluster Deployment

```shell
$ yasrman sys/********@192.168.1.2:1688 -c "restore database from tag 'xbsa_full_1' dest client params 'XBSA_LIBRARY=/home/yashan/lib/libxbsa.so, TOKEN=157257815837, ENV=(BSA_SERVICE_HOST=192.168.1.1:1601,BSA_BACKUP_UUID=yashan1234561)'" -D /home/yashan/catalog
$ yasrman sys/********@192.168.1.2:1688 -c "restore database from tag 'xbsa_incr_0' dest client params 'XBSA_LIBRARY=/home/yashan/lib/libxbsa.so, TOKEN=157257815837, ENV=(BSA_SERVICE_HOST=192.168.1.1:1601,BSA_BACKUP_UUID=yashan1234562)'" -D /home/yashan/catalog

$ yasrman sys/********@192.168.1.2:1688 -c "restore archivelog all from tag 'arch_all2' dest client params 'XBSA_LIBRARY=/home/yashan/lib/libxbsa.so, TOKEN=157257815837, ENV=(BSA_SERVICE_HOST=192.168.1.1:1601,BSA_BACKUP_UUID=yashan1234562)'" -D /home/yashan/catalog
```

### DEST

This is for syntax compatibility only, but it is recommended to keep the DEST consistent with what was specified during backup, as the actual recovery will flexibly restore according to the CATALOG recorded location.

## Full Database Recovery

Full database recovery for Standalone/YAC/Distributed Cluster Deployment:

```ebnf
= RESTORE dbObjectSpecifier ([FROM TAG tag_name|DBID database_id] (UNTIL ((SCN integer)|(TIME time_string)) [IGNORE PITR TARGET ERROR])|FROM TAG tag_name)
[SKIP VALIDATE][OVERWRITE] [MAPPED FILE 'mapfile_name']
[restoreCommonSpecifier].
```
**dbObjectSpecifier::=**

```ebnf
= DATABASE [ROOT]|PLUGGABLE DATABASE (pdb_name {"," pdb_name}).
```

Full database recovery in ISC Distributed Cluster Deployment:

```ebnf
= RESTORE CLUSTER FROM TAG tag_name [MAPPED FILE 'mapfile_name'] [restoreCommonSpecifier].
```

Using this command executes operations similar to the [RESTORE DATABASE](../../../Development Guide/SQL Reference Manual/SQL Statements/RESTORE DATABASE) statement, but restoring a backup set with this command will start the current node to open state, and in ISC Distributed Cluster Deployment, it will also build a standby database (if exists).

Before executing this command for recovery, it is mandatory to ensure:

- The current database version must be completely identical to the version when the backup file set was created.
- On all nodes, the data file directory, archive log file directory, and bucket directory of the instance must be cleared and started in NOMOUNT state.

    In ISC Distributed Cluster Deployment, the command [yasboot](../../yasboot/Introduction to yasboot Command/yasboot cluster) cluster clean **--restore** can be executed to ensure the cluster environment meets this requirement. 

	> **Warn**:
	>
    > Please ensure to execute cluster clean **--restore**; a clean command without the --restore option will completely clear the DATA directory on the node and cannot be restored. Additionally, if the default path of the backup set was used in the BACKUP CLUSTER command, the backup set located in the DATA directory will also be cleared.

- In YAC/Distributed Cluster Deployment, the target node connected during recovery must be a MASTER ROLE node (can be determined by querying the INSTANCE_ROLE field of view V$INSTANCE), otherwise, the database cannot be recovered.


### dbObjectSpecifier|CLUSTER

Specify backup objects via keywords:

| Applicable Scenario         | Keyword      | Functional Description     |
|-----------------|-------------|-------------------------|
| Non-CDB | DATABASE  |Recovers the entire database in Standalone Deployment or YAC Deployment. |
| Non-CDB | CLUSTER |Recovers the entire ISC Distributed Cluster Deployment database. |
| CDB | DATABASE |Recovers the entire database or a single PDB based on connection:<br/>* Connected to the CDB root: Recovers the CDB root, PDB seed, and all PDBs. If PITR is performed by specifying a database ID (`RESTORE DATABASE DBID id UNTIL TIME/SCN`), it is equivalent to performing PITR on the CDB root alone — that is, only the CDB root is recovered to the target time.<br/>* Connected to a PDB: Recovers that PDB — PITR recovery is not supported. |
| CDB | DATABASE ROOT |Recovers the CDB root. Must connect to the CDB root to execute.  |
| CDB | PLUGGABLE DATABASE |Recovers  the specified PDB — must be executed by a user with recovery and connection privileges for the specified PDB, connected to the CDB root. <br />PITR cannot be performed by specifying a database ID (`RESTORE PLUGGABLE DATABASE DBID id UNTIL TIME/SCN`). |

### FROM TAG

Specifies the backup set used for full database recovery, which must be a full database backup set existing in the catalog.

### PITR Recovery

#### FROM TAG

Specifies the backup set used for PITR recovery, which must be a full database backup set existing in the catalog. When omitted, *yasrman* will automatically obtain a suitable full database backup set from the catalog, scan the backup sets in the order of their generation until a suitable full database backup set is found, and then start to perform the recovery.

During the recovery process, if the archive logs in the target full database backup set are insufficient to support the recovery scope of this operation, *yasrman* will scan all the archive log backup sets recorded in the catalog in the order of their generation, obtain the appropriate archive logs, and perform the recovery.

#### DBID

Specifies the database ID for PITR recovery. The ID value does not change after database creation and is used to uniquely identify the database. It can be obtained from the DATABASE_ID field of the V$DATABASE view.

*yasrman* will search for and recover the backup set of the specified database ID from the catalog.

When restoring a CDB by specifying database ID, will always restore only the container on which the current operation is performed.

#### UNTIL

The UNTIL option is used for PITR recovery. When using PITR recovery, a database backup set can be specified or the DBID can be used to automatically search for the most recent database backup set. If neither TAG nor DBID is specified, any backup set closest to the target point in time will be searched.

When executing PITR recovery, the database backup set is first restored, followed by an attempt to restore the archive files backup within the target range, and finally an attempt to reuse the locally archive log files of the database to restore to the target point as much as possible. Therefore, if all archive files within the target point are included in the *yasrman* backup or all exist locally in the database, restoration to the target point is possible.

In a CDB, when performing PITR recovery for the entire CDB, the operation is divided into two phases:

- Phase 1: First, perform PITR recovery on the CDB root. If recovery succeeds, proceed to Phase 2; otherwise, the entire recovery operation is interrupted.

- Phase 2: Concurrently recover the PDB seed and all PDBs. Each database object's recovery process runs independently and does not interfere with others.

	If the specified SCN/TIME is too large, some PDBs may fail to recover to the target replay point — the recovery process for those PDBs will be interrupted (without affecting other PDBs). In such cases, the target PDBs will only be restored to the MOUNT state. You must manually start them to the OPEN state and reset the log sequence (e.g., log in to the CDB root and execute the [ALTER PLUGGABLE DATABASE](../../../Development Guide/SQL Reference Manual/SQL Statements/ALTER PLUGGABLE DATABASE) pdbname_list OPEN RESETLOGS statement). You can automatically ignore error messages for such PDBs and automatically execute OPEN RESETLOGS for them by specifying the IGNORE PITR TARGET ERROR keyword — no additional manual intervention is required.

In a CDB, performing PITR recovery for multiple PDBs (using `RESTORE PLUGGABLE DATABASE pdbname_list`) is identical to Phase 2 above.

PITR is not applicable in ISC Distributed Cluster Deployment.

#### UNTIL TIME

This statement is used to restore the database to the specified time point, i.e., PITR recovery. The time_string must be a string formatted as a date and must match the format defined by the TIMESTAMP_FORMAT parameter.

The specified time point must be after the generation time of the backup set. The final restored time may be smaller than the target, but the error will be within 1 second.

#### UNTIL SCN

This statement is used to restore the database to the specified SCN number, i.e., PITR recovery. The specified SCN number must be greater than the SCN number recorded in the backup set.

<span id="IGNORE" name="IGNORE"></span>

#### IGNORE PITR TARGET ERROR

This statement is used to ignore errors that occur when the SCN/TIME is too large to replay to the target point.

When this keyword is specified, the system will continue to start the target database from the MOUNT stage to OPEN and reset the log sequence (i.e., execute OPEN RESETLOGS).

***Example*** for Standalone/YAC/Distributed Cluster Deployment

```shell
# Specify SCN and database backup set
$ yasrman sys/********@192.168.1.2:1688 -c "restore database from tag 'full_1' until time '2023-11-13'" -D /home/yashan/catalog

# Specify SCN and database ID
$ yasrman sys/********@192.168.1.2:1688 -c "restore database dbid 12573483 until time '2023-11-13 18:55:00'" -D /home/yashan/catalog

# Specify only SCN 
$ yasrman sys/********@192.168.1.2:1688 -c "restore database until time '2023-11-13 18:54:32:657892'" -D /home/yashan/catalog

# Specify SCN
$ yasrman sys/********@192.168.1.2:1688 -c "restore database from tag 'full_1' until scn 499833430256541696" -D /home/yashan/catalog

$ yasrman sys/********@192.168.1.2:1688 -c "restore database until scn 499833430256541696" -D /home/yashan/catalog
```

***Example*** for Standalone/YAC/Distributed Cluster Deployment (CDB)

```shell
# Connect to the CDB root and restore all PDBs
$ yasrman sys/********@192.168.1.2:1688 -c "restore database from tag 'full_1'" -D /home/yashan/catalog

# Connect to the CDB root and restore the specified PDB
$ yasrman sys/********@192.168.1.2:1688 -c "restore pluggable database PDB1, PDB2 from tag 'full_1'" -D /home/yashan/catalog

# Connect to the CDB root and restore the specified PDB to a specific point in time
$ yasrman sys/********@192.168.1.2:1688 -c "restore pluggable database PDB1 until time '2026-01-09 14:20:54.336905' ignore pitr target error" -D /home/yashan/catalog

# Connect to the target PDB and restore a single PDB
$ yasrman sys/********@192.168.1.2:1688/pdb1 -c "restore database from tag 'full_1'" -D /home/yashan/catalog
```

> **Note**: 
>
> - The minimum time point ensures that the database is restored to a consistent state, corresponding to the point in time when the data files were backed up and the archive log backup began, slightly less than the backup completion time.
> - If there are not enough archive log files or if the specified time point (or SCN) is too late, the database may not reach the designated point even after applying is complete. Users can check the actual apply progress using v$database's current_scn. If available archive log file copies exist, they can be registered for archiving and the restore operation can be re-executed. If no extra archives are available, the current time point is the only option, and the resetlogs operation should be proceeded.
> - When multiple databases are backed up in the same catalog, it is recommended to use DBID to distinguish different databases during PITR.

### SKIP VALIDATE

This keyword is used to skip pre-checks during restore.

The pre-check items include whether the target path is reachable, the disk space capacity, and whether there are files with the same name in the path.

### OVERWRITE

This keyword is used to overwrite files with the same name, but REDO files and archive files may be used for PITR recovery and therefore will not be overwritten. If such files with the same name exist, they must be cleaned up manually.

### MAPPED FILE

When restoring a database, by default, all files are restored to their original paths. If you need to adjust the storage location of data files or REDO log files, you can first prepare a path mapping file according to your planning, and then perform the restore operation based on this mapping file, at which point the corresponding data files or REDO log files will be stored at the new path.

This keyword is used to specify the path mapping file.

> **Note**: 
> 
> - If a path conversion file is specified during RESTORE, the path conversion parameters in the original configuration file yasdb.ini will become ineffective. After the RESTORE operation is completed, if a standby database needs to be established, the path conversion parameters in the yasdb.ini file must be reconfigured, otherwise, it may lead to abnormal primary/standby data files.
>
> - In ISC Distributed Cluster Deployment, if the path conversion file is specified, and the target node of the RESTORE has a standby node, the path primary/standby path conversion parameters for that node must be configured, otherwise, the RESTORE operation may fail.

### restoreCommonSpecifier

Decryption, parallelism, and other common recovery attributes, please refer to [Common Recovery Attributes](#restoreCommonSpecifier).

***Example*** for Standalone/YAC/Distributed Cluster Deployment

```shell
$ yasrman sys/********@192.168.1.2:1688 -c "restore database from tag 'full_1'" -D /home/yashan/catalog
```

***Example*** for ISC Distributed Cluster Deployment

```shell
$ yasrman sys/********@192.168.1.2:1688 -c "restore cluster from tag 'full_1'" -D /home/yashan/catalog
```

## Tablespace Recovery

```ebnf
= RESTORE TABLESPACE (TBS_NAME {"," TBS_NAME}) FROM TAG tag_name [CLEAN FILE] [SKIP VALIDATE] [OVERWRITE] 
[restoreCommonSpecifier].
```

Tablespace RESTORE operations are only applicable to Standalone Deployment.

Before executing this command for recovery, it is essential to ensure:

- The database must be in MOUNT or OPEN state.
- The target tablespace must be in OFFLINE state, with all data files under that tablespace in OFFLINE or RECOVER status.

After the tablespace RESTORE is completed, a [RECOVER](RECOVER) operation must also be executed for consistent recovery of the tablespace object files.

### TABLESPACE

This keyword is used to indicate recovery operations for the tablespace files.

TBS_NAME indicates the target tablespace for recovery.

### CLEAN FILE

Using this command will clean up any residual original tablespace data files during the recovery process. If this option is not specified in the recovery command and a database file with the same name exists, the recovery will fail.

### SKIP VALIDATE

This keyword is used to skip pre-checks during restore.

The pre-check items include whether the target path is reachable, the disk space capacity, and whether there are files with the same name in the path.

### OVERWRITE

This keyword is used to overwrite files with the same name, but REDO files and archive files may be used for PITR recovery and therefore will not be overwritten. If such files with the same name exist, they must be cleaned up manually.

### restoreCommonSpecifier

Decryption, parallelism, and other common recovery attributes, please refer to [Common Recovery Attributes](#restoreCommonSpecifier).

***Example*** for Standalone Deployment

```shell
$ yasrman sys/********@192.168.1.2:1688 -c "restore tablespace spc_test from tag 'spc_test_bak' " -D /home/yashan/catalog
```

## Archive Log Files Recovery

```ebnf
= RESTORE ARCHIVELOG [ROOT] archivelogRangeSpecifier [FROM TAG tag_name] [SKIP VALIDATE][OVERWRITE] [restoreCommonSpecifier].
```

### RESTORE ARCHIVELOG

This keyword is used to indicate recovery of database archive log files.

### RESTORE ARCHIVELOG ROOT

In a CDB, specifying this keyword indicates that the archive log file recovery operation is performed at the CDB root.

### archivelogRangeSpecifier

This is used to specify the range of archive log files to be restored, following the same methods and rules as described in the [RESTORE ARCHIVELOG](../../../Development Guide/SQL Reference Manual/SQL Statements/RESTORE ARCHIVELOG) statement.

### FROM TAG

Specifies the backup set used for archive log recovery, which must be an archive log backup set or full database backup set existing in the catalog.


When the recovery range is specified as ALL, the backup set must be specified via FROM TAG.


In other scenarios, FROM TAG can be omitted. When omitted, *yasrman* will automatically obtain a suitable archive log backup set or full database backup set from the catalog. It will scan these backup sets in the order of their generation until it finds a backup set that contains the archive logs within the recovery range, and then then proceed with the recovery.

### SKIP VALIDATE

This keyword is used to skip pre-checks during restore.

The pre-check items include whether the target path is reachable, the disk space capacity, and whether there are files with the same name in the path.

### OVERWRITE

This keyword is used to overwrite files with the same name, but REDO files and archive files may be used for PITR recovery and therefore will not be overwritten. If such files with the same name exist, they must be cleaned up manually.

### restoreCommonSpecifier

Decryption, parallelism, and other common recovery attributes, please refer to [Common Recovery Attributes](#restoreCommonSpecifier).

***Example*** for Standalone/YAC/Distributed Cluster Deployment

```shell
$ yasrman sys/********@192.168.1.2:1688 -c "restore archivelog all from tag 'arch_bak002'" -D /home/yashan/catalog

$ yasrman sys/********@192.168.1.2:1688 -c "restore archivelog sequence between 10 and 20" -D /home/yashan/catalog
```
