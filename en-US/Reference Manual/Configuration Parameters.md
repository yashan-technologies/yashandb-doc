YashanDB opens system operation configuration capabilities by adjusting configuration parameters. All configuration parameters are set to default values upon product installation, and can be adjusted according to business, performance, and other requirements during subsequent actual usage. For specific operations, please refer to [Parameter Configuration](../Database Administration/Instance Management/Database Parameter Configuration).

**Parameter Attributes**

- Immediate Effect on Modification: Indicates whether the parameter can take effect in real time when set by the ALTER SYSTEM SET command (real-time effect means scope=memory).

- Session-Level Parameter: Indicates whether the parameter can be set as session-level effective through the ALTER SESSION SET command.

- Read-Only Parameter: Modification is not supported after the database is created.

- Whether multi-instance consistency is required: In YAC/Distributed Cluster Deployment, certain parameters require all instances to maintain identical parameter values. This attribute can be verified via the CLUSTER_CONSISTENT field in the V$PARAMETER view.

    > **Note**:
    >
    > When modifying such parameters and specifying immediate effect, the database automatically synchronizes the change to all instances to ensure global consistency.
    > 
    >
    > If you intend to specify the change to take effect after a restart (scope=spfile) or require a restart to take effect, you must restart the entire cluster to ensure that the corresponding configuration is applied consistently across all instances; otherwise, inconsistent configurations across instances may affect normal startup.

- Action Scope: When YashanDB is installed as a CDB, parameters are divided into CDB global parameters, CDB private parameters, or common parameters through the action scope attribute:

	- CDB Global Parameter: These parameters represent CDB-level configurations that can only be modified by connecting to the CDB root.

	- CDB Private Parameter: These parameters are configured independently in each container (the CDB root, PDB). They can only be customized by directly connecting to the target container, and they only take effect for themselves.

	- Common Parameter: These parameters can be customized in each container or inherit the configuration from the CDB root. Their effective scope depends on the execution instance and the specified container attribute.

- Introduced Version: Indicates the version from which the parameter was introduced.

- Obsolete Version: Indicates the version from which the parameter is no longer recommended for use. It is kept for version compatibility and will be deprecated after several versions. After configuring in the system, operational log alerts will occur, but it does not affect startup.

### ARCH_CLEAN_IGNORE_MODE

*   Parameter Type: String  

*   Default Value: NONE  

*   Value Range/Format: [NONE|BACKUP|STANDBY|BOTH]

*   Parameter Description: Specifies the ignore mode when cleaning archived files. Ignoring backup means that archived files will be cleaned regardless of whether they have been backed up. Ignoring standby database means that in primary/standby deployment, archived files will be cleaned regardless of whether they have been obtained by all standby databases. If the ARCHIVELOG_DELETION_POLICY archive cleaning strategy configuration is not DEFAULT, the current configuration parameter becomes invalid, and the cleaning strategy will depend on ARCHIVELOG_DELETION_POLICY.

    *   NONE means that cleaning archived files does not ignore backup and standby databases.

    *   BACKUP means that cleaning archived files ignores backups. If backups are not needed, please set this parameter to BACKUP.

    *   STANDBY means that in primary/standby deployment, cleaning archived files ignores standby databases. If waiting for the standby database is not needed, please set this parameter to STANDBY, but it may cause the standby database to fall behind and enter a need repair state.
    
    *   BOTH means that cleaning archived files ignores both backups and standby databases. If neither backups nor standby databases is needed, please set this parameter to BOTH.  

*   Immediate Effect on Modification: Yes

*   Session-Level Parameter: No

*   Read-Only Parameter: No

*   Whether Multi-Instance Consistency Is Required: Yes

*   Action Scope: Common Parameter

*   Introduced Version: v22.1

### ARCH_CLEAN_LOWER_THRESHOLD

*   Parameter Type: Numeric  

*   Default Value: 12G  

*   Value Range/Format: [0,32T]  

*   Parameter Description: Specifies the stopping condition for the automatic cleaning of archived files functionality. Once this functionality is triggered, it will automatically delete the current database's archive log files until the total size of the existing archive log files and the next archive log files to be generated does not exceed this value. This value cannot be greater than [ARCH_CLEAN_UPPER_THRESHOLD](#ARCH_CLEAN_UPPER_THRESHOLD). Setting it to 0 means that all cleanable archive log files will be cleaned.

*   Immediate Effect on Modification: Yes

*   Session-Level Parameter: No

*   Read-Only Parameter: No

*   Whether Multi-Instance Consistency Is Required: Yes

*   Action Scope: Common Parameter

*   Introduced Version: v22.1

### ARCH_CLEAN_UPPER_THRESHOLD

*   Parameter Type: Numeric  

*   Default Value: 16G 

*   Value Range/Format: [0,32T]  

*   Parameter Description: Specifies the maximum space allowed to be occupied by all archive log files generated by the current database. Before archiving, the system will calculate whether the total size of the upcoming archive log files and all existing archive log files exceeds this value. If so, it will first trigger the automatic cleaning of the archived files functionality, and only after cleaning is completed will it generate new archive log files. This value serves only as the trigger condition for the automatic cleaning of archived files; even if the total size of archive log files exceeds this value, it does not affect the normal operation of transactions. This value cannot be less than [ARCH_CLEAN_LOWER_THRESHOLD](#ARCH_CLEAN_LOWER_THRESHOLD). Setting it to 0 means that automatic cleaning is disabled and archive log files will not be automatically cleaned.

*   Immediate Effect on Modification: Yes

*   Session-Level Parameter: No

*   Read-Only Parameter: No

*   Whether Multi-Instance Consistency Is Required: Yes

*   Action Scope: Common Parameter

*   Introduced Version: v22.1

### ARCHIVE_DEST_1 ~ 32

*   Parameter Type: String

*   Default Value: ''  

*   Value Range/Format: ARCHIVE_DEST_XXX='SERVICE=IP:port VALID_FOR=validity_range DB_UNIQUE_NAME= standby_database_name NODE_ID=node_no AFFIRM=YES/NO NET_TIMEOUT=timeouts'

*   Parameter Description: Specifies the configuration for the standby database with the following parameters:

    *   SERVICE: Defines the IP and port of the standby database. In a YAC, the IP and port of all instances of the standby database must be provided, separated by commas, with no spaces.

    *   VALID_FOR: Defines the validity range for the standby database, default is PRIMARY_ROLE, indicating effective when the current instance is the primary database. STANDBY_ROLE indicates effective when the current instance is the standby database, and ALL_ROLES indicates effective at all times.

    *   DB_UNIQUE_NAME: Defines the name of the standby database. If not configured, the default value will be standby+id. This value must be unique and cannot be duplicated with other standby databases, case insensitive.

    *   NODE_ID: Node number under leader election mode, formatted as group-node:endpoint. This value must be unique and cannot be duplicated with other standby databases.

    *   AFFIRM: Under maximize availability mode, indicates whether the standby database will reply ACK after flushing logs to disk. Setting it to NO improves performance but may lead to data loss, with the default being YES.

    *   NET_TIMEOUT: In maximize availability mode, specifies the timeout duration for waiting for the standby database to recover ACK after transaction submission, with a value range of [3,1000] in seconds, with the default being 30 seconds. When the primary database detects a network disconnection from the standby database, if the transaction submission wait for the standby database ACK exceeds this time, the standby database will be set to asynchronous mode, and subsequent transactions will no longer wait for this standby database. If the primary database detects a network disconnection (e.g. heartbeat timeout or network transmission error), it will immediately set the standby database to asynchronous mode, and subsequent transactions will no longer wait for this standby database. For heartbeat timeout parameters, please refer to [HA_ELECTION_TIMEOUT](#HA_ELECTION_TIMEOUT).

    *   DISABLE_ELECTION: Marks whether the current link participates in the leader election voting and election nodes. Configurable values are TRUE and FALSE, with a default value of FALSE. If specified as TRUE, it indicates that it does not participate in leader election voting and election, only serves as a data synchronization link between primary and standby databases, and the election switch HA_ELECTION_ENABLE of the target standby must be off; nodes pointed to in the QUORUM_SYNC_STANDBYS configuration cannot include this link, and the ANY configuration specified in QUORUM_SYNC_STANDBYS must also not contain this node.

    Examples of configuring multiple standby database links:

    *   ARCHIVE_DEST_1='SERVICE=127.0.0.1:2801', indicates the address of standby database 1, with standby database type as normal backup, using the default name standby1.

    *   ARCHIVE_DEST_2='SERVICE=127.0.0.1:2802 VALID_FOR=STANDBY_ROLE NODE_ID=1-1:1', indicates the address of standby database 2, with standby database type as cascade standby, using the default name standby2, and node number is 1-1:1.

    *   ARCHIVE_DEST_3='SERVICE=127.0.0.1:2803 VALID_FOR=ALL_ROLES  AFFIRM=YES', indicates the address of standby database 3, with standby database type as both normal and cascade standby, using the default name standby3.

    *   ARCHIVE_DEST_4='SERVICE=127.0.0.1:2804 DB_UNIQUE_NAME=standby4', indicates the address of standby 4, standby type as normal backup, with name: standby4.

    *   ARCHIVE_DEST_5='SERVICE=127.0.0.1:2805 NODE_ID=1-1:1 DISABLE_ELECTION=TRUE', indicates the address of standby 5, with node number 5-1:1, and this link only participates in data synchronization between primary and standby, not in the overall leader election voting and election of the primary/standby cluster.

    In a YAC, the SERVICE parameters in the above examples must list the IP and port of all instances of the standby database. For standby database 1, it would be configured as follows: ARCHIVE_DEST_1='SERVICE=127.0.0.1:2801,127.0.0.1:2901'.

*   Immediate Effect on Modification: Yes

*   Session-Level Parameter: No

*   Read-Only Parameter: No

*   Whether Multi-Instance Consistency Is Required: Yes

*   Action Scope: CDB Global Parameter

*   Introduced Version: v22.1

### ARCHIVELOG_DELETION_POLICY

*   Parameter Type: String  

*   Default Value: DEFAULT

*   Value Range/Format: [DEFAULT|NONE|BACKED UP integer TIMES|SHIPPED TO ALL STANDBY]

*   Parameter Description: Specifies the automatic and manual cleaning strategies for archived files. When performing archive cleaning operations, only archived files that meet the cleaning strategy can be cleaned.

    *   DEFAULT: Default value, indicating that the corresponding configuration of the ARCH_CLEAN_IGNORE_MODE parameter serves as the cleaning strategy for the archived files. Configuring this value is mutually exclusive with any other values.

    *   NONE: Archive cleaning does not need to meet backup times and synchronization to standby databases. This strategy is essentially equivalent to ARCH_CLEAN_IGNORE_MODE = BOTH, but is still restricted by the flashback guarantee restore point (CREATE RESTORE POINT … GUARANTEE FLASHBACK DATABASE) and the starting point of the database's redo log apply, allowing only archived log files before the permanent restore point and redo log apply starting point to be cleaned. Configuring this value is mutually exclusive with any other values.

    *   BACKED UP integer TIMES: Indicates that only archived log files that have been backed up a specified number of times (integer) are allowed to be cleaned, with an integer range of [1,15]. This can be configured together with SHIPPED TO ALL STANDBY.
    
    *   SHIPPED TO ALL STANDBY: Indicates that only archived log files that have been cleaned and synchronized to standby databases are allowed to be cleaned, which can be configured together with BACKED UP integer TIMES.

    Example of configuring archive cleaning strategies:

    *   ARCHIVELOG_DELETION_POLICY = 'BACKED UP 2 TIMES, SHIPPED TO ALL STANDBY' indicates that the archive can only be cleaned after being backed up twice and synchronized to all standby databases.

*   Immediate Effect on Modification: Yes

*   Session-Level Parameter: No

*   Read-Only Parameter: No

*   Whether Multi-Instance Consistency Is Required: Yes

*   Action Scope: Common Parameter

*   Introduced Version: v23.4.1

    Scenarios that consume session resources include user connection sessions, parallel execution, and some database background threads. Parallel execution requires exclusive session resources specified by the [MAX_PARALLEL_WORKERS](#mpara) parameter, while other session resources are shared by user connections and database background threads. ### SHARE_POOL_SIZE

- Parameter Type: Numeric  

*   Default Value: 320M

*   Value Range/Format: [0,64T]

This configuration method is for backward compatibility; it is recommended to use the first percentage configuration.

### USE_LARGE_PAGES

If the database is to use large page memory, large page memory must be configured in the operating system and refer to [Operating System Parameter Adjustments](../Installation and Upgrade/Installation and Deployment/Pre-Installation Preparation/Configuring the Installation Environment) to disable transparent huge pages; otherwise, YashanDB may be terminated abnormally by the system.

### USE_NATIVE_TYPE

*   Parameter Type: Boolean

*   Default Value: TRUE

*   Value Range/Format: [TRUE|FALSE]

*   Parameter Description: Configures whether the database uses native data types. TRUE indicates the use of native data types; FALSE indicates the use of Oracle-compatible types. When the parameter value is FALSE, the database exhibits the following behaviors:

### VM_BUFFER_SIZE

*   Parameter Type: Numeric  

*   Default Value: 128M  

*   Value Range/Format: [8M,2T]  

*   Parameter Description: Specifies the memory size used for SQL standard calculations. When the amount of data involved in sorting, materialization, JOIN, etc. during calculations is large, it is recommended to increase this parameter to enhance computational performance.

    In Standalone Deployment, YAC Deployment, or Distributed Cluster Deployment, when online modifying this parameter value (i.e., specifying SCOPE=MEMORY|BOTH), the following constraints apply:

    - Only increasing the value is allowed; the upper limit is constrained by the parameter's value range, available server memory, and the quota specified in the resource plan instruction.

    - The memory size allocated to each VM partition (the number of partitions is controlled by the hidden parameter `VM_BUFFER_PARTS`, defaulting to 1) for a single adjustment must not be less than 8MB, i.e., the adjustment difference must be greater than or equal to `8MB * VM_BUFFER_PARTS`.
